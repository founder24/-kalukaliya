Chat Pipeline — Full Trace
Stage 1 — Question Classification (pure regex, ~0ms)
prompts.classify_intent(query) runs first on every request. It's pure Python — no LLM, no network call:

Pattern detected	Intent	DB category
"hello", "hi", "thanks"…	casual	none
"notes for", "define", "explain", "MCQ"…	notes	notes
"syllabus", "course structure"…	syllabus	none
"PYQ", "previous year", "solve question"…	pyq	question_paper
"important questions"…	important_questions	important_questions
Everything else	general	none
It also computes a per-question token budget: casual gets 256 tokens, notes 2048, PYQ 6000 — so long-form questions don't burn cheap turns on one-liners.

Stage 2 — Three-Way Router (probe takes up to 500ms)
chat_router.route() picks one of three branches:

casual intent?  → direct  (no embed, no Pinecone, no web — instant)
        ↓
probe_topic_score() → similarity score vs 0.55 threshold
  score ≥ 0.55  → rag    (search your Pinecone/MongoDB chunks)
  score < 0.55  → web    (DuckDuckGo + Exa AI search)
  score = None  → rag    (probe-pending sentinel, safe default)

English probe: wai_chapter_index.classify() — embeds the question using bge-small-en-v1.5 (384-dim centroids per subject), cosine similarity. Requires subject_id to work. Without it → returns None → router defaults to rag.

Assamese probe: Cohere multilingual-v3 via AWS Bedrock → Pinecone namespace as topK=1. Also requires subject_id.

Stage 3 — RAG Retrieval (100–800ms when Pinecone has data)
When routed to rag, resolve_rag_context() runs:

Pinecone vector search (1024-dim, language-namespaced)
MongoDB BM25/keyword fallback for exact terms
Internal chapter chunks from MongoDB
User memory brain hits (personalised context)
All 4 run in parallel via asyncio.gather.

Stage 4 — Provider Chain (the main latency)
English (english_rag_chat): Vertex Gemini 2.5 Flash → Workers-AI Llama-3.2-3B fallback

Assamese (assamese_rag_chat): Sarvam-m (sole head) → Vertex Assamese → retrieval-only fallback

Stage 5 — Training knowledge fallback
When RAG returns no chunks AND no inline document is attached, the system prompt at build_rag_system_prompt() injects: "Answer from your training knowledge. Be accurate and curriculum-aligned." — BUT only when the router chose rag. If the router chose web, it never reaches this path.

Live Test Results — 3 Bottlenecks Found
Bottleneck 1 — DuckDuckGo is blocked from Replit's network (critical)

Every study question without a subject_id → probe returns None (no subject context) → goes to rag branch. But for questions WITH a subject and a score below 0.55 → router picks web → DuckDuckGo returns 0 results from Replit's IP range → V4 §12 fail-loud rule fires → 503. There is no graceful fallback to training knowledge on the web branch — this is by design (founder lock: "no silent fallbacks"). The production ACA backend uses its Azure eastus2 IP which likely has working DDG access; the Replit dev server does not.

Bottleneck 2 — Casual LLM path is slow (15s) when phrase doesn't match hardcoded dict

get_instant_response("hello how are you") returns None (only exact matches like "hello" or "hi" are in the dict). So it falls through to the full LLM provider call. Vertex Gemini 2.5 Flash responded in 15s in the test — likely cold-start latency from the Replit dev server (not the Azure ACA instance). On production ACA this runs ~800ms.

Bottleneck 3 — No subject_id → probe skipped → weaker routing signal

The embedding probe is entirely skipped when no subject_id is passed. Without it, the router can't distinguish a strong-match study question from a weak-match one — it defaults to rag and hopes Pinecone has relevant chunks. Add subject_id + subject_name + chapter_id in the request for the sharpest routing.

What works correctly
Intent classifier: fast, accurate, 0ms
Instant casual replies (exact dict matches): 0ms TTFB
RAG retrieval when subject_id is provided and Pinecone has indexed content
Assamese translation pre-processing (IndicTrans2 → Vertex polish)
Provider fallback chain inside each branch
5-layer cache (browser → CDN → KV → Redis → D1) — hits on repeated questions return in <50ms
The fail-loud 503 is intentional (V4 §12) — production ACA has working web search, so students see retries, not hallucinations
The production deployment at api.syrabit.ai is healthy and not affected by the DDG/Replit-network issue. To test locally in a way that avoids the web branch, always pass a subject_id so the probe runs and the router can make a real similarity decision.
