Root Cause 1: CHAT_CAP_DAILY = 3 (The main culprit)
The Cloudflare edge proxy was silently enforcing only 3 chat messages per day for all free and unauthenticated users. Meanwhile the chat interface showed "30 / 30 free messages left today" — a completely separate backend counter that was never actually being hit, because the edge wall fired at 3 first.

Users like the ones in the screenshot sent "hii" twice, got no response for either, and saw the generic error toast. They had 28 messages "remaining" in the display but hit an invisible wall at 3.

Fixed: CHAT_CAP_DAILY 3 → 20 in workers/edge-proxy/src/index.ts

Root Cause 2: AI_RATE_LIMIT_RPM = 30 on a shared-IP bucket
The AI route limiter allowed only 30 requests/minute per IP address — not per user, but per IP. On campus WiFi, Jio CGNAT, or any shared connection, all students collectively share this single bucket. One classroom hitting chat simultaneously could exhaust it in seconds.

Fixed: AI_RATE_LIMIT_RPM 30 → 60 in workers/edge-proxy/src/index.ts

Root Cause 3: 429 error handler regex never matched
ChatPage.jsx had a regex /daily request ceiling|sign in|anon/i to detect the daily cap error and show a helpful "Sign in" prompt. But the actual edge error message was "Daily chat allowance reached. Try again after the next UTC midnight..." — which never matched, so every single type of 429 silently fell through to the generic "Too many requests — please wait a moment and try again" toast. Users couldn't tell if they hit a rate limit, daily cap, or monthly cap.

Fixed: ChatPage.jsx 429 handler now correctly branches on errData.error === 'chat_daily_soft_cap', 'chat_budget_exhausted', and AI rate limit patterns, showing specific actionable messages for each.

Root Cause 4: Display–enforcement mismatch (20 vs 30)
The "X / 30 free messages" display came from the backend's /user/credits endpoint (30/day). The edge enforced 3/day (now 20). These were completely different counters with different keys in different systems.

Fixed across all layers:

config.py PLAN_LIMITS["free"]["credits_per_day"] 30 → 20
PLAN_PRICES["free"]["description"] updated to "20 credits/day"
ChatPage.jsx fallback display 30 → 20
AdminPlans.jsx and AdminMonetization.jsx default credits 30 → 20
Latency analysis (why responses take 3–4 s)
The English chat pipeline stacks these hops every turn:

Stage	Typical time
Edge: JWT verify + KV cap reads + DO rate checks	150–300 ms
Backend: Supabase JWKS auth	50–100 ms
Intent classification (LLM call)	200–500 ms
RAG: Workers AI embed + Pinecone + MongoDB	500–800 ms (study Qs)
LLM generation TTFT (Vertex gemini-2.5-flash)	800–2 000 ms
Total before first streaming token	1.7–3.7 s
The good news: ENABLE_PARALLEL_LLM_RACE=true is already set, and the "Fast" SLM path (@cf/meta/llama-3.2-3b-instruct) is active with ~300–700 ms TTFT. The casual/greeting path already short-circuits RAG. The primary bottleneck on study questions is the RAG embed + Pinecone round-trip (500–800 ms) followed by Vertex generation. Enabling the KV AI_RESPONSE_CACHE (currently commented out in wrangler.toml) for deterministic content types would cut the LLM call entirely for repeated queries.
