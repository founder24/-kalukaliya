### Cache Reserve (Enable for Long-Tail PYQ)

**Current state:** Zero references in code/docs → NOT enabled

**Enable via Dashboard:**
```
1. Cloudflare Dashboard → Caching → Cache Reserve
2. Toggle: ENABLE Cache Reserve
3. Select: "Cache content that is infrequently requested"
4. Save
```

**What it does:**
- Stores long-tail content in Cloudflare's global cache (even if not actively requested)
- When requested, served **instantly** (cache hit) instead of origin fetch (cache miss)
- Perfect for PYQ (Past Year Questions) — some queried rarely, some queried frequently

**Expected impact:**
- Tiered Cache: **-20-40% origin hits** = **$40-80/mo savings**
- Cache Reserve: **-15-25% cache misses** = **$20-40/mo savings**
- Combined: **+5-8% hit ratio** = **~$60-120/mo total savings**

## Task #3: Add CloudWatch Alarm on Per-Path EdgeHitRate (1 hour)

### Problem

Currently: Alarms only fire on AI-cache rows (`/api/ai/chat`)  
Missing: No alarms when `/api/seo/` or `/api/content/` hit ratio drops below target

### Implementation

**File: `infra/cloudwatch/cache-hit-ratio-alarm.yml`**

```yaml
# NEW: Per-path EdgeHitRate alarms (not just AI cache)

Alarms:
  - Name: EdgeHitRatio-SEO-Drop
    Metric: EdgeHitRate
    Namespace: Syrabit/Cache
    Dimensions:
      - Path: /api/seo/

    Comparison: LessThanThreshold
    Period: 300  # 5 minutes
    EvaluationPeriods: 3  # 15 minutes sustained drop
    Action: sns:cache-alerts

  - Name: EdgeHitRatio-Content-Drop
    Metric: EdgeHitRate
    Namespace: Syrabit/Cache
    Dimensions:
      - Path: /api/content/chapters/
    Threshold: 0.85  # Target
    Comparison: LessThanThreshold
    Period: 300
    EvaluationPeriods: 3
    Action: sns:cache-alerts

  - Name: EdgeHitRatio-PYQ-Drop
    Metric: EdgeHitRate
    Namespace: Syrabit/Cache
    Dimensions:
      - Path: /api/pyq/
    Threshold: 0.90  # Target
    Comparison: LessThanThreshold
    Period: 300
    EvaluationPeriods: 3
    Action: sns:cache-alerts

  - Name: EdgeHitRatio-Global-Drop
    Metric: EdgeHitRate
    Namespace: Syrabit/Cache
```


**Worker code change:**
```javascript
// In workers/edge-proxy/index.ts
if (path.startsWith('/chapter/') && !userKeyed) {
  cacheKey = new URL(request.url);
  cacheKey.searchParams.delete('utm_');
  cacheKey.searchParams.delete('fbclid');
  
  const cached = await caches.default.match(cacheKey);
  if (cached) {
    return cached;  // Serve entire HTML from edge
  }
  
  const response = await fetch(request);
  if (response.status === 200 && response.headers.get('content-type')?.includes('text/html')) {
    await caches.default.put(cacheKey, response.clone());
  }
  return response;
}
```

## FAQ

### Q: Why not enable everything at once?

**A:** We want **measurable impact per change**. If we enable all 6 gaps together, we can't tell which change drove which improvement. Stack them:

1. TTL bumps + exam stretches → measure hit ratio gain
2. Tiered + Cache Reserve → measure hit ratio gain
3. Alarms → measure drift detection
4. Image + HTML cache → measure hit ratio gain

### Q: What if hit ratio doesn't improve after TTL bumps?

**A:** Likely causes:
1. Traffic pattern changed (still-normal)
2. Origin sends `Cache-Control: no-store` (check headers)
3. `Vary: User-Agent` not fully stripped (check middleware)

**Fix:** Add per-path logging to trace misses:

```javascript
const missReason = response.headers.get('CF-Cache-Status');
// Cache, HIT, EXPIRED, REVALIDATED, DYNAMIC, BYPASS
if (missReason === 'DYNAMIC') {
  console.log("明知 cacheable but marked dynamic:", path);
}
```

### Q: Should I enable everything at once or in phases?

**A:** **Phased** (2-day sprint):
- Day 1: Core fixes (TTL bumps + Tiered + Cache Reserve + alarms)
- Day 2: Monitor + optional (Image + HTML cache)

**Why:** You can measure Day 1 impact → decide if Day 2 is worth it.
