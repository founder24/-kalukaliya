Migrate Railway to Digital Ocean
What & Why
Railway currently hosts two production services for Syrabit: the Python/FastAPI backend (artifacts/syrabit-backend) and the Rust "Neural Mesh Core" (backend/rust-core). We want to move both to Digital Ocean — App Platform for the Python backend (best fit for Dockerfile + env vars + managed TLS) and a Droplet running Docker for the Rust core (because App Platform doesn't cleanly expose the gRPC :50051 listener the Rust service needs alongside HTTP :3000). All deploy docs, helper scripts, and operational references to Railway should be updated so on-call docs and CI don't drift.

Done looks like
The Python backend runs on Digital Ocean App Platform from artifacts/syrabit-backend/Dockerfile, with all required env vars set, /api/health returning 200 over HTTPS at a stable DO-issued hostname.
The Rust core runs on a Digital Ocean Droplet via Docker, exposing HTTP :3000 (with /health reachable) and gRPC :50051, behind TLS, with restart-on-failure.
api.syrabit.ai (and any other Cloudflare/edge proxy origin pointers that currently target the Railway hostname workspacemockup-sandbox-production-df37.up.railway.app) point at the new DO origin, with the Cloudflare worker configs updated to match.
Nightly smoke tests, deploy guides, and the scripts/railway.sh helper are replaced (or superseded) by Digital Ocean equivalents — no broken references remain in operational docs.
A short cutover/rollback runbook exists so the team can revert to Railway if the new origin misbehaves within the first 24h.
Out of scope
Migrating Cloudflare Workers, Pages, Vectorize, R2, or any non-Railway infra.
Changing the application code itself (FastAPI routes, Rust handlers, business logic) — this is a hosting migration only.
Migrating Mongo, Postgres, Upstash Redis, or Supabase. Those stay where they are; only the connection strings move with the new compute.
Tearing down the Railway project. The plan leaves Railway running in parallel during cutover; full decommission is a follow-up once the new origin is stable.
Steps
Inventory and freeze the current Railway surface. Capture exact env vars, secrets, custom domains, healthcheck paths, exposed ports, restart policy, and resource sizing for both Railway services so the DO setup matches 1:1. Confirm the live origin host that api.syrabit.ai resolves to today.

Provision DO App Platform for the Python backend. Create the app pointing at artifacts/syrabit-backend/Dockerfile, configure the same /api/health healthcheck, port, and instance size, and load all env vars (Mongo, Postgres, Upstash Redis, Supabase, JWT/admin secrets, etc.). Validate with a non-production hostname before any DNS change.

Provision a DO Droplet for the Rust core. Stand up a Droplet, install Docker, deploy backend/rust-core/Dockerfile via docker-compose with restart-on-failure, expose :3000 (HTTP, behind TLS) and :50051 (gRPC, behind TLS), and verify /health and a gRPC handshake from outside the box.

Repoint Cloudflare and edge proxies. Update workers/edge-proxy/wrangler.toml, workers/bedrock-proxy/wrangler.toml, any monitored-urls.json entries, and the dispatch-v2 service so their origin/backend URLs point at the new DO hostnames instead of the Railway *.up.railway.app host. Cut over api.syrabit.ai DNS only after the new origin passes smoke tests.

Replace the Railway helper script and CI hooks. Retire scripts/railway.sh (or stub it to print a deprecation notice) and add a scripts/digitalocean.sh equivalent covering deploy, redeploy, logs, status, vars, var-set, var-unset against doctl / DO App Platform APIs. Update scripts/refresh-trustpilot-aggregate.mjs, scripts/cf_upgrade.sh, scripts/verify_integration.sh, deploy-neural-mesh.sh, and artifacts/syrabit/scripts/nightly-smoke.js to call the new script and hit the new origin.

Update deployment and ops documentation. Replace docs/RAILWAY-DEPLOYMENT.md and artifacts/syrabit-backend/RAILWAY-DEPLOY.md with Digital Ocean equivalents; refresh DEPLOYMENT_SUMMARY.md, DEPLOYMENT_READINESS_PLAN.md, DEPLOYMENT_BLOCKERS.md, DEPLOYMENT_COMPLETE_SUMMARY.md, PHASE1_COMPLETE.md, PHASE3_DEPLOYMENT_GUIDE.md, NEURAL_MESH_IMPLEMENTATION.md, CLOUDFLARE_DEPLOYMENT_WIRING.md, replit.md, docs/SECRET_ROTATION.md, docs/ops/mtls-activation.md, docs/cloudflare-cost-map.md, the docs/adr/redis-to-cloudflare-migration.md ADR, and the syrabit subtree docs (artifacts/syrabit/CLOUDFLARE_PAGES.md, artifacts/syrabit/docs/infra/*, artifacts/syrabit-backend/CREDITS.md, artifacts/syrabit-backend/docs/CLOUDFLARE_ZERO_TRUST.md, artifacts/syrabit-backend/CLOUDRUN-DEPLOY.md) so every Railway reference becomes the Digital Ocean equivalent or is removed.

Remove or supersede Railway config files. Delete or clearly mark backend/rust-core/railway.toml as deprecated and add the equivalent Digital Ocean App Platform spec (.do/app.yaml) for the Python backend plus a docker-compose file for the Droplet under backend/rust-core/deploy/digitalocean/.

Cutover, smoke-test, and write a rollback runbook. Run the nightly smoke suite against the new origin, verify mTLS / Cloudflare Access still works, then flip DNS. Add a short docs/ops/digitalocean-cutover.md runbook covering how to revert api.syrabit.ai and the Cloudflare worker origins back to Railway within minutes if anything regresses in the first 24h.
