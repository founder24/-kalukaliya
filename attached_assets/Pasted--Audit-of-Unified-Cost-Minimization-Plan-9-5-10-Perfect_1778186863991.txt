## ⚠️ Issue #2: **ACA minReplicas: 2 → 1 Risk During Deploy Windows**

### Problem

```
Task #597: ACA minReplicas: 2 → 1, with deploy-window safety check

Risk: During deploy, if revision-traffic policy doesn't guarantee healthy new replica,
      dropping to 1 replica before old one is confirmed healthy = potential outage
```

**Current guard:**
```python
"with deploy-window safety check (revert to 2 during active rollout if 
 revision-traffic policy doesn't guarantee a healthy new replica)"
```

**This is vague — how do you know?** Need explicit check:

### Fix (3 Lines of Code)

```yaml
# artifacts/syrabit/infra/azure/aca-syrabit-backend.bicep

// BEFORE: Deploy window safety check (vague)
// NOW: Explicit condition

resource acaBackend 'Microsoft.App/managedEnvironments@2023-05-01' = {
  name: 'aca-syrabit-backend'
  properties: {
    configuration: {
      activeRevisionsMode: 'Multiple'
    }
    templates: [
      {
        name: 'syrabit-backend'
        containers: [
          {
            name: 'backend'
            image: '[...]'
          }
        ]
        // Explicit: minReplicas depends on active revision count
        minReplicas: if(
          // If deploying AND old revision still active
          !empty(azureContainerApps.activeRevisions) && 
          length(azureContainerApps.activeRevisions) > 1
        ) {
          2  // Keep 2 during deploy
        } else {
          1  // Drop to 1 after deploy confirmed
        }
      }
    ]
  }
}
```

## ✅ Issue #4: **Mongo maxPoolSize Formula Might Be Too Conservative**

### Problem

```
Current: maxPoolSize = floor(ATLAS_MAX_CONNECTIONS × 0.7 / (MAX_ACA_REPLICAS × GUNICORN_WORKERS_PER_REPLICA))

Example:
  ATLAS_MAX_CONNECTIONS = 20,000 (100K DAU tier)
  MAX_ACA_REPLICAS = 8 (at 100K DAU)
  GUNICORN_WORKERS_PER_REPLICA = 4
  
  maxPoolSize = floor(20,000 × 0.7 / (8 × 4))
              = floor(14,000 / 32)
              = 437
```

**Is 437 too conservative?**

| Replica Count | Workers/Replica | Connection Pool | Total Connections | Utilization |
|--------------|-----------------|-----------------|-------------------|-------------|
| 2 replicas | 4 workers | 437 | 3,496 | 17% |
| 4 replicas | 4 workers | 437 | 6,992 | 35% |
| 8 replicas | 4 workers | 437 | 13,984 | 70% ✅ |
| 16 replicas | 4 workers | 437 | 27,968 | 140% ❌ |

**Problem:** At **16 replicas** (scaling above 100K DAU), utilization = 140% → **connection exhaustion**.

### Fix (Dynamic Formula)

```python
# artifacts/syrabit/backend/config.py

from math import floor

def calculate_mongo_max_pool_size():
    """
    Dynamic maxPoolSize based on actual replica count (not MAX_ACA_REPLICAS)
    """
    ATLAS_MAX_CONNECTIONS = 20000  # Free tier: 5K, paid: 20K (100K+ DAU)
    SAFETY_FACTOR = 0.7  # 70% utilization target
    
    # Get current replica count from ACA (not MAX, ACTUAL)
    current_replicas = int(os.getenv("ACA_REPLICA_COUNT", 2))
    gunicorn_workers = int(os.getenv("GUNICORN_WORKERS", 4))
    
    # Dynamic maxPoolSize per worker
    max_pool_size = floor(
        (ATLAS_MAX_CONNECTIONS × SAFETY_FACTOR) / 
        (current_replicas × gunicorn_workers)
    )
    
    # Clamp between 10-500 (reasonable bounds)
    return max(10, min(500, max_pool_size))

# Export for pymongo
MONGO_MAX_POOL_SIZE = calculate_mongo_max_pool_size()
```

**At different scales:**

| ACA Replicas | Workers | maxPoolSize | Total Connections | Utilization |
|--------------|---------|-------------|-------------------|-------------|
| 2 replicas | 4 workers | 1,750 → clamped to 500 | 4,000 | 20% |
| 4 replicas | 4 workers | 875 → clamped to 500 | 8,000 | 40% |
| 8 replicas | 4 workers | 437 | 13,984 | 70% ✅ |
| 16 replicas | 4 workers | 218 | 13,952 | 70% ✅ |
| 32 replicas | 4 workers | 109 | 13,952 | 70% ✅ |

**Verdict:** Change **static → dynamic** formula ✅
