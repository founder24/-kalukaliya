```bash
# Mongo Sharding Tradeoffs (after #363)

## Why hashed `user_id` shard key is good for OLTP, bad for OLAP
- Choosing `{ user_id: "hashed" }` optimizes **hot‑writes per user**:
  - Each user's conversation tree lives on one shard.
  - Range queries across all users become scatter‑gather.
- Future analytics queries like:
  - "all conversations between dates X and Y across all users"
  must be done via **map‑reduce‑style** scatter‑gather, not range‑scan.

## Shard‑key‑requirement on `session_id`
- Assumption: `session_id` embeds `user_id` (e.g., `u1234_session_...`).
- If `session_id` is random UUID, the plan breaks under sharding.
- Verification check:
  - Capture current `session_id` format:
    - `db.sessions.find_one()` -> check prefix or embedded `user_id`.
  - If not true, add `document.session_id = f"u{user_id}_{uuid}"` in dispatcher.
- Index requirements under sharding:
  - Ensure `conversations(session_id, ts desc)` is **sharded by `user_id`**:
    - Each shard only sees its own `user_id` conversations.
EOF
```
