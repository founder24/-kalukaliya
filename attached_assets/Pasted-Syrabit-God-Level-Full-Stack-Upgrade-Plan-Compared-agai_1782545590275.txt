ARCHITECTURE DECISIONS (IMMUTABLE RULES)
These rules govern every change below. All future work must obey them.

RULE 1 — CONTENT DUAL-PURPOSE SPLIT
  content_en / content_as   = user-facing display text (HTML/Markdown, summaries, notes)
  rag_text_en / rag_text_as = retrieval-only plain prose (extracted from PDFs, full book text)
  SAME metadata on both: board, class, subject, chapter, topic, medium
  NEVER use display content for retrieval. NEVER show raw rag_text in UI.
RULE 2 — WEB SEARCH GATING (STRICT)
  Greeting / generic → no embedding, no web, no RAG → LLM only (fast path)
  HIGH (≥0.80)       → MongoDB fast path only. NO web search.
  MID  (0.65-0.80)   → MongoDB fast path only. NO web search. (CHANGE from current)
  LOW  (0.50-0.65)   → MongoDB fast path + Vectorize + light web (scaffold only)
  NONE (< 0.50)      → web + LLM knowledge only
  BOTH stream and non-stream endpoints must apply this rule identically.
RULE 3 — SINGLE SOURCE OF TRUTH PER LAYER
  MongoDB    = authoritative for all structured data (chapters, users, chats)
  CF KV      = edge cache for library bundles (invalidated by admin)
  Redis      = ephemeral cache only (responses, history, rate limits) — never authoritative
  localStorage = UI state only (tokens, anon_id, filter preferences) — never structural data
RULE 4 — SYSTEM PROMPT LANGUAGE
  lang="en"  → English system prompt, English citations, English answer
  lang="as"  → Assamese system prompt, Assamese citations, Assamese answer
  No mixing. If rag_text is English-only, backend translates section headers only,
  not the full content (Sarvam handles cross-lingual generation).
RULE 5 — CONTENT HIERARCHY CHAIN
  Every RAG result, source card, and library card must carry the full chain:
  board_slug → class_level → stream_slug (optional) → subject_slug → chapter_slug → topic_id
  Partial chains are not allowed past the Chapter level.

PHASE 1 — CHAT CORRECTNESS

P1.1 — Fix non-streaming endpoint confidence-gated web search
File: apps/backend/app/api/v1/chat.py — async def chat() (lines 111-486)

Problem: The non-streaming /chat/ endpoint runs ChatService.retrieve_web_context() for ALL non-generic queries (line 288-295). It has no topic match score or confidence tier check. The streaming endpoint has full confidence gating; the non-streaming does not.

Fix:

# In _process_chat() inside async def chat():
# BEFORE (current — wrong):
web_chunks: list[dict] = []
if not skip_rag:
    web_chunks = await ChatService.retrieve_web_context(sanitized_message, lang=detected_lang)
# AFTER (correct — mirrors stream endpoint):
web_chunks: list[dict] = []
confidence_tier = "generic"
if not skip_rag:
    topic_match, query_embedding = await ChatService.check_topic_match_with_embedding(sanitized_message)
    match_score = topic_match.get("score", 0.0) if topic_match else 0.0
    if match_score >= CONFIDENCE_HIGH or match_score >= CONFIDENCE_MID:
        confidence_tier = "high" if match_score >= CONFIDENCE_HIGH else "mid"
        # High/Mid: MongoDB only, no web
        context_chunks = await ChatService.retrieve_context_from_chapter(
            chapter_id=topic_match.get("chapter_id"),
            chapter_title=topic_match.get("chapter_title", ""),
            detected_lang=detected_lang,
        ) if topic_match else []
    elif match_score >= CONFIDENCE_LOW:
        confidence_tier = "low"
        # Low: MongoDB + light web
        context_chunks = await ChatService.retrieve_context_from_chapter(...) if topic_match else []
        web_chunks = await ChatService.retrieve_web_context(sanitized_message, lang=detected_lang)
    else:
        confidence_tier = "none"
        # None: web only
        web_chunks = await ChatService.retrieve_web_context(sanitized_message, lang=detected_lang)

Acceptance: POST /api/v1/chat/ with a well-matched educational query returns no web_chunks and latency drops by ~200-400ms (eliminates DuckDuckGo call for HIGH/MID matches).

P1.2 — Remove web search from MID confidence tier in streaming endpoint
File: apps/backend/app/api/v1/chat.py — streaming chat_stream() function, lines ~648-672

Problem: MID (0.65-0.80) currently triggers a parallel web search in the stream endpoint. A score of 0.72 is a good topic match — web search adds noise and 200-400ms of latency.

Fix:

# BEFORE:
elif match_score >= CONFIDENCE_MID:
    # MID: MongoDB fast path + light web in parallel
    confidence_tier = "mid"
    mongo_result, web_result = await asyncio.gather(
        ChatService.retrieve_context_from_chapter(...),
        ChatService.retrieve_web_context(sanitized_message, lang=detected_lang),
        return_exceptions=True,
    )
    context_chunks = mongo_result if not isinstance(mongo_result, Exception) else []
    web_chunks = web_result if not isinstance(web_result, Exception) else []
# AFTER:
elif match_score >= CONFIDENCE_MID:
    # MID: MongoDB fast path ONLY — score is strong enough, web adds noise
    confidence_tier = "mid"
    context_chunks = await ChatService.retrieve_context_from_chapter(
        chapter_id=topic_match.get("chapter_id"),
        chapter_title=topic_match.get("chapter_title", ""),
        detected_lang=detected_lang,
    )
    web_chunks = []  # explicitly empty — no web at MID

Acceptance: A query scoring 0.72 on topic match produces no web_used: true in the SSE done event route_trace. TTFB drops by ~200ms for these cases.

P2.2 — Update RAG retrieval to prefer rag_text fields

Fix:

@staticmethod
async def retrieve_context_from_chapter(chapter_id, chapter_title, detected_lang):
    chapter = await Chapter.get(...)
    # Prefer rag_text (pure prose) over content (may contain HTML/UI markup)
    if detected_lang == "as":
        content = chapter.rag_text_as or chapter.content_as
    else:
        content = chapter.rag_text_en or chapter.content_en
    # Cross-lingual fallback: if Assamese rag_text absent, use English
    if not content and detected_lang == "as":
        content = chapter.rag_text_en or chapter.content_en

@staticmethod
def _generate_title(user_message: str) -> str:
    """First 8 words of user message, max 60 chars, stripped of special chars."""
    clean = re.sub(r'[^\w\s\u0980-\u09FF]', '', user_message.strip())
    words = clean.split()[:8]
    title = ' '.join(words)
    return title[:60] if title else "Chat"

P8.1 — MongoDB fallback for token blacklist on logout
File: apps/backend/app/api/v1/auth.py — logout() endpoint

Problem: If Redis is unavailable, logout() still returns 200 but the access token is NOT blacklisted. The user's old token remains valid until natural expiry.

Fix: On Redis failure during logout, write to MongoDB revoked_tokens collection:

try:
    redis = get_redis()
    await redis.set(f"blacklisted_token:{token_hash}", "1", ex=remaining_ttl)
except Exception:
    # Fallback: MongoDB revoked_tokens collection with TTL index on expires_at
    await db.revoked_tokens.insert_one({
        "_id": token_hash,
        "expires_at": datetime.now(timezone.utc) + timedelta(seconds=remaining_ttl),
    })
    logger.warning("Redis unavailable for token blacklist — used MongoDB fallback")

In get_current_user(), check MongoDB revoked_tokens as fallback after Redis miss:

if not blacklisted:  # Redis miss
    mongo_revoked = await db.revoked_tokens.find_one({"_id": token_hash})
    blacklisted = mongo_revoked is not None

Create TTL index: db.revoked_tokens.create_index("expires_at", expireAfterSeconds=0)

PHASE 9 — ANONYMOUS IDENTITY HARDENING (PROD)
Priority: LOW (prod correctness) Impact: anon history in CF-proxied production only

P9.1 — Ensure CF Worker passes CF-Connecting-IP to backend
Context: In production, CF Worker sits between browser and Cloud Run backend. resolve_anon_id() checks CF-Connecting-IP header first. If CF Worker does NOT forward this header, backend falls back to TCP client (Cloud Run's internal IP), making ALL anonymous users share the same identity.

Fix (CF Worker apps/edge/src/worker.ts or middleware):

// Ensure CF-Connecting-IP is forwarded to backend
const clientIP = request.headers.get('CF-Connecting-IP') || '';
newHeaders.set('CF-Connecting-IP', clientIP);

Verify: GET /api/v1/debug/anon-id (dev-only endpoint) should return ip_xxx_xxx_xxx_xxx with the actual client IP, not ip_127_0_0_1 or Cloud Run's internal IP.
