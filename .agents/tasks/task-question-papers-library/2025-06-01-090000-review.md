# Question Papers library section

Adds a "Question Papers" feature end-to-end: a Beanie document model for paper metadata, a public API endpoint that returns published papers with constructed R2 image URLs, a React Query hook, and two frontend components that display a card grid on the library page. The implementation mirrors existing patterns (CmsDocsSection, library-bundle endpoint) closely. Watch for: unbounded query with no pagination or limit on the backend (confirmed), silent error swallowing that returns 200-with-empty-array on database failures (confirmed), and hardcoded R2 base URL that duplicates the edge worker's origin (likely).

## High-level view

The backend endpoint fetches all published question papers matching optional filter criteria in a single unbounded `to_list()` call. This is consistent with how `library-bundle` works today, but question papers could grow to thousands of entries unlike the structural hierarchy data. The response is a flat list with image URLs constructed by prepending a hardcoded `https://api.syrabit.ai/assets/` prefix to the stored `r2_key`. If this origin ever changes (or differs per environment), every cached response becomes stale.

The frontend fetches the full list, displays the first 6 cards, and shows a "Showing 6 of N" message when more exist — but provides no way to actually view the rest. The section is lazy-loaded via `LazyOnVisible` + `Suspense`, following the existing pattern exactly.

## Unbounded to_list() and missing pagination

The endpoint calls `QuestionPaper.find(query).to_list()` with no limit. The library-bundle endpoint does the same thing for boards/classes/streams/subjects, but those collections are structurally bounded (a few dozen boards, a few hundred subjects). Question papers grow with every exam cycle — a few boards × several subjects × yearly releases compounds quickly. Without a limit, the endpoint will eventually pull thousands of documents, serialize them all, and send them in one response.

```python
papers = await QuestionPaper.find(query).to_list()
```

A `.limit(200)` or pagination via `skip`/`limit` query params would cap memory use and response size. The frontend already only displays 6, so fetching all is wasteful even today if the collection has more than a handful of entries.

## Silent error swallowing

When the database query fails, the endpoint logs a warning and returns an empty list with HTTP 200:

```python
except Exception as e:
    logger.warning(f"Question papers DB query failed: {e}")
    return []
```

This matches the `library-bundle` pattern — clearly intentional — but it creates an observability gap. Health checks and frontend logic cannot distinguish "collection is empty" from "MongoDB is unreachable." A middle ground: return 200 with an explicit `{"papers": [], "degraded": true}` field, or return 503 with a retry-after header.

## Truncated "View All" experience

`QuestionPapersSection` slices papers to 6 and renders a text-only message when more exist:

```jsx
{papers.length > 6 && (
  <div className="mt-4 text-center">
    <span className="text-xs text-muted-foreground">
      Showing 6 of {papers.length} papers
    </span>
  </div>
)}
```

There is no link, button, or route that shows the full set. The user learns papers exist but cannot access them. Either wire up a `/library/question-papers` route or add a "show more" button that expands the grid client-side.

## Hardcoded asset origin

The image URL is constructed server-side:

```python
"image_url": f"https://api.syrabit.ai/assets/{paper.r2_key}",
```

The edge worker serves R2 objects at `/assets/<key>` on whatever origin it's deployed to. In production that's `api.syrabit.ai`, but local/staging deployments use different origins. The existing `library-bundle` endpoint avoids this problem by not constructing URLs (it returns IDs/slugs and lets the frontend build URLs). Consider either moving URL construction to the frontend or reading the base URL from `settings`.
