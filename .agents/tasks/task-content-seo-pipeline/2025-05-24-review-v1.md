# Content Management and SEO Pipeline for Educational Platform

This change replaces a minimal two-endpoint content admin with a full content management system (39 endpoints) and a separate SEO pipeline (28 endpoints), plus 3 public endpoints. The system manages an educational content hierarchy (boards > classes > streams > subjects > chapters > topics), supports bilingual content (English + Assamese) with AI generation via Vertex AI and Sarvam, and publishes content to Azure Search for RAG retrieval. A parallel SEO pipeline extracts topics from chapters, generates multiple page types (notes, MCQs, summaries, etc.) per topic, and manages quality/publishing workflows. Supporting changes add credential guards to AI clients, make Azure Search initialization resilient, add PATCH to CORS allowed methods, and fix a timezone issue in chat.

**Watch for:** Azure Search admin key used without null-check sends an empty-string api-key on publish (confirmed). Background `asyncio.create_task` jobs have no lifecycle management—server shutdown mid-job loses progress silently (confirmed). Public endpoints expose raw ObjectId-based lookups with no rate limiting (confirmed). Duplicated code between `admin_content.py` publish and search-index endpoints, and between `extract_topics` and `_run_pipeline_job` (confirmed).

## High-level view

The content hierarchy is a five-level CRUD (boards → classes → streams → subjects → chapters) with topics embedded as subdocuments inside chapters. Each level follows an identical pattern: validate admin, parse body, insert/update/delete in MongoDB, return serialized result. The repetition is deliberate—it makes each endpoint self-contained—but it also means a bug in the pattern (like missing input validation) propagates across 20+ routes.

AI generation is split across two providers: Vertex AI produces English study notes from chapter topics, Sarvam translates to Assamese. Both clients now fail-fast if credentials are absent. The generation endpoints (`generate-notes`, `translate`) swallow AI failures into logged errors or re-raise as 500s, but never persist partial state that could confuse retry logic.

The publish pipeline chunks English content into ~512-word segments and pushes them to Azure Search's REST indexing API using the admin key. This key is `Optional[str] = None` in config, and the code falls back to an empty string rather than aborting, which will send authenticated-looking requests that Azure rejects with opaque 403s.

The SEO pipeline operates on a separate collection (`seo_topics` / `seo_pages`) and runs either synchronously (extract-topics, generate) or as fire-and-forget background tasks (auto-run, backfill-notes, run-subject). Background jobs use `asyncio.create_task` with no task registry, no cancellation support, and no graceful shutdown hook.

Public endpoints serve FAQ JSON-LD, published topics, and topic indexes. They require no authentication and have no rate limiting or caching—the only protection is that they read from MongoDB and return structured responses.

1. **Azure Search admin key empty-string fallback** — `settings.AZURE_SEARCH_ADMIN_KEY or ""` sends an empty api-key header instead of aborting. Guard against `None`/empty before making the HTTP call.
2. **Background task lifecycle** — `asyncio.create_task` jobs are fire-and-forget with no registry, no cancellation, and no shutdown hook. Add a task set and drain on app shutdown.
3. **No input validation on body fields** — Endpoints trust `request.json()` without schema validation. A missing `name` field inserts `None` into MongoDB. Use Pydantic models or at minimum null-checks.
4. **Public endpoints unprotected against abuse** — `/content/chapters/{id}/faq-jsonld`, `/content/chapters/{id}/published-topics`, `/content/subjects/{id}/topic-index` have no rate limiting or caching. Add rate limiting or Cloudflare rules.
5. **Duplicated publish/index logic** — `publish_chapter` and `index_to_search` share identical chunking and HTTP-push logic. Extract a shared helper.
6. **Duplicated topic extraction logic** — `extract_topics` endpoint and `_run_pipeline_job` contain the same Vertex AI extraction code. Consolidate.
7. **`related_by_chapter` endpoint is public on an admin router** — Mounted at `/api/v1/seo/related-by-chapter/{chapter_id}` but requires no auth, while the rest of the SEO router is admin-only.
8. **Unbounded `.to_list(1000)` / `.to_list(500)`** — Large collections will load thousands of documents into memory. Add pagination or lower the ceiling for production.
9. **AI-generated JSON parsed unsafely** — `_json.loads(result) if result.startswith("[") else []` will crash on malformed JSON (partial bracket, nested object starting with `[`). Wrap in try/except.
10. **No idempotency on topic extraction** — Without `force=True`, duplicates are skipped by exact title match, but AI may generate slightly different titles across runs, creating near-duplicates.
11. **`chunk_text` splits on whitespace only** — For Assamese or mixed-script content this may produce semantically broken chunks. Not used for Assamese currently, but `content_en` could contain code blocks or tables where word-split is lossy.
12. **`has_assamese` flag set unconditionally in translate** — `translate_chapter` sets `has_assamese: True` even when `target_lang` is not `"as"`. Should be conditional.

## Azure Search indexing without credential guard

The `publish_chapter` and `index_to_search` endpoints construct an HTTP request to Azure Search's admin REST API:

```python
"api-key": settings.AZURE_SEARCH_ADMIN_KEY or "",
```

`AZURE_SEARCH_ADMIN_KEY` is `Optional[str] = None` in config. When unset, this sends a request with an empty api-key header. Azure will return a 403 or 401, which propagates as a 500 to the caller with the message "Search indexing failed: ..." — but the failure reason is opaque because it doesn't distinguish "key not configured" from "key is wrong" from "network error." The query-side client (`azure_search.py`) already has the right pattern: check if credentials exist before constructing the client. The publish side should do the same — raise a clear error early if the admin key is absent.

Additionally, these two endpoints (`publish_chapter` and `index_to_search`) are nearly identical. The only difference is that `publish_chapter` also updates the chapter status to "published." This duplication means a fix to chunking logic or header construction must be applied in two places.

## Background task lifecycle and failure modes

Three endpoints spawn background tasks via `asyncio.create_task`: `auto_run_pipeline`, `run_subject_pipeline`, and `backfill_notes`. The created tasks are not stored anywhere. If the server receives a shutdown signal (SIGTERM in container orchestration), these tasks are cancelled without cleanup. The job document in MongoDB will remain in "running" status permanently—there's no recovery mechanism, no timeout, and no health check that detects orphaned jobs.

The pattern also means concurrent calls to `auto_run_pipeline` can spawn multiple overlapping tasks that race on the same `seo_topics` and `seo_pages` collections. There's no locking or job-level deduplication beyond the "skip if exists" check, which doesn't prevent two tasks from creating the same topic simultaneously if they read the "not exists" state before either writes.

## Input validation gaps across all CRUD endpoints

Every endpoint extracts fields from `await request.json()` without validation:

```python
doc = {
    "name": body.get("name"),  # can be None
    "slug": auto_slug(body.get("name", "")),  # produces "" slug
    ...
}
```

A request with `{}` as body creates a board with `name: null` and `slug: ""` in MongoDB. The `auto_slug` function handles the empty-string case (returns `""`), but an empty slug is semantically invalid and will cause URL routing issues if these slugs are used in Cloudflare-served pages. The subject `update_subject` endpoint validates that at least one field is present, but `create_board`, `create_class`, `create_stream`, and `create_chapter` do not validate required fields.

## Public endpoint exposure without rate limiting

The three public endpoints (`chapter_faq_jsonld`, `chapter_published_topics`, `subject_topic_index`) accept arbitrary ObjectId strings and perform MongoDB lookups with no rate limiting, no caching, and no input validation beyond what `ObjectId()` constructor provides (which raises `bson.errors.InvalidId` — an unhandled exception that will produce a 500, not a 400). An attacker can enumerate chapter IDs or DDOS the MongoDB read path.

The `related_by_chapter` endpoint in `admin_seo_pipeline.py` has the same exposure pattern—it's mounted on the admin SEO router but explicitly does not call `_validate_admin_session`, making it a public endpoint hiding in an admin module.

## Duplicated topic extraction logic

The synchronous `extract_topics` endpoint and the background `_run_pipeline_job` function contain the same Vertex AI call pattern:

```python
result = await vertex_client.generate(
    "You are an education expert. Return a JSON array...",
    f"Extract key topics from the chapter titled: {title}",
)
topics_list = _json.loads(result) if result.startswith("[") else []
```

This appears three times total (once in `extract_topics`, once in `_run_pipeline_job`, once in `pilot_run`). The JSON parsing is fragile—`result.startswith("[")` doesn't guarantee valid JSON (the model could return `[broken`), and the fallback silently produces an empty list, which means extraction failures are invisible unless you check logs.

## `has_assamese` flag logic error

In `translate_chapter`:

```python
update_data = {update_field: translated, "has_assamese": True, "updated_at": ...}
```

This sets `has_assamese = True` regardless of `target_lang`. If the endpoint is ever called with a language other than `"as"` (the code accepts arbitrary `target_lang` from the request body), the flag becomes incorrect. The guard should be `"has_assamese": target_lang == "as"`.

## Memory pressure from unbounded queries

Multiple endpoints use `.to_list(1000)` or `.to_list(500)` without pagination:

- `list_boards`: 1000
- `list_classes`: 1000
- `list_subjects`: 1000
- `list_chapters`: 1000
- `list_seo_topics`: 500
- `list_seo_pages`: 500
- `_run_pipeline_job`: 500 chapters + 1000 topics

For an educational platform with thousands of chapters across multiple boards, these queries will load entire collections into process memory. The SEO pipeline job is the worst case: it loads all chapters, then all ready topics, then iterates with individual AI calls. If the Vertex API is slow, the job holds all those documents in memory for the entire duration.
