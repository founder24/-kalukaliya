# Audit remediation: security hardening, data integrity, performance parallelization, and accessibility

This change implements approximately 30 fixes across four phases identified in a prior audit. The security layer adds NoSQL injection validation on content routes, OData injection allowlisting on search filters, HTML escaping and URL encoding in email templates, and AuthGuard wrappers on previously unprotected frontend routes. Data integrity improvements include a Redis distributed lock for the content pipeline, stale-chunk deletion before re-indexing, per-batch error handling in the search indexer, a circuit breaker for Azure Search, cache-aside persistence in content routes, and in-memory sitemap caching. Performance gains come from `asyncio.gather` parallelization in the pipeline/translator/SEO generator and `Promise.allSettled` in the admin dashboard. Accessibility and PWA fixes add ARIA labels, `List-Unsubscribe-Post` header, color-scheme support in offline.html, and a manifest `dir` field.

**Watch for:** The CI coverage threshold jump from 30% to 60% will almost certainly break the deploy workflow (confirmed). The email rate limiter and sitemap cache are both in-memory singletons that reset on every process restart and diverge across replicas (confirmed). The `_delete_stale_chunks` method in search_indexer builds a filter by interpolating the slug directly into an OData expression without escaping (confirmed). The StaffGuard redirect change from `/login` to `/` creates a redirect loop since `/` itself redirects to `/chat` which is behind AuthGuard (likely).

## High-level view

The security additions are straightforward input validation and output escaping. The NoSQL injection fix uses a strict `^[a-z0-9-]+$` regex on all path parameters. The OData tier allowlist prevents filter injection. Email templates now escape user-supplied values with `html.escape` and URL-encode the reset token. However, the search indexer introduces a new OData injection vector in `_delete_stale_chunks` by interpolating slugs directly into filter expressions without validation or escaping.

The data-integrity layer introduces multiple resilience patterns. The Redis-based pipeline lock degrades gracefully when Redis is unavailable. The circuit breaker in Azure Search is a simple in-process implementation that resets on restart and doesn't share state across workers. The cache-aside pattern in content routes persists rendered HTML back to the KnowledgeObject, creating a write-on-every-miss pattern that could amplify database writes under cold-cache bursts.

Performance parallelization is the most impactful change. The pipeline's IndexNow + Cloudflare KV steps now run concurrently, the SEO generator fires 5 vertex calls per topic in parallel, the translator batches MCQ translations with `asyncio.gather`, and the admin dashboard fires 8 API calls with `Promise.allSettled`. The translator's definitions and important_questions remain sequential (unlike MCQs), leaving latency on the table.

The CI threshold changes are aggressive: coverage raised from 30% to 60% and failure tolerance dropped from 20 to 0. Given the explicit comment in the workflow that "Redis/Upstash unavailable in CI" causes known test failures, dropping the threshold to 0 will fail every CI run that touches these paths.

## OData injection in stale chunk deletion

The new `_delete_stale_chunks` method in `search_indexer.py` constructs an OData filter by directly interpolating the knowledge object's slug:

```python
filter=f"slug eq '{knowledge_obj.slug}'"
```

The search indexer receives its `knowledge_obj` from internal pipeline calls, not directly from HTTP requests. If a KnowledgeObject's slug in the database ever contains a single quote (e.g., from a migration issue or admin manual entry), this becomes an OData injection. The fix applied to `azure_search.py` validates `user_tier` against an allowlist, but the same discipline wasn't applied here. The slug should either be validated against the same `^[a-z0-9-]+$` pattern or single quotes should be escaped to `''` per OData convention.

## CI thresholds will break deployments

The deploy workflow (`deploy-all.yml`) previously tolerated up to 20 test failures with an explicit comment: "Allow up to 20 known failures (Redis/Upstash unavailable in CI)." The comment is now contradicted by the code:

```yaml
if [ "$FAILED" -gt 0 ]; then
  echo "Test failures detected ($FAILED > 0). Failing CI."
```

The success message reads "All tests passed ($FAILED failures within threshold)" which is self-contradictory text. The coverage threshold in `ci-backend.yml` was raised from 30% to 60% without updating the adjacent comment which still says "Only fail if coverage drops below 30%."

If Redis-dependent tests aren't properly skipped (via `pytest.mark.skipif` or fixture checks), every CI run will fail. This blocks all deployments.

## Email rate limiter design gaps

The `_email_send_times` dict is never pruned of old keys. A recipient who received one email six months ago still occupies memory with an empty list as their value. Over a long-lived process this is unbounded growth proportional to unique recipients.

The `RESEND_API_URL` constant is defined twice (lines 15 and 37).

The idempotency key is computed from `to:subject:int(time() // 60)`, meaning two emails with the same subject to the same recipient within the same calendar minute get the same idempotency key. This could suppress legitimate retries if the first attempt failed at the Resend API level but returned before `raise_for_status()`.

## Pipeline distributed lock semantics

The Redis lock uses `nx=True, ex=300` (5-minute TTL) with release in a `finally` block. If the pipeline takes longer than 300 seconds, the lock expires, a second pipeline starts, and then the first pipeline's `finally` block deletes the second pipeline's lock. The standard mitigation (compare-and-delete with a unique lock value via Lua script) isn't implemented. The practical risk depends on whether any pipeline run can exceed 5 minutes, which seems unlikely but is worth noting for correctness.

## Translator parallelization is partial

MCQ translation uses `asyncio.gather` across all MCQ items, and within each MCQ translates question + explanation + options concurrently. However, the definitions loop and important_questions loop remain sequential:

```python
for defn in generated.definitions:
    translated_defn["term"] = await self.translate_text(...)
    translated_defn["definition"] = await self.translate_text(...)
```

Each `translate_text` call incurs a Sarvam API round-trip with exponential backoff on failure. The definitions and important_questions sections contribute sequential latency proportional to their count.

## Cache-aside write amplification

On a cold cache (e.g., after a deployment or database migration that clears `rendered_html`), every page request triggers both a render and a MongoDB write:

```python
obj.rendered_html[page_type] = html
await obj.save()
```

If the site receives a burst of traffic to previously-uncached pages (common during crawls), this creates write amplification. The try/except around `save()` prevents request failures but doesn't prevent the thundering herd of writes. A short-lived in-memory "recently saved" set could deduplicate writes within a single process.

## ISR cache key inflation

Including `url.search` in the cache key means bots requesting the same path with different tracking parameters (`utm_source`, `fbclid`, etc.) each create a separate KV entry. Over time this could inflate KV storage significantly. A normalized cache key (stripping known-irrelevant params) would be more space-efficient.

## AdminDashboard memory cap edge case

The `prevAlertIdsRef` eviction (`[...currentIds].slice(-500)`) keeps the last 500 from the set's insertion order. Recently-resolved alerts in the evicted first half could replay a sound notification on the next alert cycle. In practice 1000 alerts would take days to accumulate, so this is low-risk but worth documenting.
