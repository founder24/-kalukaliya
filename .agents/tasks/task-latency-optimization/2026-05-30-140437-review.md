# Multi-layer edge caching and RAG fast-path skip

This change adds two layers of caching at the Cloudflare edge worker (CF Cache API for redirect responses, KV-backed health cache shared across PoPs) and two backend optimizations (RAG timeout halved from 1.5s to 0.8s, module-level flag to skip RAG entirely when Vertex Search is uninitialized). The edge caching targets repeat visitors and monitoring/uptime probes; the backend changes reduce worst-case latency for the chat pipeline.

**Watch for:** The `_rag_available` flag is set once at process startup and never re-evaluated (confirmed) — if the search service initializes lazily or reconnects after startup, RAG stays permanently disabled for the lifetime of that process. The 302 redirect caching uses `s-maxage=3600` which means a stale redirect target persists at the edge for up to an hour after a configuration change to `ALLOWED_ORIGIN` (confirmed). The health KV caching may propagate a stale `backend_reachable=false` globally for up to 30 seconds after a backend recovers (confirmed, by design).

## High-level view

The edge worker now caches the 302 "go to frontend" redirect using Cloudflare's Cache API with a 1-hour shared TTL and 24-hour stale-while-revalidate window. This eliminates a worker invocation for repeat visitors hitting non-API paths that aren't in the R2 bucket or ISR pipeline. The trade-off is that frontend origin changes take up to an hour to propagate through edge cache.

The `/health` endpoint moves from a single per-isolate in-memory cache to a 3-layer scheme: in-memory (10s) → KV (30s) → backend fetch. The KV layer means that once one PoP fetches backend health, all other PoPs serve from KV for 30 seconds rather than each independently probing the backend. The code duplicates the backend-fetch logic in two places (KV-miss path and KV-error path), creating a maintenance concern.

On the backend, a module-level `_rag_available` flag captures `search_service._initialized` on the first call to `retrieve_context` and never rechecks. This is a process-lifetime decision: if the search service fails to initialize at startup, RAG is permanently skipped without retry. The timeout reduction from 1.5s to 0.8s tightens the tail-latency budget for the regional Vertex Search call.

## `_rag_available` as a one-shot latch

The module-level `_rag_available` flag in `chat_service.py` is set exactly once:

```python
global _rag_available
if _rag_available is None:
    _rag_available = search_service._initialized
if not _rag_available:
    return []
```

This reads `search_service._initialized` on the first invocation and caches the result indefinitely. The `VertexSearchService.__init__` sets `_initialized = True` only if all config (project, location, data store, serving config) is present at construction time. If the service starts with missing config and the config arrives later (environment variable hot-reload, secret rotation, delayed binding), `_rag_available` stays `False` for the entire worker process.

The lack of any re-check or reset mechanism means a transient initialization failure during deploy (e.g., secret manager timeout) permanently disables RAG until the pod restarts. Consider at minimum a `reset_rag_flag()` utility or a periodic re-check (e.g., every N minutes).

## 302 redirect caching at the edge

The CF Cache API integration sits at the bottom of the routing pipeline, after all specific routes have been checked:

```
caches.default.match(request) → hit? return cached
                               → miss? build 302, cache.put, return
```

The cached response includes `Cache-Control: public, s-maxage=3600, stale-while-revalidate=86400`. Cloudflare will serve the stale 302 for up to 24 hours while revalidating in the background — aggressive for a redirect whose target (`ALLOWED_ORIGIN`) could change during a domain migration or a staging/production swap. For a stable production domain this is low-risk, but worth documenting as a known operational constraint.

## Health endpoint: 3-layer caching and code duplication

The refactored health handler adds a KV layer between the existing in-memory cache and the backend fetch:

```
in-memory hit (10s) → return
  ↓ miss
KV hit (30s)        → return, refresh in-memory
  ↓ miss
backend fetch       → return, refresh in-memory, write KV (waitUntil)
  ↓ KV read throws
backend fetch       → return, refresh in-memory (no KV write attempted)
```

The KV-error fallback branch does not attempt to write to KV after a successful backend fetch. A transient KV blip (single failed read) leaves no KV entry behind, and the next PoP will also hit the backend directly until KV recovers.

The backend-fetch code is duplicated verbatim in the KV-miss path and the KV-error path (AbortController, setTimeout, fetch, clearTimeout). If the timeout or URL construction changes, both sites must be updated in lockstep. An extracted `fetchBackendHealth(env: Env): Promise<boolean>` would prevent drift.

## Test coverage gaps

Not tested: behavior when `cache.put` throws (e.g., response body already consumed), behavior when `JSON.parse(kvCached)` throws on corrupted KV data, and the interaction between the global `healthCache` and concurrent requests within the 10s window (race between two requests both seeing stale in-memory and both hitting KV).

The global `caches` stub in `tests/setup.ts` is overridden per-test in `edge-caching.test.ts`. Other test files that import the worker without their own stub will get the setup.ts version whose mock functions accumulate calls across tests without being reset — a latent assertion hazard if new test files are added.
