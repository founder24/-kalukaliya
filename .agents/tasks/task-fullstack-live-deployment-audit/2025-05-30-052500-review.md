# Full-stack live deployment audit of syrabit.ai

This PR adds a comprehensive 605-line deployment audit report (`FULLSTACK_LIVE_DEPLOYMENT_AUDIT.md`) covering the full request chain — Cloudflare Pages frontend, Cloudflare Workers edge proxy, and GCP Cloud Run backend — through a combination of live HTTP probing and static configuration review. The audit identifies 20 findings across 5 severity tiers, with two critical discoveries: the backend is completely unreachable from the edge (403 from Cloud Run, likely a missing service account key or org policy), and the www subdomain returns a 522. The report is well-structured with an executive summary, live test evidence, root-cause analysis, and a prioritized remediation matrix.

**Watch for:** The audit has a gap in verifiable evidence for the GOOGLE_SA_KEY hypothesis (confirmed); several findings conflate the same root cause into separate items inflating the count (confirmed); and the report omits circuit-breaker behavior testing that was called for in the task plan (confirmed).

## High-level view

The audit covers the full stack — DNS, SSL, frontend, edge, backend, security, integration, and performance — with live curl evidence for every connectivity claim. The two critical findings (backend 403, www 522) are well-diagnosed with plausible root causes and specific remediation steps.

The finding taxonomy shows overlap that inflates perceived severity. HIGH-02 (ingress "all" with auth required), HIGH-03 (GOOGLE_SA_KEY not configured), and HIGH-04 (--allow-unauthenticated ineffective) describe three facets of the same root issue — the backend is not reachable because authentication is required but identity tokens aren't being sent. Splitting them into three separate "High" findings makes "2 Critical + 4 High" look worse than the actual state of "1 Critical with 3 contributing causes + 1 unrelated High."

The report's weakest area is the gap between what was planned and what was delivered. The task plan called for circuit-breaker implementation review, but the report only discusses timeouts and health-check caching. The SSL section relies entirely on curl verbose output (no openssl s_client was available) without noting the reduced confidence that introduces for chain validation.

## Finding taxonomy and root-cause conflation

The remediation priority matrix lists 20 findings with severity counts (2 Critical, 4 High, 5 Medium, 4 Low, 5 Informational). This count is structurally inflated because multiple findings describe the same underlying failure from different angles.

CRIT-02 ("Backend unreachable from edge"), HIGH-02 ("Ingress 'all' with auth required"), HIGH-03 ("GOOGLE_SA_KEY likely not configured"), and HIGH-04 ("--allow-unauthenticated ineffective") all trace back to one operational state: Cloud Run requires authentication and the edge worker isn't providing valid identity tokens. The live test evidence — a 403 HTML page from Cloud Run — is the same evidence cited in all four findings. The remediation for all four converges on the same action: configure the service account key or adjust the org policy.

The worker-name mismatch (HIGH-01) is genuinely distinct — it's a deployment-targeting risk independent of the auth chain. But the backend-auth cluster should be collapsed into one Critical finding with a remediation sequence, dropping the total Highs from 4 to 1.

## Coverage gaps relative to task plan

The FEAT-001 task specification lists 10 sections, including "Review circuit breaker implementation" (Section 9) and "Check for race conditions in KV-based rate limiting" (Section 8). The delivered report addresses the rate-limiting race condition theoretically (MED-03 describes the read-then-write pattern) but provides no live test evidence — a 10-request burst would demonstrate whether the window allows bypass.

The circuit-breaker review is entirely absent. The report discusses health-check caching (10-second TTL) and timeout alignment, which are related resilience patterns, but a circuit breaker — tripping open after N failures to avoid hammering an unhealthy backend — is a distinct concern. If one exists in the codebase, the report should have assessed it. If one doesn't exist, the report should have flagged its absence given the backend is currently unreachable (the exact scenario where a circuit breaker matters).

## DNS evidence limitations

The DNS section adapts to sandbox limitations (no dig/nslookup) by using `getent hosts`, which resolves via the system resolver. This provides IP addresses but cannot show record types (CNAME vs A), TTLs, or authoritative nameservers. The report presents the results as confirmatory ("All domains resolve to Cloudflare edge IPs") without noting that `getent` cannot distinguish between a direct A record and a CNAME chain. For a deployment audit, this distinction matters — if the record is a CNAME to a Cloudflare Pages hostname vs a proxied A record, the origin configuration requirements differ.

## Severity calibration — MED-04 robots.txt elevated

MED-04 (conflicting robots.txt directives) is one finding where the severity feels elevated. The report states "Per RFC, the LAST matching rule wins for most crawlers, but behavior is not guaranteed." In practice, GPTBot follows the most specific matching user-agent block, and the conflict's worst case is GPTBot crawls a public site — a Low-severity consequence for most teams. The audit should note whether the site owner intends to block or allow GPTBot before assigning severity.

## Remediation actionability gap in medium tier

The Critical-tier remediations are specific: CRIT-02's three-step investigation sequence (verify secret → check org policies → ensure identity token) gives an operator a clear debugging path. HIGH-03 provides the exact command (`npx wrangler secret put GOOGLE_SA_KEY --env production`).

Medium-tier remediations are less consistent. MED-05 ("Ensure EDGE_SHARED_SECRET is set in both Worker secrets and backend environment variables") doesn't tell the operator how to verify the current state or what value to set. A more actionable version: "Run `npx wrangler secret list --env production` to check if EDGE_SHARED_SECRET exists. If absent, generate a 256-bit random value and set it in both `wrangler secret put` and the Cloud Run environment variable."

MED-03 ("Document as accepted risk or migrate to Durable Objects") could note the expected burst tolerance — if the KV propagation delay is ~60 seconds globally, concurrent requests within that window from different edge locations can all pass. Quantifying the gap helps the team decide whether to accept or fix.
