# Bulk hidden-functionality audit fixes across all three tiers

This change addresses 121 issues from HIDDEN_FUNCTIONALITY_AUDIT.md across the Python FastAPI backend, Cloudflare Workers edge, and React frontend. The approach is surgical: each fix targets a specific identified gap without restructuring existing code. Authentication receives fail-open on Redis blacklist checks, fail-closed on rate limiting, and atomic token refresh via SETNX. Payment flow adds signature validation, a payment record trail, and two-phase webhook idempotency. The chat pipeline gains token budget enforcement, streaming retry safety, and dead letter fallback on double-failure. The edge worker now gates X-Edge-Secret on JWT validity and injects correlation IDs.

**Watch for:** The circuit breaker's `_on_success` and `_on_failure` methods mutate `_state`, `_failure_count`, and `_success_count` without holding `_state_lock`, creating a race when multiple coroutines complete simultaneously (confirmed). The cron downgrade endpoint reuses `TRANSLATE_CRON_SECRET` as its auth mechanism, meaning anyone who knows the translation cron secret can trigger subscription downgrades (confirmed). The two-phase webhook idempotency has no actual staleness check for "processing" entries despite the comment claiming a 5-minute window (confirmed).

## High-level view

The auth layer now rate-limits forgot-password and refresh endpoints, masks PII in logs, verifies HMAC with `hmac.HMAC` (fixing the incorrect `hmac.new`), and claims refresh tokens atomically via Redis SETNX. The Redis blacklist check fails open so a Redis outage doesn't lock all authenticated users out, while the rate limiter fails closed to prevent brute-force when Redis is down.

The payment and subscription system stores payment records on verify, validates webhook amounts, extends idempotency to 35 days with a two-phase processing/completed marker, and adds a cron endpoint that downgrades expired subscriptions. The cron secret reuse and the null amount in payment records are the main concerns.

The chat pipeline enforces token budget limits before LLM calls by trimming conversation history when the prompt would exceed model context. Streaming retry logic correctly refuses to retry after chunks have already been yielded to the client. The budget trimming drops all history rather than attempting progressive reduction, and doesn't re-check after trimming.

The edge worker only attaches `X-Edge-Secret` when the JWT is actually valid, closing a privilege escalation path where an unauthenticated request could reach the backend appearing as edge-trusted. The backend's legacy shared-secret-only auth path (no HMAC) still grants full user impersonation and has no expiration mechanism.

The frontend deduplicates concurrent token refresh calls with a module-level promise mutex, wraps `sessionStorage` access in try/catch for SSR safety, and normalizes credit field names from the backend response.

<summary>Issues (9)</summary>

1. **Circuit breaker state mutation outside lock** — `_on_success()` and `_on_failure()` mutate `_state`, `_failure_count`, `_success_count` without acquiring `_state_lock`, creating races when multiple coroutines complete simultaneously. Wrap state mutations in the lock.
2. **Cron secret reuse** — `POST /cron/downgrade-expired` uses `TRANSLATE_CRON_SECRET` for authentication. Add a dedicated `CRON_DOWNGRADE_SECRET` or a general `CRON_SECRET` to avoid cross-purpose secret sharing.
3. **Payment amount not recorded** — `verify_payment` inserts a payment record with `"amount": None` because the amount isn't in the verify request body. Store the amount in Redis at order creation (like credit topup does) and read it back in verify.
4. **Token budget trimming drops all history** — When the prompt exceeds the budget, the code rebuilds `system_prompt` without history but doesn't re-check whether context alone still exceeds the limit. Add progressive trimming.
5. **Webhook body-size check is advisory** — The `content-length` header can be absent or spoofed. The body is still read in full regardless. Use a streaming body reader with a hard byte limit.
6. **Two-phase idempotency has no staleness check** — The "processing" state recovery path passes through unconditionally despite the comment claiming a 5-minute staleness check. Store a timestamp and actually compare it.
7. **Monthly reset race condition in chat.py** — The check-then-update on `last_reset_date` is not atomic. Two concurrent requests in a new month could both reset, potentially losing one increment. Use a conditional update with month precondition.
8. **Edge legacy auth path has no expiration** — The backend's shared-secret-only fallback (no HMAC) still grants full user impersonation. Add a configuration flag or deadline to disable this path.
9. **Webhook amount validation threshold** — The hardcoded `29900` paise minimum doesn't account for plan price changes or promotional pricing. Consider making this configurable or deriving it from the plan lookup.

## Circuit breaker state races

The `CircuitBreaker.call()` acquires `self._state_lock` only for the state-check phase (determining if OPEN/HALF_OPEN should block the call), then releases it before executing the wrapped function. This avoids serialization of actual HTTP calls. However, `_on_success()` and `_on_failure()` are called after `func` completes and mutate `_state`, `_failure_count`, and `_success_count` without any lock. When two coroutines complete simultaneously:

```python
def _on_failure(self):
    self._failure_count += 1  # Non-atomic read-modify-write
    self._last_failure_time = time.time()
    # ...
    elif self._failure_count >= self.failure_threshold:
        self._state = CircuitState.OPEN  # Could fire twice
```

In CPython, the GIL makes `+=` effectively atomic for integers, but the compound check-then-mutate (`if count >= threshold: state = OPEN`) is not atomic across the two lines. Under high concurrency with multiple failures, two coroutines could both read `_failure_count == 4`, both increment to 5, and both trigger the transition. The practical impact is minor (double-logging a transition), but the lock already exists and should wrap these methods too.

## Cron downgrade endpoint secret reuse

```python
cron_secret = request.headers.get("X-Cron-Secret")
if not cron_secret or cron_secret != settings.TRANSLATE_CRON_SECRET:
    raise HTTPException(status_code=403, detail="Unauthorized")
```

`TRANSLATE_CRON_SECRET` is a secret originally provisioned for the content translation pipeline. Reusing it means anyone with access to the translation cron configuration (potentially a different team or service) can trigger subscription downgrades.

## Payment record with null amount

In `verify_payment`, the payment record is inserted with `"amount": None`:

```python
await db.payments.insert_one({
    "user_id": str(user.id),
    "razorpay_order_id": body.razorpay_order_id,
    "razorpay_payment_id": body.razorpay_payment_id,
    "amount": None,  # Amount not available in verify request
    ...
})
```

The credit-topup flow demonstrates the fix: store the amount in Redis at order creation time keyed by `order_id`, read it back during verification. Without the amount, payment history records are useless for reconciliation or audit.

## Token budget overflow protection

```python
if total_tokens > max_context - 1000:
    if history:
        system_prompt = ChatService.build_system_prompt(detected_lang, context_chunks)
```

This drops history entirely but doesn't re-check whether the prompt still fits. If `context_chunks` alone produce a prompt exceeding `max_context - 1000` tokens (e.g., 5 long documents for the 4096-token Sarvam model), the LLM call proceeds over-budget. The code also doesn't attempt partial history retention; it's all-or-nothing.

## Two-phase idempotency gap

The webhook sets `"processing"` initially but the recovery path for stuck entries is:

```python
if existing == "processing":
    # Check if stuck (processing for > 5 min means previous attempt crashed)
    # Allow reprocessing for stuck entries
    pass
```

The code passes through unconditionally. There's no timestamp stored with the "processing" state and no comparison against a 5-minute threshold. A concurrent Razorpay retry arriving seconds later will reprocess the event, potentially double-charging or double-renewing.

## Edge secret gating and legacy backend fallback

The edge worker now correctly gates `X-Edge-Secret` on `jwtResult.valid`, closing the main vulnerability. However, the backend's `get_current_user` still has:

```python
# Backward compatibility: allow shared-secret-only during rollover
if not request.headers.get("X-Edge-Signature"):
    logger.warning("Edge request using legacy shared-secret-only auth...")
    user = await User.get(user_id_header)
    return user
```

This path is unreachable from the edge (which no longer sends the secret for invalid JWTs) but remains exploitable by any caller that knows the shared secret and can reach the backend directly. The rollover period has no defined end date or kill switch.
