# Static content pipeline: GCS dual-write and CDN-first frontend

This change introduces a static content serving layer. The backend gains a GCS content store that writes chapter JSON and hierarchy data on publish, plus a Cloudflare Pages deploy hook to trigger rebuilds. The frontend gains a build-time script that pulls data from GCS (or falls back to the API) and writes static JSON files and sitemaps into `public/`. Three content fetchers (`fetchBoards`, `fetchLibraryBundle`, `fetchLibraryBundleSlim`) now try `/static/*.json` before hitting the API. The `_routes.json` exclude list is updated to serve these static files directly from the CDN, bypassing the worker.

**Watch for:** The `_routes.json` now excludes sitemap paths that the worker's `SEO_PASSTHROUGH_RE` was explicitly designed to intercept — the old warning comment is left in place but contradicted by the new exclusions (confirmed). The backend never writes `library-bundle-slim.json` to GCS, yet both the build script and frontend try to fetch it from there (confirmed). The GCS bucket public-read requirement is implicit and undocumented (likely). No tests were added for any of the new backend code (confirmed).

## High-level view

The GCS store is a write-through cache — chapter publishes write to both MongoDB and GCS, with every step fail-soft. The hierarchy sync performs sequential per-entity GCS writes, which becomes a scaling bottleneck past a few hundred entities.

The frontend's static-first pattern creates a two-tier data strategy: build-time static JSON from CDN for the three heaviest payloads, with API fallback. The `_routes.json` changes transition sitemaps from worker-proxied-to-backend to build-time-generated static files, which directly contradicts the existing `_comment_xml_routes` warning written to prevent an SEO collapse.

Subject and chapter sitemaps will be empty when both GCS and API are unreachable during build. The static sitemap index is always generated regardless.

## Sitemap routing transition and contradictory documentation

The existing `_comment_xml_routes` in `_routes.json` is an explicit post-mortem note: "Sitemap paths are intentionally NOT in exclude — they MUST flow through _worker.js so it can proxy them to the backend (see SEO_PASSTHROUGH_RE). Putting them here would bypass the worker, hit the static asset pipeline, 404, and Googlebot would silently drop the sitemap (the Apr 2026 indexing collapse)."

This PR adds `/sitemap-index.xml`, `/sitemap-static.xml`, `/sitemap-subjects.xml`, `/sitemap-chapters.xml` to exclude. The reasoning is sound — the build script generates these files, so they exist in the asset pipeline and won't 404. But the old comment remains, directly contradicting the new entries. A future developer who reads that comment might remove the exclusions and break static sitemap serving.

The `_comment_static_generated` added by this PR partially addresses this, but doesn't explicitly supersede the old warning. The old comment should either be removed or amended to note that build-time-generated sitemaps are a different case.

The worker's `SEO_PASSTHROUGH_RE` still matches these paths (e.g., `/sitemap-index.xml`). Since excluded paths never reach the worker, this regex is now dead code for these specific sitemaps — harmless, but worth noting for future cleanup.

## Missing `library-bundle-slim.json` in GCS

The build script attempts:
```javascript
const bundleSlim = await fetchFromGCSOrBackend(
  "static/library-bundle-slim.json",
  "/api/content/library-bundle?slim=1"
);
```

And the frontend fetcher attempts:
```javascript
const res = await fetch('/static/library-bundle-slim.json');
```

But `hierarchy_sync.py` only calls `gcs_content_store.write_library_bundle(library_bundle)` which writes to `static/library-bundle.json`. No slim variant is ever written to GCS. The build script will always fall through to the API for the slim bundle. If the API is also unreachable during build, no `library-bundle-slim.json` is generated, and the frontend fetcher always falls through to the API at runtime — defeating the static-first optimization for this payload.

## Deploy hook: no debounce, no rate limit

`trigger_cloudflare_rebuild` fires on every `publish_chapter` call:

```python
async with httpx.AsyncClient(timeout=30.0) as client:
    response = await client.post(hook_url)
```

If an admin publishes 50 chapters in succession, 50 rebuild requests fire. Cloudflare may debounce internally, but client-side debouncing (e.g., a cooldown timer or a "rebuild pending" flag that coalesces multiple publishes into one trigger) would be more predictable. The hook URL is also a bearer secret — if it leaks, anyone can trigger unlimited builds with no authentication barrier.

## Hierarchy sync: sequential writes

`sync_hierarchy_to_gcs` writes each entity individually:

```python
for board in boards:
    await gcs_content_store.write_hierarchy("boards", str(board.id), {...})
for cls in classes:
    await gcs_content_store.write_hierarchy("classes", str(cls.id), {...})
```

Each write is a separate `asyncio.to_thread` call. For low hundreds of entities this works, but `asyncio.gather` with a semaphore would parallelize without overwhelming GCS. Not blocking for current scale but a clear optimization target.

## Frontend static-first: staleness and dev-mode noise

The static-first fetchers have no freshness signal. If static files are stale (from a previous build) and the API has newer data, the frontend serves stale data until the next build deploys. Combined with the 30-minute `staleTime` on React Query hooks, clients could serve data up to 30 minutes older than the latest build. This is acceptable for infrequently-changing content but should be documented as a known trade-off.

In development (Vite dev server), `/static/boards.json` won't exist, so every page load makes a failed fetch per fetcher before falling to the API. The empty `catch {}` handles this gracefully, but DevTools will show three red 404s on every navigation — potentially confusing for developers unfamiliar with the pattern.

## `published_topics` serialization risk

In `publish_to_gcs`:

```python
"published_topics": [
    t.model_dump() for t in chapter.published_topics
],
```

If `chapter.published_topics` is `None`, iterating raises `TypeError`. The outer `try/except Exception` catches it and logs, but the chapter silently won't be written to GCS. A defensive `chapter.published_topics or []` guard would make the fail-soft behavior explicit rather than accidental.
