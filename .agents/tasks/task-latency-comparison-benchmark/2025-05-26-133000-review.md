# Latency comparison benchmark tests for chat, edge, and page load

Three new test files simulate "old" (sequential) and "new" (parallel/optimized) code paths using controlled `asyncio.sleep`/`setTimeout` delays, then assert the optimized path is measurably faster. The tests exist to document the latency savings from optimizations made in prior tasks (parallel gather, Redis pipeline, edge trust header, middleware consolidation, Azure Search warm-up). They are pure timing assertions over mocked delays — no production code is imported or exercised.

**Watch for:** The benchmarks are tautological — they hardcode the delays they then measure, so they can never fail unless the sleep durations are changed in the test itself (confirmed). The edge test models a "4 KV ops" OLD flow that doesn't match the actual production rate-limit code, which already uses 2 ops (confirmed). The frontend test lives at a path that implies React component testing but contains no component logic (confirmed, minor).

## High-level view

The backend test creates async functions with fixed sleeps (150ms, 100ms, 25ms) and runs them sequentially for "OLD", then via `asyncio.gather` for "NEW". The assertions pass by construction because the timing is determined entirely by the sleep values authored in the test. No production module is imported, so these tests cannot detect a regression in actual code.

The edge test models an "OLD" flow with 4 sequential KV operations, but the real `rate-limit.ts` already performs only 2 KV operations (one `get`, one `put`). The benchmark's OLD baseline is fictional — it doesn't reflect any code that shipped. The result is a 50% improvement figure that overstates the actual optimization delta.

The frontend test compares sequential vs `Promise.all` for three fetch calls and verifies the well-known property that wall-clock time equals max of parallel delays. No React rendering or component behavior is involved; the test file lives alongside component tests but tests vanilla async orchestration.

## Benchmarks test themselves, not production code

The backend file defines its own `retrieve_context`, `load_conversation_history`, and `rate_limit_old_sequential` as local async closures wrapping `asyncio.sleep`. The production `chat.py` already uses `asyncio.gather` for context + history retrieval — but that code is never imported here. A developer could revert the gather in `chat.py` to sequential awaits and every benchmark test would still pass unchanged. The improvement percentages printed in CI output (50%, 94%) reflect the ratio of hardcoded sleep values, not measured system behavior.

The same pattern holds for the edge and frontend tests: they implement both code paths inline, measure them, and assert the "new" path (fewer sleeps) is faster. This makes them documentation artifacts dressed up as automated tests — they communicate the optimization rationale but provide zero regression safety.

If the goal is a living benchmark, the tests should import the production functions and mock only the external backends (Redis, Azure Search, HTTP) with controlled latency, so the gather/pipeline/Promise.all orchestration in production code is the thing being timed.

## Edge OLD baseline is fictional

The test's "OLD" flow performs 4 sequential KV operations (get monthly, get burst, put monthly, put burst). The actual `rate-limit.ts` performs a single `get` followed by a single conditional `put` — 2 operations total. The "NEW" test flow matches reality (2 ops), which means the comparison is: fictional-4-ops vs real-2-ops. The claimed 50% improvement on single-request latency is an artifact of comparing against something that never existed in production.

Similarly, the backend test's "OLD" rate limit simulates 4 sequential Redis calls at 25ms each (100ms total). The real `check_rate_limit` in `rate_limit.py` uses a pipeline for the non-edge path (2 ops batched into one `pipe.exec()` round-trip) and a single `incr` for the edge-trusted path. The test's 100ms OLD figure doesn't correspond to any real prior state.

## Frontend test placement

The file uses a `.jsx` extension, which tells the build toolchain to expect JSX syntax, but contains none. It imports nothing from React, renders no components, and tests generic `Promise.all` behavior. Placing it in `src/__tests__/` alongside component tests adds noise to the test suite inventory. A plain `.test.ts` in a separate `benchmarks/` directory would be clearer.
