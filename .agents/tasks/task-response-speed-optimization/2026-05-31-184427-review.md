# Greeting fast-path and topic-match short-circuit for response speed

The change adds two fast-path optimizations to the chat pipeline: a `has_topics()` gate on `TopicMatcher` that skips the 0.5s embedding call when no topic embeddings are cached, and a hardcoded greeting response that bypasses the LLM entirely for generic queries like "hi" or "hello". Both the non-streaming and streaming endpoints gain early-return paths. A secondary change fixes Python 3.10+ type hints (`X|Y`) to `typing.Optional` for 3.9 compatibility across several files, and corrects a misleading SSE docstring.

**Watch for:** The non-streaming greeting fast-path fires after rate-limit enforcement runs in a `gather` but before the rate-limit *result* is checked — meaning a rate-limited user still gets a free greeting response (confirmed). The streaming endpoint's `greeting_stream()` generator creates a `save_chat` task after yields complete, but if the client disconnects between yields the chat is never persisted — an asymmetry with the non-streaming path (likely).

## High-level view

The topic-match short-circuit in `has_topics()` is straightforward: same double-checked locking pattern already used by `match_topic`, returning a boolean before the expensive `generate_embedding_vector` call fires.

The greeting fast-path converts `is_generic_query` from a "skip RAG" signal into a "skip everything" signal. In the non-streaming endpoint, the greeting check sits *after* the `asyncio.gather` that concurrently fires rate-limit check, history load, and RAG retrieval — but *before* the rate-limit result is inspected. A user who has exceeded their quota still receives greeting responses. The streaming endpoint doesn't have this problem because rate limiting is checked and enforced before the greeting path.

`get_greeting_response` delegates to the `GENERIC_QUERY_PATTERN` regex, which matches "thanks", "bye", "ok", "who are you", and "what can you do" — all of which now receive the same "Hello! I'm Syrabit..." response. A user typing "bye" gets a greeting. The method name suggests a narrower scope than what actually triggers it.

## Rate-limit enforcement ordering in non-streaming path

The non-streaming `_process_chat()` runs rate limiting, RAG retrieval, and history loading concurrently in `asyncio.gather`. After the gather completes, the code unpacks results and checks `allowed`:

```python
allowed, current_count, limit, limit_type = rate_result
if not allowed:
    raise HTTPException(status_code=429, ...)
```

But the greeting fast-path is inserted *between* the gather and this check:

```python
# Fast-path for greetings: return instant response without LLM
if skip_rag:
    greeting = ChatService.get_greeting_response(sanitized_message, detected_lang)
    if greeting:
        ...
        return ChatResponse(response=greeting, model_used="cache", ...)

if cached:
    ...
```

A rate-limited user sending "hello" gets a successful response. The streaming endpoint does not have this issue — `check_rate_limit` is called and its result inspected before the greeting check.

## Streaming greeting generator and save_chat persistence gap

The `greeting_stream()` generator yields two SSE events then creates a fire-and-forget `asyncio.create_task` to persist the chat. The task is spawned only after both yields complete. If the client disconnects mid-stream (between the two yields), the generator is cancelled by Starlette before reaching the `create_task` line, so the chat is never saved. The non-streaming greeting path always persists (via `create_task` before return), creating an inconsistency: identical greetings are saved or not depending on which endpoint was used and whether the client stayed connected.
