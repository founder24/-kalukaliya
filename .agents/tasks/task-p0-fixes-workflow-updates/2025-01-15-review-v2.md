## High-level view

The fail-closed posture is now consistent across all three Redis-dependent auth paths (`get_current_user`, `refresh_token_endpoint`, `logout`). The KeyVault fetch step uses `set -euo pipefail` with `::add-mask::` before each `GITHUB_ENV` write, so pipeline failures halt rather than proceeding with empty values.

The canary deploy gates on a 10-minute 90/10 traffic-split health check (20 probes, auto-rollback at >2% error rate). The main pipeline additionally runs smoke tests post-deploy with a separate rollback job on failure — two layers of protection.

The two remaining known gaps are low-severity: PostHog only captures successful stream completions (error visibility requires structured log queries), and the Resend client singleton can theoretically double-init under concurrent first-call (mitigated by lifespan ordering).

## PostHog observability on error paths

In `chat_stream`, the `posthog.capture()` call sits inside the `event_stream()` generator, after the `"done": True` message is yielded. If the stream errors during generation (the `except Exception as e` block that yields an error JSON and returns), the generator exits before reaching PostHog. The Sarvam->Vertex double-failure path also returns early.

```python
# Only reached on success:
posthog = get_posthog(http_request)
if posthog:
    posthog.capture(...)
```

Error-rate analytics require querying structured logs rather than PostHog dashboards. If the team relies on PostHog for error-rate visibility, this is a gap worth fixing with a capture call in the error paths.

## Test coverage for fail-closed behavior

Not tested: the 503 response when Redis raises an exception during the webhook idempotency read, and the auth 503 behavior when Redis is unavailable for blacklist/revocation checks. The Redis mock fixture always returns success. These negative-path tests would strengthen confidence but aren't blocking — the implementation is a straightforward `except Exception` -> `raise HTTPException(503)`.
