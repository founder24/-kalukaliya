# P0 security/reliability hardening and CI pipeline wiring

This change addresses 11 P0-classified issues spanning authentication fail-closed behavior, Turnstile bot protection enforcement, removal of Azure OpenAI embedding infrastructure (in favor of Azure Search built-in vectorization), typed exception handling in chat endpoints, payment webhook idempotency, async email client rewrite, and PostHog observability. It also wires a canary deploy step into the deploy pipeline and adds Azure KeyVault secret injection for Container Apps.

Watch for:
- **Secrets printed to workflow logs** (confirmed): the KeyVault fetch step writes secret values into `GITHUB_ENV` via `echo`, which appears in step output unless masked.
- **Logout fails open on Redis outage** (confirmed): `get_current_user` and `refresh_token_endpoint` now fail closed (503), but the `logout` endpoint still swallows Redis errors and returns 200.
- **Chat GET endpoints bypass Turnstile** (confirmed): the edge worker only mandates Turnstile for `POST` on chat paths; `GET /api/v1/chat/history` and `GET /api/v1/chat/{session_id}/messages` pass through without bot verification.

## High-level view

The fail-closed posture for Redis unavailability is applied to `get_current_user` and `refresh_token_endpoint`, converting a silent pass into a 503. The logout endpoint was not given the same treatment — during a Redis outage, a user who logs out gets a 200 but their token remains unblacklisted. The practical window is narrow (Redis comes back, blacklist entry was never written, token is still valid for up to 60 minutes).

Azure OpenAI is fully removed: the embedding client now returns sanitized text, and Azure Search does the vectorization server-side via `VectorizableTextQuery`. This eliminates a runtime dependency (DefaultAzureCredential, httpx client, token refresh) and a configuration field. Embedding behavior is now entirely controlled by the Azure Search index skillset — if the skillset drifts, there's no local signal.

The CI pipeline wires KeyVault secrets directly into `GITHUB_ENV` and then passes them as `--set-env-vars` on the container app. GitHub will only mask values registered via `::add-mask::` — runtime-fetched values are not automatically masked.

Turnstile enforcement is extended to all `POST` on `/api/v1/chat/*` (excluding feedback). The chat `GET` endpoints are left unprotected, which is consistent for authenticated read-only data but should be a deliberate choice.

The Resend client rewrite drops the synchronous SDK + `asyncio.to_thread` pattern in favor of a lazy-init `httpx.AsyncClient` singleton with proper shutdown registration.

## Fail-closed auth and the logout asymmetry

The diff changes `get_current_user()` and `refresh_token_endpoint()` to raise `HTTPException(503)` when Redis is unreachable — previously both had bare `pass` statements. However, `logout()` still catches Redis exceptions and returns 200:

```python
except Exception as e:
    logger.error(f"Redis unavailable for token blacklisting during logout: {e}")
# (no raise — falls through to return 200)
```

During a Redis outage, a user who logs out believes their session is terminated, but the token remains usable. The refresh token is also not revoked. The practical window: Redis comes back but the blacklist entry was never written — the access token is still valid for up to 60 minutes.

The `LogoutRequest.refresh_token` field is now required (`str` instead of `Optional[str] = None`), but the docstring still says "Optionally revokes the refresh token as well." The code path uses `if body.refresh_token:` which is always truthy for a required `str` unless the user passes an empty string (Pydantic won't reject `""`). Add a `min_length=1` validator or remove the conditional.

## Webhook idempotency: fail-closed on read, fail-open on write

The webhook rejects requests when `event_id` is missing (400) or when Redis is unavailable for the dedup lookup (503). On the *write* side (marking the event as processed), Redis failures are swallowed:

```python
try:
    await redis.set(f"webhook_processed:{event_id}", "1", ex=604800)
except Exception as e:
    logger.error(f"Redis unavailable for webhook idempotency storage: {e}")
```

If this write fails, the handler returns 200 to Razorpay (stopping retries), but the event is never marked. If Redis is intermittently failing, the read succeeds (not a duplicate), processing happens, but the write fails — a subsequent retry re-processes. The subscription update is idempotent, but `send_receipt_email` is not — users may receive duplicate receipts.

## Secrets in CI workflow logs

```yaml
JWT_SECRET=$(az keyvault secret show --vault-name syrabit-kv --name jwt-secret --query value -o tsv)
echo "JWT_SECRET=$JWT_SECRET" >> "$GITHUB_ENV"
```

Values fetched at runtime via `az keyvault secret show` and written to `GITHUB_ENV` are not automatically masked by GitHub Actions. If any subsequent step prints the environment, the values appear in plain text in workflow logs.

Fix: add `echo "::add-mask::$JWT_SECRET"` for each value before writing to `GITHUB_ENV`, or use the `Azure/get-keyvault-secrets` action which handles masking automatically.

## Embedding removal and VectorizableTextQuery

The `exhaustive=True` parameter is removed from the vector query, meaning the search now uses approximate nearest neighbors (HNSW) instead of exhaustive KNN. For the 50-candidate retrieval set this is a speed/accuracy tradeoff worth noting but unlikely to materially affect RAG quality.

`AZURE_EMBEDDING_MODEL` and `AZURE_EMBEDDING_DIMENSIONS` remain in config but are no longer referenced in application code — they're dead config that could confuse future developers.

## Resend client singleton lifecycle

The `_get_client()` accessor initializes on first use with no lock. Two concurrent coroutines hitting it simultaneously could each create a client; the second assignment overwrites the first, leaking it unclosed. In practice, the lifespan startup completes before requests are served, so concurrent access would require emails during startup (which doesn't happen). Low probability, but the pattern invites a future bug if startup behavior changes.

## PostHog observability gap on error paths

The `posthog.capture()` call in `chat_stream()` fires *after* the stream completes successfully. Streams that error mid-way (including the Sarvam->Vertex fallback failure path) never emit a PostHog event. Error-path analytics are only available through structured logging, not PostHog.

## Test coverage gaps

Not tested in this diff: the 503 behavior when Redis raises an exception (the mock always succeeds). The `test_webhook_valid_signature_payment_failed` test doesn't assert that `event_id` was stored in Redis. The auth fail-closed behavior (503 on Redis outage) has no dedicated test.
