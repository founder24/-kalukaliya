# TopicHub Authority Layer and Knowledge Graph

This change introduces the TopicHub subsystem: a Beanie Document model that transforms isolated topic definitions into interconnected knowledge hubs with MCQs, Previous Year Questions, authority sources, and semantic relationships between topics. Two new services power this — KnowledgeGraphService for traversing relationships (prerequisite chains, clusters, neighbors) and AuthorityGeneratorService for AI-driven content generation via Vertex AI. Public and admin API endpoints expose the data, and integrations with the content publisher (Vertex Search indexing) and chat service (RAG context enhancement) wire the new model into the existing platform.

Watch for: N+1 query patterns in the knowledge graph traversal methods that will degrade at scale (confirmed); the `auto_generate_relations` endpoint returns raw, unvalidated AI output directly to clients without persisting it (confirmed); the `enrich_authority_sources` method generates source suggestions but never saves them anywhere (confirmed); admin endpoints accept arbitrary `hub_id` strings and will throw unhandled `bson.errors.InvalidId` exceptions on malformed input (confirmed).

## High-level view

The TopicHub model has a unique compound index on `(topic_slug, chapter_id)` enforcing the domain constraint that a topic can exist once per chapter. The model carries rich metadata fields (Bloom taxonomy, study time, formula, diagram) that are defined but never populated by any code path in this diff — they're extension points for future use.

The knowledge graph service implements three traversal patterns — direct neighbors, prerequisite chains, and BFS clusters — all backed by sequential `find_one` calls per node. This will issue O(n) database queries proportional to graph size and depth.

The authority generator delegates all content creation to Vertex AI with defensive JSON parsing. MCQs are appended-only (no deduplication or replacement strategy), so repeated calls accumulate duplicates. PYQ solutions are generated individually rather than batched, incurring one AI call per unsolved question.

The `chapter_id` disambiguator is optional on public endpoints, meaning a request for a topic slug that exists in multiple chapters will return whichever MongoDB finds first — deterministic within a query but not semantically stable. The related and study-path endpoints don't accept `chapter_id` at all.

1. **N+1 queries in graph traversal** — `get_related_topics`, `get_prerequisite_chain`, and `get_topic_cluster` each issue a separate `find_one` per relation edge. Batch-fetch related slugs with a single `find({"topic_slug": {"$in": [...]}})` query instead.
2. **Unvalidated AI output returned from generate-relations** — `auto_generate_relations` returns raw JSON from Vertex AI as the endpoint response without validating it against the `TopicRelation` schema or persisting it. Validate and optionally save before returning.
3. **enrich_authority_sources never persists** — The method returns suggested sources but doesn't append them to the hub or save. Either persist or rename to make the "suggestion-only" contract clear to callers.
4. **MCQ accumulation without deduplication** — `generate_mcqs` appends to `hub.mcqs` unconditionally. Repeated calls will duplicate questions. Add deduplication by question text or a generation batch marker.
5. **Invalid ObjectId crashes admin endpoints** — `PydanticObjectId(hub_id)` in admin endpoints throws `bson.errors.InvalidId` on malformed strings. Wrap in a try/except or use a Pydantic-validated path parameter.
6. **Ambiguous slug resolution on public endpoints** — When `chapter_id` is omitted and a `topic_slug` exists in multiple chapters, `find_one` returns an arbitrary match. Consider requiring `chapter_id` or returning a disambiguation response.
7. **PYQ solution generation is sequential** — Each unsolved PYQ triggers a separate AI call. For hubs with many PYQs, this will be slow. Batch them into a single prompt or use `asyncio.gather` with concurrency limits.

## N+1 query pattern in graph traversal

The `get_related_topics` method iterates over a hub's relations list and issues one `TopicHub.find_one({"topic_slug": ...})` per relation to fetch the related hub's title and definition. The `get_prerequisite_chain` does the same at each hop. The `get_topic_cluster` BFS is the worst case — at depth 2 with a well-connected graph, it could issue dozens of sequential queries.

```python
for relation in hub.relations:
    related_hub = await TopicHub.find_one({"topic_slug": relation.related_topic_slug})
```

The fix is straightforward: collect all `related_topic_slug` values upfront and issue a single `TopicHub.find({"topic_slug": {"$in": slugs}}).to_list()`, then build a lookup dict. For the BFS, batch each level's expansions into one query.

## Unvalidated AI output in generate_relations

The `auto_generate_relations` method parses the Vertex AI response as JSON and returns it directly. The admin endpoint surfaces this raw list in the HTTP response:

```python
relations = await authority_generator_service.generate_topic_relations(str(hub.chapter_id))
return {
    "relations_generated": len(relations),
    "relations": relations,  # raw AI JSON, no schema validation
}
```

If the LLM hallucinates extra fields or omits required ones, the response schema is unpredictable. Validate each item against `TopicRelation` (or a response-specific schema) before returning. Additionally, these relations are never persisted to any hub's `relations` list — the endpoint generates them but doesn't store them, making it a "preview" operation with no path to actually apply the results.

## enrich_authority_sources is disconnected

Unlike `generate_mcqs` (which appends to `hub.mcqs` and saves), `enrich_authority_sources` never modifies the hub:

```python
# generate_mcqs does:
hub.mcqs.extend(mcqs)
await hub.save()

# enrich_authority_sources does:
return sources  # no save
```

There's no admin endpoint that calls `enrich_authority_sources` either, so it's currently unreachable from the API.

## MCQ accumulation and deduplication gap

`generate_mcqs` calls `hub.mcqs.extend(mcqs)` and saves. If an admin triggers MCQ generation twice for the same hub, duplicate questions accumulate with no deduplication check. The simplest fix is to check `question` text against existing MCQs before appending, or to replace rather than extend.

## ObjectId validation gap in admin endpoints

All admin endpoints accept `hub_id` as a path parameter string and immediately cast it:

```python
hub = await TopicHub.get(PydanticObjectId(hub_id))
```

If `hub_id` is not a valid 24-character hex string, `PydanticObjectId()` raises `bson.errors.InvalidId`, which FastAPI will surface as a 500 Internal Server Error rather than a 400.

## Public endpoint slug ambiguity

The unique compound index ensures `(topic_slug, chapter_id)` is unique, but a topic slug alone is not unique across chapters. When `chapter_id` is omitted, `TopicHub.find_one({"topic_slug": slug})` returns whichever document MongoDB finds first — the user might get "Osmosis" from Biology Chapter 5 when they wanted it from Chemistry Chapter 3. The related and study-path endpoints don't accept `chapter_id` at all, making them always ambiguous for shared slugs.
