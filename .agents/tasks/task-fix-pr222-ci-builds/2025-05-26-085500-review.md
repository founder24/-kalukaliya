# CI pipeline fixes: gitleaks suppression, build env vars, and workflow hardening

This PR resolves multiple CI failures across the security scan, performance regression, and quality gate workflows. The gitleaks failure is fixed by removing `.replit` from git tracking and adding a path-based allowlist in `.gitleaks.toml`. The build failures are fixed by injecting `VITE_BACKEND_URL` into the two jobs that build the frontend, and by adding a MongoDB service container (plus env vars) to the quality gate's backend pytest step. A parallel set of changes hardens all workflows: top-level permissions blocks, `azure/login` downgrade from v3 to v2, and `fromJSON()` wrapping on string-to-number comparisons in `if:` conditions. The PR also includes a security fix in the chat streaming endpoint (passing sanitized input instead of raw user input to the LLM), real KV namespace IDs in `wrangler.toml`, and an expanded `.env.shared` template.

**Watch for:** The `VITE_BACKEND_URL` value `https://api.syrabit.ai` is hardcoded in two workflow files — if the backend URL changes, CI will silently build against the wrong API (confirmed). The wrangler.toml now contains real Cloudflare KV namespace IDs committed to version control — these are not secrets per se (they're IDs, not tokens), but they do expose infrastructure identifiers (confirmed). The canary deploy's `printf "%.2f"` normalization has a failure mode where `bc` failure produces `"0.00"`, which evaluates as healthy and promotes the canary (likely).

## High-level view

The gitleaks fix removes `.replit` from tracking entirely and adds a path regex allowlist in `.gitleaks.toml` to suppress historical scan hits. This is preferable to fingerprint-based suppression because it doesn't break when the file appears in multiple commits.

The build-env fix addresses the root cause of both the performance-regression and quality-gate frontend failures: the Vite build calls `check-build-env.mjs` which hard-fails without `VITE_BACKEND_URL`. The value is set at job level so all steps see it. However, `deploy-all.yml` uses `${{ secrets.VITE_BACKEND_URL }}` while these two workflows hardcode the URL — an inconsistency that will bite when the URL changes.

The workflow hardening (carried over from PR #220 fixes) downgrades `azure/login` from v3 to v2 to fix `startup_failure` on runners without node24, wraps `fromJSON()` around string outputs used in numeric comparisons, and adds least-privilege permissions blocks.

The chat endpoint fix closes a real security gap: the streaming path was passing `request.message` (raw user input) to the LLM call while the non-streaming path correctly used `sanitized_message`.

## Canary deploy numeric comparison and bc edge case

The `printf "%.2f"` wrapping ensures `fromJSON()` always receives a well-formed JSON number (e.g. `"0.00"` instead of raw `bc` output like `.00`). The `scale=4` gives `bc` enough precision before `printf` truncates to 2 decimal places.

The gap: if `bc` is missing or fails, the subshell `$(echo ... | bc)` produces empty output, and `printf "%.2f" ""` outputs `"0.00"`. Since `0.00 <= 2`, the promote step fires. The validate step catches a completely empty `error_rate` output but cannot catch `"0.00"` because that's a valid-looking value. Adding `set -o pipefail` to the `run:` block would cause the step to fail if `bc` fails, surfacing the problem instead of silently promoting.

Separately, the validate step (which exits 1 on empty error_rate) doesn't actually prevent rollback/promote from executing. In GitHub Actions, a failed step causes subsequent steps to be skipped only if those steps have no `if:` condition or use `if: success()`. Steps with custom `if:` expressions are always evaluated regardless of prior step failures. Both rollback and promote have custom `if:` conditions, so they'll run even after validate fails.

## Hardcoded backend URL inconsistency

Both `agent-performance-regression.yml` and `agent-quality-gate.yml` set `VITE_BACKEND_URL: https://api.syrabit.ai` as a literal. The `deploy-all.yml` frontend deploy uses `${{ secrets.VITE_BACKEND_URL }}`. If the secret is ever changed (staging, migration), the quality gate and perf regression jobs will build against a stale URL without any visible failure — the build will succeed, but the app will be configured to talk to the wrong backend.

## Sanitized message in streaming path

The diff at `apps/backend/app/api/v1/chat.py` changes the streaming endpoint to pass `sanitized_message` instead of `request.message` to `ChatService.call_llm_streaming()`. This closes a gap where the streaming path bypassed whatever injection defenses `sanitize_user_input()` provides while the non-streaming path was already protected.

## Wrangler KV namespace IDs

The diff replaces `REPLACE_ME` sentinel values with actual Cloudflare KV namespace IDs. These are not authentication tokens — they're namespace identifiers that still require a separate API token to access. However, they reveal infrastructure identifiers that could be used for targeted abuse if the repository is public. The deploy-all workflow's guard step that checks for remaining `REPLACE_ME` strings will now pass correctly.
