# Full-stack audit report and high-priority security fixes

A comprehensive audit report was produced (FULLSTACK\_AUDIT\_REPORT.md) and seven high-priority fixes were applied across the backend, CI, and frontend. The fixes address: JWT key separation for admin and reset tokens, rate limiter fail-open to fail-closed, bandit SAST in CI, deprecated `datetime.utcnow` removal, test coverage gates, a nonexistent TypeScript version, and test deps removed from production requirements. The approach is conservative — new secrets fall back to the existing `JWT_SECRET` when unset, and test fixtures patch out the now-failing rate limiter.

**Watch for:** The `requirements.in` references a `requirements-dev.in` that does not exist, and the compiled `requirements.txt` still contains pytest (confirmed). The `--cov` flags in CI will fail once the lockfile is recompiled. The TypeScript version was corrected from a fictional 6.0.3 but pinned to `~5.7.0` rather than the stated `~5.8.3` from the task spec (confirmed).

## High-level view

The JWT key separation adds `ADMIN_JWT_SECRET` and `RESET_TOKEN_SECRET` as optional config fields, threading them through token creation and verification in admin.py and auth.py with `or JWT_SECRET` fallback. The security benefit is zero until operators actually set separate values — there is no startup warning or documentation prompting them to do so.

The rate limiter fail-closed change flips a single `except Exception: pass` to raise a 503, with a corresponding test fixture that patches `_check_rate_limit` to a no-op for all tests. The test suite no longer exercises rate limiting logic at all — neither the 429 path nor the new 503 path.

The `requirements.in` change removes test deps and adds a comment pointing to `requirements-dev.in`, but that file was never created and the lockfile was not recompiled. CI installs from `requirements.txt`, so pytest remains available only by accident. A future `pip-compile` will break the test job.

The CI additions (bandit, coverage) work today but have a latent dependency on the stale lockfile for pytest-cov. The bandit step installs fresh on every run rather than using the cached pip install, adding avoidable latency.

## JWT key separation: backward-compatible but inert

`config.py` adds two `Optional[str]` fields defaulting to `None`. The consuming code uses `settings.ADMIN_JWT_SECRET or settings.JWT_SECRET` for both encoding and decoding, so token creation and verification are symmetric across admin.py and auth.py.

What's missing: there is no `model_validator` or startup log that warns when these fields are still `None` in production. The existing `validate_production_secrets` validator checks `JWT_SECRET` against placeholder values but does not surface that separate secrets are now available. An operator deploying this code gets zero security improvement unless they read the source or the audit report. A `logger.warning` in the validator when `ADMIN_JWT_SECRET is None and APP_ENV == "production"` would close this gap.

## Rate limiter fail-closed and test patching

The fix raises a 503 when Redis is unavailable instead of silently skipping rate limiting. The conftest patches `_check_rate_limit` to a no-op for all tests since tests run without Redis.

This means the test suite provides zero coverage of rate limiting behavior. The 429 path (too many attempts) and the new 503 path (Redis down) are both untested. A dedicated unit test for `_check_rate_limit` with a mocked Redis client would close this gap:

```python
@pytest.mark.asyncio
async def test_rate_limit_redis_down():
    """Verify 503 when Redis is unavailable."""
    with patch("app.api.v1.auth.get_redis", side_effect=ConnectionError):
        with pytest.raises(HTTPException) as exc:
            await _check_rate_limit(mock_request, "login", 10)
        assert exc.value.status_code == 503
```

## requirements.in vs requirements.txt desync

The diff removes pytest, pytest-asyncio, and pytest-cov from `requirements.in` and adds a comment saying they live in `requirements-dev.in`. But:

1. `requirements-dev.in` does not exist anywhere in the repository.
2. `requirements.txt` (the compiled lockfile, 173KB) was not recompiled and still contains all three packages with pinned hashes.
3. CI installs from `requirements.txt`, so tests still pass today — but only because the lockfile is stale.

The next time someone runs `pip-compile requirements.in`, the output will exclude pytest. The test job in `ci-backend.yml` will fail with "pytest: command not found" unless a `requirements-dev.in` + `pip install -r requirements-dev.txt` step is added to CI.

The Dockerfile also installs from `requirements.txt` and has a workaround for the pytest-asyncio/pytest version conflict (Dockerfile lines 12-17). That workaround installs test tooling into the production container — it becomes unnecessary once the lockfile is properly split, but currently remains as dead weight and expanded attack surface.

## CI coverage and bandit

The `--cov` flags require `pytest-cov` to be installed. Today this works because `requirements.txt` still contains pytest-cov. After recompilation, it will break unless the requirements-dev split is completed first.

The bandit step installs via `pip install bandit` rather than adding it to the `pip install ruff mypy` line that already exists in the same job. Moving it there (or into a lint requirements file) would let it benefit from pip caching.
