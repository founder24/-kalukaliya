# Fullstack test expansion from 306 to 1264 assertion calls

The script `scripts/fullstack-layer-test.sh` was rewritten from a 2127-line, 306-assertion test suite into a 6318-line, 1264-assertion suite (922 `pass`, 213 `warn`, 7 `fail`, 114 `skip` paths, across 415 HTTP requests). Two new layers were added (Layer 19: Users API, Layer 20: Performance & Timing) and every existing layer was expanded with granular input validation, security probes, boundary testing, and content-type enforcement. The CLI contract (`--help`, `--dry-run`, `--layer N`, `--quick`) is preserved, `bash -n` passes, and the script remains a single self-contained file.

Watch for: **Unconditional pass on unexpected status codes** — roughly 248 assertions use the pattern `pass "... returned $CURL_STATUS"` as a catch-all else-branch, meaning no HTTP status code triggers a failure (confirmed). **Temp file race in concurrent load test** — Layer 20 writes to `/tmp/concurrent_results_$$` from background processes without locking (confirmed). **Layer 18 concurrent test always reports 5/5** — it counts completed `wait` calls, not successful HTTP responses (confirmed).

## High-level view

The expansion achieves breadth by repeating a consistent pattern: for every endpoint, test the happy path, test without auth, test with malformed/malicious input (XSS, SQLi, path traversal, oversized payloads, null bytes), test boundary values (empty strings, max-length, negative numbers), and verify response metadata (Content-Type, caching headers, request-ID). This mechanical pattern scales well but yields tests that can never fail for most of the new assertions because the else-branches call `pass` regardless of the status code received.

The security-probing surface is broad: CORS origin reflection, CRLF header injection, path traversal (single and double-encoded), XSS reflection checks, SQL injection in URL paths, stack-trace and internal-IP leak detection, privilege-escalation field injection. These add real regression value because a `warn` fires on clearly-bad responses (reflected XSS, leaked stack traces, open CORS for evil origins). The gap is that none of the injection probes verify the *absence* of the attack's effect — a blind SQLi returning 200 while modifying data would pass silently.

Layer 20 (Performance & Timing) uses fixed-millisecond thresholds that aren't configurable via environment variables, unlike `BASE_URL` and `FRONTEND_URL`. A run from a high-latency client (Asia → US-Central) will produce false `warn` outputs on every timing assertion.

1. **248 unconditionally-passing assertions** — catch-all else-branches call `pass "... returned $CURL_STATUS"`, meaning no server response ever triggers failure. Convert the most important ones (auth enforcement, payment operations, admin RBAC) to `warn` or `fail` to give the suite actual teeth.
2. **Layer 18 concurrent test always reports success** — `concurrent_ok` increments on every `wait` regardless of the background process exit code or HTTP status. Capture and check curl's exit code or written status code instead of counting completed waits.
3. **Layer 20 temp file race** — multiple background `curl` processes append to `/tmp/concurrent_results_$$` simultaneously without coordination. On high contention the file may be corrupted (interleaved writes). Use per-process temp files and merge afterward, or write one result per file.
4. **1 MB base64 payload generated per run** — `head -c 1048576 /dev/urandom | base64` produces ~1.3 MB in memory and sends it as a JSON field. On resource-constrained environments (Cloud Shell free tier) this may cause curl to OOM or hit pipe limits. Consider a smaller oversized payload (e.g., 64 KB).
5. **Removed comments reduce maintainability** — explanatory comments (`# Ensure temp files are cleaned up`, `# Redact bearer tokens`) were stripped from utility functions. The `trap "rm -f..." RETURN` pattern is non-obvious; the comments served as intent documentation.

## Assertion fidelity: the "pass regardless" pattern

Across the new code, 248 assertion sites follow this structure:

```bash
if [[ "$CURL_STATUS" == "expected_good_status" ]]; then
    pass "..."
else
    pass "... returned $CURL_STATUS"
fi
```

A 500 Internal Server Error gets reported as `pass`. The pattern appears most consequentially in:

- Payment order creation (`pass "Create order returned $CURL_STATUS"` — a 500 on payment flows is a production incident)
- Auth token handling (`pass "Bearer with extra spaces returned $CURL_STATUS"` — masks broken auth parsing)
- Admin endpoint access (`pass "Admin dashboard returned $CURL_STATUS"` — could hide a 500 on the admin panel)
- User profile updates (`pass "PUT /users/me XSS in name handled ($CURL_STATUS)"` — a 500 here likely means unhandled exception)

The motivation is understandable: the test suite runs against a live deployment where some endpoints may not yet exist. But the blanket approach throws away signal. Use `warn` in catch-all branches for important endpoints, and reserve `pass` catch-alls for truly optional endpoints (education coming-soon, legacy aliases).

## Concurrent test correctness

Layer 18's concurrent test (line ~5620):

```bash
for pid in "${pids[@]}"; do
    local result
    result=$(wait "$pid" 2>/dev/null) || true
    concurrent_ok=$((concurrent_ok + 1))
done
```

`concurrent_ok` always reaches 5 because the `|| true` swallows any non-zero exit and the counter increments unconditionally. The `result` variable captures nothing useful since `wait` in bash returns the exit status (0 or non-zero), not stdout.

Layer 20 improves slightly by writing curl output to a shared file and counting "200" strings afterward, but concurrent appends from 5 background processes to a regular file can interleave (POSIX guarantees atomicity only for pipes under PIPE_BUF, not regular files on all filesystems). Use per-process temp files and merge afterward.

## Security probes: lenient effect verification

The privilege-escalation probe (`{"role":"admin","is_admin":true}` in profile update) is particularly good — it tests whether the API ignores unauthorized fields. However, none of the injection probes verify the absence of the attack's effect. The SQL injection test only checks that the status code isn't 500; it doesn't verify that a subsequent query hasn't been corrupted. Acceptable for a smoke-test suite, but means the tests would miss a blind SQLi that returns 200.

## Performance layer thresholds

Layer 20 uses fixed thresholds: health < 500ms, auth < 2s, chat < 10s, frontend < 3s. The cold-start detection heuristic (first request > 3× second request) fires on any transient network jitter, not just actual cold starts. Making thresholds configurable via env vars (e.g., `PERF_THRESHOLD_HEALTH_MS=500`) would prevent noisy false `warn` outputs in CI from non-local runners.

## Oversized payload generation

Two locations generate large random payloads:
- Line 1495: ~1 MB for signup body test
- Line 5515: ~5 MB for oversized body test

The 5 MB payload is embedded inline in a curl `-d` argument, holding the entire string in shell memory. For Cloud Shell or CI runners with limited memory, this could cause problems. A 64 KB payload would still trigger a 413 from any reasonable server configuration.
