# Agentic Workflow System for CI/CD Automation

Sixteen GitHub Actions workflows spanning PR automation, security scanning, quality gates, performance monitoring, release management, and operational alerting. The design follows a layered approach: Layer 1 handles PR/issue lifecycle, Layer 2 covers security and compliance, Layer 3 enforces quality and performance thresholds, Layer 4 automates releases and deployment. Supporting scripts handle environment variable sync and security pattern definitions.

**Watch for:** The auto-fix workflow checks out fork PRs and pushes back to them with `contents: write` and `GITHUB_TOKEN` — on public repos, this enables a code injection vector via malicious formatter configuration in the PR branch (confirmed). The canary deployment relies on `bc` for error rate calculation but has no fallback if `bc` produces empty output — fail-open to promotion (likely). The performance regression workflow references `RESULT_FILE` as an env var from a step output that is never set, so Lighthouse metrics are never parsed (confirmed).

## High-level view

The PR automation layer combines path-based labeling (via `actions/labeler@v5`) with a custom GitHub Script step that does size calculation, type inference from branch prefix, BREAKING CHANGE detection, and description validation. The issue triage workflow parses title and body against keyword regexes to assign P0-P3 priority and posts an SLA comment.

The security layer chains gitleaks, grep-based pattern scanning, pip-audit, and pnpm audit into a single workflow, with separate container scanning via Trivy. The `security-patterns.yml` config file is defined but not actually consumed programmatically by the security-scan workflow — the grep patterns are hardcoded in the workflow YAML itself, making the patterns file dead configuration.

The auto-fix workflow runs formatters on PR branches and pushes commits back. It checks out from `github.event.pull_request.head.repo.full_name`, which means it checks out code from forks. Running `pnpm install` on untrusted code (which can execute arbitrary lifecycle scripts) before formatting is a supply-chain risk on public repositories.

The canary deployment is a production-affecting workflow that uses health-check polling to decide between rollback and promotion. The health monitoring is endpoint-level only (HTTP 200 checks) with no application-level error rate or latency metrics beyond what the single `/health` endpoint reveals.

The release workflow handles versioning via manual shell arithmetic and conventional commit parsing, pushes tags and creates GitHub Releases. When triggered via the PR `labeled` event, the checkout ref is ambiguous — it will check out the merge ref rather than `main`, causing `git push origin HEAD` to fail.

The quality gate splits into backend (pytest coverage, radon complexity, vulture dead code) and frontend (bundle size) parallel jobs with a comment-results job that aggregates outputs. The performance regression workflow runs Lighthouse CI against a static `serve` of the built frontend, but the `RESULT_FILE` env var plumbing is broken so results are never actually parsed.

## Auto-fix supply-chain risk on fork PRs

The auto-fix workflow checks out the PR head using `repository: ${{ github.event.pull_request.head.repo.full_name }}`. For fork PRs on public repositories, this means attacker-controlled code enters the runner. The workflow then runs `pnpm install --no-frozen-lockfile`, which executes `preinstall`, `install`, and `postinstall` scripts from `package.json` — an attacker can inject arbitrary commands here.

The `GITHUB_TOKEN` provided to this workflow has `contents: write` and `pull-requests: write`, so any code executing during install has those permissions. The `[skip ci]` in the commit message prevents a recursive loop but does nothing for the initial execution.

Mitigation: add `if: github.event.pull_request.head.repo.full_name == github.repository` to skip fork PRs entirely, or at minimum use `pnpm install --ignore-scripts --no-frozen-lockfile`.

The `git add -A` pattern compounds this: if an install script writes files to the workspace, they get committed and pushed to the PR branch.

## Canary deployment fail-open on monitor error

The health monitor step calculates error rate using `bc`:

```bash
ERROR_RATE=$(echo "scale=2; ($FAILURE_COUNT * 100) / $TOTAL" | bc)
```

If `bc` produces unexpected output or the calculation fails, `ERROR_RATE` will be empty. The subsequent step conditions:

```yaml
if: steps.monitor.outputs.error_rate > 2   # rollback
if: steps.monitor.outputs.error_rate <= 2   # promote
```

GitHub Actions coerces empty strings to `0` in numeric comparisons. So a broken monitor (empty error_rate) results in `0 > 2` = false (no rollback) and `0 <= 2` = true (promote). The failure mode is fail-open: a completely broken health monitor promotes the canary to 100% traffic.

Fix: add a guard step that fails the workflow if `error_rate` is empty or if the monitor step failed, before reaching the promote/rollback decision.

## Performance regression RESULT_FILE gap

The "Parse Lighthouse results" step sets:

```yaml
env:
  RESULT_FILE: ${{ steps.lhci-collect.outputs.result_file || '' }}
```

The "Run Lighthouse CI collect" step never sets a `result_file` output — Lighthouse CI writes results to `.lighthouseci/` but does not expose the path as a step output. The shell portion of the parse step runs `find .lighthouseci -name 'lhr-*.json'` and stores the path in a local variable, but the Python heredoc receives `RESULT_FILE` from the env var (which is empty).

The Python script does `open(os.environ.get('RESULT_FILE', ''), 'r')` — opening an empty filename raises `FileNotFoundError`. The `exit 0` in the "No Lighthouse results" fallback never executes because it's in a different code path (the shell block that checks if `RESULT_FILE` is empty, not the Python block).

Net effect: the performance regression workflow will never successfully parse Lighthouse results, always reporting "N/A" and never detecting regressions.

## Dead security-patterns.yml configuration

The `security-patterns.yml` defines patterns for secrets, dangerous functions, injection, SSRF, and path traversal. The `agent-security-scan.yml` workflow never reads this file. The grep-based scanning step hardcodes its own patterns:

```bash
grep -rn '\b\(eval\|exec\)\s*(' apps/backend/ --include="*.py"
```

Changes to `security-patterns.yml` have no effect on scanning behavior. Either rewrite the scan step to consume the YAML (via a Python/Node script that parses patterns and runs grep dynamically), or remove the file to avoid maintenance confusion.

## Uptime monitor concurrency hazard

The uptime monitor runs every 15 minutes with `cancel-in-progress: true`. For a monitoring workflow, silent cancellation on overlap means missed alerts. If the GitHub API calls in the "Handle endpoint failure" step are slow (rate limits, retry backoff), the next scheduled run could cancel a run that detected a failure before it creates the incident issue. Use `cancel-in-progress: false`.

## License audit issue accumulation

The license-audit workflow unconditionally creates a new issue each time incompatible licenses are found:

```javascript
await github.rest.issues.create({...labels: ['compliance', 'agent-created']})
```

Unlike the environment-sync, accuracy-report, and uptime-monitor workflows (which all search for existing open issues before deciding to create or update), the license audit always creates fresh issues. If the same GPL dependency persists, a new issue appears each Monday. Fix: search for open `compliance` issues first, update if found.

## Release workflow checkout ambiguity

When triggered by `pull_request: types: [labeled]`, the default checkout ref is `refs/pull/{n}/merge` (the GitHub-constructed merge commit). The workflow then runs `git push origin HEAD`, which attempts to push to a ref that doesn't correspond to a real branch. This will fail with a "remote rejected" error.

The workflow only functions correctly via `workflow_dispatch`, where the default ref is the repository's default branch. For the label-triggered path to work, the checkout step needs `ref: main` (or `${{ github.event.pull_request.base.ref }}`).

## Unrelated node_modules changes

The diff includes changes to `node_modules/.bin/tsc` and `node_modules/.bin/tsserver` — these update hardcoded `NODE_PATH` values from a CI runner path to the sandbox path. These are environment artifacts that should not be committed. `node_modules` should typically be in `.gitignore`.
