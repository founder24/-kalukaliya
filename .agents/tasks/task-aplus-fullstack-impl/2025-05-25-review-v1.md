# Fullstack hardening: rate limiting, caching, migration system, and test scaffolds

This change implements 16 audit remediation items across four priority layers. The bulk of the work introduces burst rate limiting with Redis, a search result cache for Azure Search, a forward-only database migration tracking system, and refactors to reduce coupling in the frontend auth context and backend chat endpoint. Test coverage is expanded with Razorpay payment lifecycle tests, edge worker middleware tests (rate limiting, CORS, bot verification), and Playwright E2E scaffolds for login, chat, and navigation flows.

Watch for:
- **Token storage in sessionStorage** — access tokens and refresh tokens are persisted to sessionStorage, which is accessible to any XSS payload running in the same origin (confirmed).
- **Search cache does not include `text` in the cache key** — two requests with the same `query` + `user_tier` but different `text` parameters will return the same cached result, potentially serving stale or wrong context chunks (confirmed).
- **Burst rate limit returns ambiguous signal** — when the burst limit is exceeded, `check_rate_limit` returns `(False, burst_count, burst_limit)` rather than `(False, monthly_count, monthly_limit)`, but callers don't differentiate which limit was hit (confirmed).

## High-level view

The rate limiting refactor extracts the function from `chat.py` into its own dependency module and adds a per-minute burst check on top of the existing monthly quota. The two checks share a return signature but the tuple semantics change depending on which limit triggers, meaning the caller can't tell the user whether they hit a minute or month ceiling.

Azure Search results are cached in Redis with a 5-minute TTL keyed by SHA-256 of `query + user_tier`. The `text` parameter (which may be a raw embedding or vectorizable text and can differ from `query`) is excluded from the key, creating a correctness gap for callers that pass different values for `query` and `text`.

The AuthContext refactor splits token management, silent refresh, and anonymous data sync into standalone modules. The token manager stores JWTs in sessionStorage for tab-persistence, expanding the XSS attack surface relative to in-memory-only storage.

The migration runner is a clean forward-only system that runs after Beanie initialization. Concurrent startup replicas could race on `find_one` + `insert_one` since there's no distributed lock or `DuplicateKeyError` handling.

CI additions include a Trivy critical-severity scan, a webhook alert step in the uptime monitor, and a KV placeholder guard. The Dockerfile removes its pytest filter, relying on the `requirements-dev.in` split to keep test packages out — but no CI check enforces that invariant.

<summary>Issues (7)</summary>

1. **Search cache key excludes `text` parameter** — If `text` differs from `query` (e.g., when an embedding string is passed), the cache serves stale results. Include `text` in the hash input.
2. **Token sessionStorage exposure** — Access and refresh tokens in sessionStorage are readable by any XSS in the origin. Consider keeping tokens in memory only and relying on httpOnly cookies for persistence, or accept the trade-off and document it.
3. **Burst vs monthly ambiguity in rate limit return** — The caller receives `(False, count, limit)` but can't determine which limit was hit. Either return a discriminated tuple or raise typed exceptions.
4. **Migration runner has no distributed lock** — Two app replicas starting simultaneously could both pass the `find_one` check and attempt `insert_one`, causing a duplicate key error that propagates as unhandled startup failure. Catch `DuplicateKeyError` and treat as "already applied."
5. **Dockerfile now installs test dependencies in production** — Removing the pytest/coverage filter means `requirements.txt` packages like pytest end up in the production image if the `requirements-dev.in` split isn't enforced. Add a CI check that `requirements.txt` contains no test packages.
6. **Prompt injection patterns are trivially evadable** — Unicode confusables and character substitution bypass all regex patterns. Don't treat this as a security boundary; rely on LLM prompt delimiters as the primary defense.
7. **Payment lifecycle tests rely on module-level secret fallback** — `settings.RAZORPAY_WEBHOOK_SECRET or "test_webhook_secret"` inside each test creates fragile coupling with the handler's HMAC verification. Use a pytest fixture that patches the setting consistently.

## Search cache correctness gap

In `azure_search.py`, the cache key is computed as:

```python
cache_input = f"{query}:{user_tier}"
cache_key = f"search_cache:{hashlib.sha256(cache_input.encode()).hexdigest()}"
```

The `search_context` method accepts both `query` and `text` as separate parameters. Callers pass `text=embedding` (from `generate_embedding`) while `query` is the raw user message. If the embedding generation is deterministic for a given query this is harmless. But if `text` can vary independently (e.g., a different embedding model, truncation differences), two semantically different searches share a cache key. The fix is to include `text` in the hash or, if `text` is always derived from `query`, document that invariant and enforce it.

Empty-result queries always hit Azure Search (the cache skips storing them), which means a repeatedly-failing query creates sustained load on the Azure endpoint with no backoff.

## Token persistence and XSS surface

`useTokenManager.js` stores both access and refresh tokens in `sessionStorage`:

```javascript
sessionStorage.setItem('syrabit_token', token);
sessionStorage.setItem('syrabit_refresh_token', token);
```

Previously these lived only in module-scoped variables (`_inMemoryToken`). The refactor adds `hydrateTokensFromStorage` so tokens survive page reloads within a tab session. Any XSS vulnerability now has a trivial path to exfiltrate both tokens via `sessionStorage.getItem`. For a refresh token — which is long-lived — this is a meaningful escalation. If the application already relies on httpOnly cookies for the refresh flow, the sessionStorage copy is redundant and should be removed.

## Rate limit return semantics

`check_rate_limit` in `rate_limit.py` performs two checks in sequence: monthly quota then per-minute burst. When the burst limit triggers, the function returns:

```python
return False, burst_count, burst_limit
```

But when the monthly limit triggers, it returns:

```python
return False, current_count, limit
```

The caller in `chat.py` receives `(allowed, count, limit)` without knowing which dimension was exhausted. If the caller constructs a "you've used X of Y messages" user-facing message, it may confusingly show "6 of 5" (burst) when the user has only sent 20 of 500 monthly messages. A fourth return value (e.g., `limit_type: "burst" | "monthly"`) or separate exceptions would disambiguate.

## Migration runner race condition

`apply_migration` checks for an existing document then inserts:

```python
existing = await db.schema_versions.find_one({"version": version})
if existing:
    return False
# ... 
await db.schema_versions.insert_one({...})
```

If two app instances start concurrently, both can pass the `find_one` check before either inserts. The v001 migration itself creates a unique index on `version`, so the second insert raises `DuplicateKeyError` — but this exception isn't caught in `apply_migration`, propagating as an unhandled startup failure. Either catch `DuplicateKeyError` and treat it as "already applied," or ensure the unique index exists before the migration loop runs.

## Dockerfile test-dependency inclusion

The old Dockerfile filtered pytest, coverage, and related packages:

```dockerfile
RUN sed 's/ *\\$//' requirements.txt | grep -v '^\s*--hash' > requirements-nohash.txt \
    && pip install --no-cache-dir --user -r requirements-nohash.txt \
```

The FEAT-002 description says "test deps should not be in requirements.txt anymore per the requirements-dev.in split," but `requirements.in` is what drives `requirements.txt` generation. If anyone accidentally adds a test dep to `requirements.in`, it ships to production with no safety net. The removed filter was that safety net — replace it with a CI step that asserts `grep -E '^(pytest|coverage)' requirements.txt` returns empty.

## Prompt injection detection limitations

The detection layer is a regex list scanned after NFKC normalization and zero-width character stripping. Patterns like `"System:"` or `"Human:"` are trivially evaded with Unicode confusables (`Ꮪystem:`) or inserting characters that survive NFKC. The structured logging (`_log_injection_attempt` with truncated snippets) is a solid audit trail, but the detection itself shouldn't be treated as a security boundary. The primary defense should be LLM prompt delimiter strategies.

## Playwright E2E scaffolds

The login test has a conditional flow (`if (await emailInput.isVisible())`) that silently passes without exercising the core assertion if the selector doesn't match. This means the test can pass even when the login form is completely broken — tighten with an unconditional `expect` assertion.

The chat spec asserts page load and input interaction but doesn't verify that the mocked SSE response actually renders in the UI. The SSE mock is set up but no assertion checks for "Hello!" or "I can help you study" in the DOM — the stated purpose of the test goes unverified.
