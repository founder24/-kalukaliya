# Content hierarchy, AI generation, and SEO publish pipeline

This change adds a full educational content management backend: a five-level hierarchy (Board > Class > Stream > Subject > Chapter) modeled as Beanie Documents, CRUD and topic-management endpoints, AI-powered content generation (Vertex AI for English, Sarvam AI for Assamese translation), a publish pipeline targeting Azure Search and Cloudflare edge prerender, and an SEO layer producing FAQ JSON-LD, coverage stats, and sitemap regeneration. Two public endpoints expose published content without admin auth. 81 new tests cover models, endpoints, and services with mocked external dependencies.

**Watch for:** publish pipeline marks chapter as "published" even when Cloudflare prerender fails (confirmed); Azure Search `SearchClient` is synchronous and called inside async code without `run_in_executor` (confirmed); public endpoints expose all topic data including `id` (UUID) fields that could leak internal identifiers (likely); in-memory `_scan_history` in `admin_seo.py` loses data across process restarts (confirmed).

## High-level view

The data model is a strict parent-child chain from Board down to Chapter with topics embedded as a list inside Chapter. This embedding is a pragmatic choice for an education platform where a chapter typically has tens of topics, but it means topic updates and queries are always chapter-scoped operations, and topic IDs are globally unique UUIDs searched with `find_one({"published_topics.id": topic_id})` across the entire chapters collection.

The AI generation flow calls Vertex for English content, then passes the full response to Sarvam for Assamese translation in sequence. No retry logic, no timeout configuration on the AI clients themselves (the service relies on whatever the singleton clients provide), and no idempotency — calling generate-notes twice produces two different sets of content and overwrites the previous one.

The publish pipeline runs Azure Search indexing and Cloudflare prerender sequentially, then unconditionally sets status to "published." If Azure indexing succeeds but Cloudflare fails (returns a non-raising error dict), the chapter is still marked published, creating a state where content is searchable but not prerendered at the edge.

SEO/GEO pipeline endpoints aggregate data with `find_all().to_list()` — fine for tens or hundreds of chapters but will load all documents into memory once the catalog grows. Scan history is process-scoped and lost on restart, which is noted as acceptable for MVP.

Public endpoints serve FAQ JSON-LD and published topics without auth and without pagination, directly from the Chapter document.

1. **Publish marks "published" despite CF failure** — `publish_chapter` sets `chapter.status = "published"` after `publish_to_cloudflare` even when CF returns `{"status": "prerender_failed"}`. Check the CF result status before committing the state change, or introduce a partial-publish status.

5. **In-memory scan history lost on restart** — `_scan_history` in `admin_seo.py` persists only for the process lifetime. Persist to MongoDB if history matters beyond restarts.
6. **meta_description truncation is naive** — `content_en[:160]` can cut mid-word or mid-sentence. Truncate at the last sentence or word boundary within 160 chars.
7. **FAQ JSON-LD uses empty string for missing definitions** — When `topic.definition` is `None`, the FAQ answer text becomes `""`. Search engines may penalize empty answers or ignore the entry. Consider skipping topics without definitions.

## Publish pipeline: partial-failure state gap

`ContentPublisherService.publish_chapter()` calls `publish_to_azure_search`, then `publish_to_cloudflare`, then saves the chapter with status "published" regardless of the Cloudflare outcome. The Cloudflare method is designed to never raise — it catches all exceptions and returns a dict with `"status": "prerender_failed"`. The caller does not inspect this dict:

```python
search_result = await self.publish_to_azure_search(chapter)
cf_result = await self.publish_to_cloudflare(chapter)
chapter.status = "published"
await chapter.save()
```

If Azure indexing itself raises (network failure, auth error), the exception propagates and the status stays unchanged — correct behavior. But if Azure succeeds and Cloudflare fails silently, the response includes the failure detail, yet the chapter is permanently marked published. A consumer querying pipeline-status would see it as fully published when the edge cache never received it.

The inverse issue also applies: if you later re-run just the `/publish/pages` endpoint after fixing the CF issue, the chapter is already "published" so there's no status inconsistency from the DB perspective, but there's no record of the partial failure to surface in pipeline-status.

## Synchronous Azure SDK call inside async handler

`SearchClient` from `azure-search-documents` is a synchronous client. `upload_documents()` performs network I/O blocking the event loop for the duration of the upload:

```python
search_client = SearchClient(
    endpoint=settings.AZURE_SEARCH_ENDPOINT,
    index_name=settings.AZURE_SEARCH_INDEX_NAME,
    credential=AzureKeyCredential(settings.AZURE_SEARCH_ADMIN_KEY),
)
result = search_client.upload_documents(documents=documents)
```

For a chapter with substantial content (target 1500+ words, ~3-4 chunks at 512 tokens each), this blocks for the duration of 3-4 document uploads. Under concurrent requests, this will starve the event loop. The Azure SDK provides `azure.search.documents.aio.SearchClient` for async use, or the call can be wrapped in `asyncio.to_thread()`.

## Unbounded list endpoints

Every list endpoint calls `.find_all().to_list()` or `.find(query).to_list()` without a limit parameter. For the content hierarchy this is likely fine in the short term (tens of boards, hundreds of chapters), but `seo/pipeline-status` and `seo/coverage` load *all* chapters and *all* subjects to compute aggregations in Python. At scale, this should use MongoDB aggregation pipelines or at minimum add `.limit()` calls.

The public endpoints (`/published-topics`, `/faq-jsonld`) return the full embedded topic list for a single chapter, which is bounded by chapter scope — not a concern.

## Topic operations: cross-collection scan

`PATCH /content/topics/{topic_id}` and `DELETE /content/topics/{topic_id}` use `Chapter.find_one({"published_topics.id": topic_id})`. There's no index defined on `published_topics.id` in `create_indexes()`. The chapters index covers `(subject_id, status)`. As the chapters collection grows, these topic-level operations will perform a full collection scan to find which chapter contains the topic. An index on `published_topics.id` or a design change (topic IDs include chapter context) would fix this.

## AI generation: no idempotency or retry

Calling `POST /content/chapters/{id}/generate-notes` twice overwrites the previous content without confirmation or versioning. There's no draft-vs-committed distinction for AI-generated content. If a generation call partially fails (Vertex succeeds but Sarvam times out), the method will raise and the chapter stays in its prior state — acceptable fail-closed behavior. But if both succeed but the content is poor, there's no way to revert without re-generating.

No retry logic is present in the service layer; it relies on the AI clients' internal retry behavior (if any). The prompts are well-structured with clear instructions and constraints.

## Content chunking heuristic

The `_chunk_content` function splits on double newlines and estimates tokens at 4 chars/token. This is a reasonable approximation for English text but will under-count for Assamese (where characters encode more semantic content). Since only `content_en` is indexed to Azure Search currently, this is acceptable. If Assamese content is later indexed, the chunking logic needs language-aware tokenization.

## Security: public endpoints and data exposure

The two public endpoints (`/content/chapters/{id}/faq-jsonld` and `/content/chapters/{id}/published-topics`) are intentionally unauthenticated. They expose:

- Topic UUIDs (internal identifiers) via `model_dump()` on published-topics
- FAQ JSON-LD entries including definition text
- Chapter IDs (ObjectIds)

The ObjectIds and UUIDs are not secrets, but exposing internal IDs in public APIs creates coupling where consumers may start using them. The topics endpoint returns `model_dump()` which includes `definition_status` (an internal workflow field). Consider a response schema that excludes internal fields.

The admin endpoints all consistently call `_validate_admin_session(request)` and mutating ones additionally call `await _csrf_check(request)`. No endpoints mix auth levels or skip CSRF on mutations.

## Test coverage gaps

Tests mock external services comprehensively (Beanie Documents, AI clients, Azure SDK). The 81 tests cover:
- Model instantiation and field defaults
- Auth enforcement (401 without session)
- CRUD happy paths
- AI generation with mocked clients
- Publish pipeline with mocked Azure/CF
- Public endpoint access without auth
- 404 handling for missing resources

Not tested:
- Partial publish failure scenario (Azure OK, CF fails) — the status is still set to "published"
- Concurrent topic updates on the same chapter (race condition on embedded list)
- Chunking edge cases (content shorter than one chunk, content with only single newlines)
- `bulk-generate` endpoint (SEO generation for multiple topics)
- `entity/refresh` health score calculation logic
- Sitemap XML output format validity
