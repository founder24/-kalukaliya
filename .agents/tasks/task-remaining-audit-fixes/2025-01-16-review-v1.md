# Multi-layer audit remediation: dependency swap, prompt hardening, chat refactor, caching, and CI tightening

This change addresses twelve audit findings across the backend, frontend, edge, and CI layers. The headliners: python-jose replaced with PyJWT, prompt injection filtering hardened with Unicode normalization and multi-pattern scoring, `chat.py` decomposed from 714 lines into a thin router plus `ChatService`, Redis caching added for search and conversation history, `AuthContext.jsx` split into focused hooks, and CI lockfile integrity restored with `--frozen-lockfile`. The CI also gains Trivy container scanning and bandit SAST.

**Watch for:** The `ChatService.search_with_cache` cache key omits the raw query text, so different inputs with identical (query+tier+limit) hash collide (confirmed). The `is_safe_url` DNS resolution is still vulnerable to TOCTOU/DNS rebinding since it resolves once then trusts the URL for later use by a different consumer (likely). The conversation history cache has no size bound, meaning a single long session could store a 2KB Redis value per session_id with no eviction beyond the 30-min TTL (possible).

## High-level view

The prompt injection filter is materially stronger than the baseline. NFKC normalization and zero-width stripping close the homoglyph and invisible-char bypass vectors. The scoring system (reject on 2+ patterns) is a useful heuristic, though the single-pattern path still strips-and-continues rather than rejecting, so a sophisticated adversary only needs to avoid triggering two patterns simultaneously.

The chat refactor extracts business logic cleanly but introduces a cache key design problem: the search cache hashes `query + user_tier + limit` via MD5 without including the `text` parameter (the embedding), which means two different messages that produce the same sanitized query string will share cached results regardless of their embeddings. Additionally, `process_chat` duplicates the save logic that already exists in `save_chat`, creating a maintenance fork.

The frontend `AuthContext` decomposition uses module-level `let` variables for in-memory tokens, which works for the SPA single-instance model but makes the hook untestable in isolation without resetting global state between test cases.

The CI changes correctly restore lockfile integrity (`--frozen-lockfile`), add Trivy scanning with fail-on-critical policy, and separate test deps from production requirements. The `pnpm-lock.yaml` still carries a phantom `typescript@6.0.3` resolution alongside the corrected `5.8.3`.

<summary>Issues (7)</summary>

1. **Search cache key ignores embedding input** (confirmed) — `search_with_cache` hashes `query + user_tier + limit` but the actual search call also takes a `text` parameter (the embedding). Two queries with identical sanitized text but different embedding outputs will share cached results. Include `text` in the hash or use `text` alone as the cache discriminator.
2. **Single-pattern injection bypass** (confirmed) — When exactly one pattern matches, the filter strips the match and returns the remaining text. A payload carefully constructed to trigger only one pattern can still inject the non-matched content. Consider rejecting (returning empty) on any match, or at minimum logging the single-match case for monitoring.
3. **DNS rebinding in is_safe_url** (likely) — The function resolves the hostname once and returns a boolean, but the caller presumably uses the URL later with a separate connection. An attacker could serve a short-TTL DNS record that resolves to a public IP during validation but to a private IP during the actual fetch. Binding the validated IP to the subsequent request would close this gap.
4. **TypeScript 6.0.3 still in lockfile** (confirmed) — The `pnpm-lock.yaml` change adds `typescript@5.8.3` but retains `typescript@6.0.3` as a resolved package. Both versions are present; the specifier in `package.json` now points to `~5.8.3`, but the old phantom resolution remains, inflating `node_modules`.
5. **ChatService.process_chat duplicates save_chat logic** (confirmed) — `process_chat` manually creates and saves a `Chat` document inline rather than calling `self.save_chat()`. Any future change to the save logic must be made in two places.
6. **MD5 used for cache key generation** (confirmed) — `search_with_cache` uses MD5 to hash the cache key. While not a security concern here (it's used for cache bucketing, not integrity), it could lead to collisions on high-volume deployments. SHA-256 truncated to 16 bytes would be equally fast and collision-resistant.
7. **ISR_CACHE_KV placeholder will fail Wrangler deploy** (confirmed) — The `wrangler.toml` placeholder IDs (`placeholder-isr-cache-kv-id`) will cause `wrangler deploy --env production` to fail with an invalid namespace error. The documentation comment explains this, but there is no CI guard to catch an accidental deploy with the placeholder still in place.

## Prompt injection scoring — the single-pattern gap

The pattern list grew from 7 to 14 entries, covering `DAN mode`, `jailbreak`, `disregard previous`, `override instructions`, and LLM role markers like `<|system|>`, `ASSISTANT:`, `Human:`. NFKC normalization and zero-width stripping are applied before pattern matching, closing the two most common bypass techniques.

The single-pattern path is the remaining soft spot. If an attacker triggers exactly one pattern, the text is stripped of that match and the rest passes through. This means injections that use only one technique (e.g., a lone `Human:` prefix followed by a carefully crafted payload) will have the marker removed but the payload preserved. The scoring threshold only kicks in at 2+. The asymmetry between "strip one" and "reject two" creates a gap where carefully-limited injections can pass content through the filter.

## Search cache key collision

```python
cache_key = f"search:{hashlib.md5((query + user_tier + str(limit)).encode()).hexdigest()}"
```

The method signature is `search_with_cache(self, query, text, user_tier, limit)`, and the actual search call passes `text` (the embedding) to `search_service.search_context`. But `text` is not included in the cache key. Since `text` is derived from `generate_embedding(sanitized_message)` and `query` is the same sanitized message, collisions require the embedding function to be non-deterministic or two different raw inputs to sanitize to the same string. The risk is low but the fix is trivial: include `text` in the hash.

## process_chat duplicates save logic

`ChatService` has a `save_chat` method that creates a `Chat` document, adds messages, saves, and invalidates cache. But `process_chat` does not call it — it manually constructs and saves inline:

```python
chat_doc = Chat(user_id=user_id if user else None, session_id=session_id)
chat_doc.add_message(role="user", content=sanitized_message)
chat_doc.add_message(role="assistant", content=response_text, ...)
await chat_doc.save()
await self.invalidate_conversation_cache(session_id)
```

The streaming path uses `asyncio.create_task(chat_service.save_chat(...))`. If `save_chat` is later modified (e.g., to add analytics or change the schema), the non-streaming path will silently diverge.

## DNS rebinding window in is_safe_url

The TOCTOU gap: `is_safe_url` resolves DNS and returns `True`, then the caller uses the original URL string to make a request, triggering a second DNS resolution. An attacker with control over a DNS server can serve a public IP during validation (passing the check) and a private IP during the actual request (achieving SSRF). The mitigation is to have `is_safe_url` return the resolved IP so the caller can connect directly to it, bypassing a second DNS lookup. This is an architectural gap rather than a bug in the function itself — the async conversion and 3-second timeout are genuine improvements over the synchronous baseline.
