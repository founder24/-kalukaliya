# SEO/GEO/AEO pipeline: prerender expansion, ISR fallback, sitemaps, and IndexNow

This change adds a multi-layer search-engine and AI-crawler optimization stack to the education platform. It raises prerender limits from 50 subjects / 6 chapters to 999/999 (effectively "prerender everything"), adds an ISR fallback in the Cloudflare edge worker for bot traffic that misses prerendered routes, introduces robots.txt and sitemap endpoints, injects BreadcrumbList + Course JSON-LD into prerendered subject pages, adds a crawlable prev/next navigation component, and wires up an IndexNow submission endpoint with a post-deploy script.

**Watch for:** The IndexNow endpoint uses INDEXNOW_API_KEY as both the IndexNow protocol key (sent to api.indexnow.org) and the internal shared secret for authenticating deploy-script calls — leaking it to the external API means anyone who intercepts that payload can call the internal endpoint (confirmed). The ISR handler proxies the original request headers (including cookies, JWT tokens) to the backend when serving bot traffic (confirmed). The sitemap proxy route is broken — the edge worker forwards `/sitemap.xml` to the backend at that same path, but the backend serves sitemaps at `/api/v1/seo/sitemap.xml` (confirmed).

## High-level view

The prerender limit raise from 50/6 to 999/999 transforms the build from a traffic-ranked subset to a full-catalogue prerender. The build budgets were raised proportionally (25 min outer, 20 min step) but the PRERENDER_BUDGET_MS — the prerender script's own wall-clock cap — was left at its original 12 minutes, creating a tension where the outer build allows 25 minutes but the prerender pass self-terminates at 12.

The ISR edge handler is a KV-backed cache-aside for bot traffic. On a cache miss it forwards the entire original request (cookies, auth headers) to the backend, which means a bot carrying a valid session could cause an authenticated page render to be cached and served to subsequent bots. The 1-hour KV TTL provides no invalidation mechanism.

The sitemap system has a routing gap: robots.txt declares `Sitemap: https://syrabit.ai/sitemap.xml`, the edge worker proxies `/sitemap*.xml` to the backend, but `proxyRequest` passes the original path through unchanged and the backend mounts sitemaps at `/api/v1/seo/`. The result is a 404 for every sitemap request from crawlers.

IndexNow uses a single secret (INDEXNOW_API_KEY) for dual duty: it authenticates the deploy script's calls to the backend AND is sent as the protocol `key` in the IndexNow API payload. This conflates an internal credential with an externally-visible protocol field.

## Sitemap routing gap

The edge worker has this route:

```typescript
if (url.pathname.startsWith('/sitemap') && url.pathname.endsWith('.xml')) {
  return proxyRequest(request, env.AZURE_BACKEND_URL, env);
}
```

`proxyRequest` constructs the target URL as `${backendUrl}${url.pathname}${url.search}` — it passes the path through unchanged. The backend mounts the seo router at `/api/v1/seo`, so sitemaps live at `/api/v1/seo/sitemap.xml`. A crawler hitting `https://syrabit.ai/sitemap.xml` (as declared in robots.txt) will get proxied to `${AZURE_BACKEND_URL}/sitemap.xml`, which is not a registered route — 404.

The fix is either: (a) add a path-rewrite before calling `proxyRequest`, (b) mount the seo router at `/` in the backend (undesirable), or (c) create a dedicated edge handler that fetches from the correct backend path.

## IndexNow secret conflation

The `indexnow.py` endpoint validates the incoming `X-IndexNow-Secret` header against `settings.INDEXNOW_API_KEY`, then sends that same value as the `"key"` field in the JSON payload to `https://api.indexnow.org/indexnow`:

```python
if x_indexnow_secret != settings.INDEXNOW_API_KEY:
    raise HTTPException(status_code=403, detail="Invalid IndexNow secret")
# ...
payload = {
    "host": "syrabit.ai",
    "key": settings.INDEXNOW_API_KEY,
    "urlList": batch,
}
```

The IndexNow API key is a public-ish protocol identifier (it must be served as a verification file at `/{key}.txt` per the spec). Using it as the authentication token for an internal endpoint means anyone who reads the verification file can replay requests to `/api/v1/indexnow/submit`. The fix is two config values: `INDEXNOW_API_KEY` for the protocol and a separate `INDEXNOW_INTERNAL_SECRET` for deploy-script auth.

## ISR header forwarding and cache poisoning

In `isr.ts`, on a cache miss the handler proxies the full request to the backend:

```typescript
const response = await fetch(backendUrl, {
  method: request.method,
  headers: request.headers,
});
```

If the backend renders different content based on auth state (e.g., premium content gating), that authenticated render gets cached in KV and served to all subsequent bots for 1 hour. The fix is to strip `Cookie`, `Authorization`, and session-related headers before proxying, and optionally validate that the response doesn't contain user-specific content markers before caching.

The handler also has no cache size bound — a crawler systematically hitting unique paths could fill the KV namespace with unbounded entries (each TTL'd at 1 hour, but concurrent storage still grows).

## Prerender budget mismatch

The build pipeline has three nested time budgets:

| Layer | Before | After |
|-------|--------|-------|
| BUILD_BUDGET_MS (build.mjs) | 12 min | 25 min |
| STEP_BUDGET_MS (prerender-all.mjs) | ~7.9 min | 20 min |
| PRERENDER_BUDGET_MS (prerender-routes.mjs) | 12 min | **12 min (unchanged)** |

With 999 subjects and 999 chapters/subject, the script will hit its 12-minute soft-stop and silently skip the remainder. The SPA shell fallback makes this non-catastrophic, but it contradicts the goal of prerendering the full catalogue. Either raise PRERENDER_BUDGET_MS or document that the 12-minute cap is intentional.

## Empty sitemap stubs

`seo.py` declares subject and chapter sub-sitemaps in the index but returns only XML comments:

```xml
<urlset xmlns="http://www.sitemaps.org/schemas/sitemap/0.9">
  <!-- populated from DB -->
</urlset>
```

Googlebot treats declared-but-empty sitemaps as errors in Search Console. The prerender manifest (written to `dist/prerender-manifest.json`) already enumerates all rendered routes — it could be used to generate real sitemap entries without a DB query.

## Duplicate prev/next navigation

`RelatedTopicsNav` renders prev/next links using plain `<a>` tags for crawlability, then `ContinueLearning` immediately follows with its own prev/next navigation. The SEO intent is sound (plain `<a>` tags are more reliably crawled than client-routed links), but users see two navigation blocks in sequence. Consider hiding `RelatedTopicsNav` visually while keeping it in the DOM for bots (e.g., `sr-only` class), or consolidating the links into `ContinueLearning` with `<a>` tags.
