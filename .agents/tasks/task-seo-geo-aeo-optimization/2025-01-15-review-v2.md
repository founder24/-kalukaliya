# SEO/GEO/AEO optimization: prerender expansion, ISR fallback, sitemaps, structured data, and IndexNow (v2)

The v1 review raised eight issues. Six have been resolved: IndexNow endpoint now authenticates via `X-IndexNow-Secret` header, the submit script sends that header, the workflow `if:` condition was removed (the script self-gates on the env var), `numberOfCredits` was replaced with `courseWorkload`, node_modules changes are gone, and manifest dead code was removed (the script now reads the manifest, uses its counts to decide whether to proceed, and only walks the filesystem for URL discovery).

**Watch for:** The ISR backend render endpoint (`/api/content/render/<path>`) still does not exist — ISR cache misses fall through to the SPA shell for all bot traffic (likely). Sitemap subjects/chapters endpoints remain stubbed with placeholder data (confirmed). KV namespace placeholder IDs in `wrangler.toml` will fail production deploy (confirmed).

**Verdict**: APPROVED

## High-level view

The IndexNow authentication gate checks `X-IndexNow-Secret` against `INDEXNOW_API_KEY` before forwarding URLs. The test suite covers 403 responses for missing and incorrect secrets. The workflow step omits the unreliable `if:` secret comparison; the script early-exits when the env var is empty.

The manifest dead-code concern is resolved — the script reads `prerender-manifest.json`, extracts chapter/subject counts, and aborts submission if both are zero. URL discovery still uses the filesystem walk, which is the correct source of truth for what was actually deployed.

Three concerns from v1 remain unaddressed but are acknowledged as intentional future work: the ISR render endpoint doesn't exist yet (ISR is inert), sitemaps are stubs, and KV IDs are placeholders. These are deploy-blockers for the ISR/sitemap features specifically, but don't block the prerender expansion or IndexNow integration from shipping.

## ISR layer remains inert until render endpoint ships

The `handleISR` function in `apps/edge/src/routes/isr.ts` proxies cache misses to `${env.AZURE_BACKEND_URL}/api/content/render${url.pathname}`. No route matching that pattern exists in `apps/backend/app/main.py` or any router file. The handler returns `null` on non-200 responses, so bot requests fall through to the SPA shell. ISR produces no value until the backend endpoint exists.

## Sibling ordering in prerender vs. client-side

The prerender pipeline computes `siblings_nav` from `candidateChapters`:

```javascript
const chapterIdx = candidateChapters.findIndex(c => c.slug === chapterSlug);
const prevCh = chapterIdx > 0 ? candidateChapters[chapterIdx - 1] : null;
const nextCh = chapterIdx < candidateChapters.length - 1 ? candidateChapters[chapterIdx + 1] : null;
```

`candidateChapters` is the traffic-ranked, `CHAPTERS_PER_SUBJECT`-limited slice of the subject's chapters. When limits are 999 this includes all chapters, but their order is by traffic rank, not curriculum order. The client-side fallback in `ChapterPage.jsx` uses `findSiblingChapters` on the full bundle (which likely preserves the natural `order` field). This creates an asymmetry: prerendered HTML may show different prev/next links than the same page rendered client-side after hydration.

With 999/999 limits, all chapters are included but sorted by descending traffic. Chapter B (highest traffic) will appear at index 0 with no "previous" link, even if it's the third chapter in the curriculum. The navigational semantics of "Previous/Next" typically imply sequence, not popularity.

## Sitemap proxy lacks error handling

The edge worker's sitemap proxy block:

```typescript
const backendResponse = await fetch(backendUrl);
return new Response(backendResponse.body, {
  status: backendResponse.status,
  headers: backendResponse.headers,
});
```

If the backend is down, `fetch` throws (network error) and the worker returns a generic 500. Wrapping in try/catch to return a 503 with `Retry-After` would be more crawler-friendly. Low severity — search engines retry on transient errors regardless.

Not tested:

- The sibling ordering behaviour under traffic-ranked conditions
- Sitemap proxy error handling at the edge
