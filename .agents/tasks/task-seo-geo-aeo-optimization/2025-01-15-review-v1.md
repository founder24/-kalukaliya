# SEO/GEO/AEO optimization: prerender expansion, ISR fallback, sitemaps, structured data, and IndexNow

The change turns the prerender pipeline from a "top 350 routes" strategy into a "cover everything" strategy (999/999 subject/chapter limits) with ISR as a safety net for anything the build doesn't reach. It adds a full SEO stack: custom robots.txt allowing AI crawlers, backend-generated sitemaps, BreadcrumbList/Course JSON-LD injection during prerender, a `RelatedTopicsNav` component for internal linking, and an IndexNow integration that pings search engines after deploy. Build budgets are raised from 12 min to 25-30 min to accommodate the expanded route set.

**Watch for:** The IndexNow submit endpoint is unauthenticated — anyone can POST arbitrary URLs to it and trigger submissions to search engines under your domain's key (confirmed). The sitemap endpoints return placeholder/stub data with TODO comments, so they will not improve indexing until wired to the database (confirmed). The ISR fallback proxies to a backend endpoint (`/api/content/render/<path>`) that does not appear to exist in this diff or the base branch, meaning ISR cache misses will 404 silently (likely).

## High-level view

The prerender pipeline limits were raised from 50/6 to 999/999 with matching budget increases. This is a "prerender the world" approach gated by a 30-minute wall-clock soft-cap — if the backend is slow, the build gracefully stops and the ISR layer picks up remaining routes for bot traffic. The fallback chain is: prerendered HTML > ISR KV cache > backend SSR proxy > SPA shell.

The ISR layer in the Cloudflare edge worker detects bots via User-Agent regex, checks KV for cached HTML, and on miss proxies to `AZURE_BACKEND_URL/api/content/render/<path>`. This backend render endpoint is not created in this diff; the ISR layer will return null (fall through to SPA) on every cache miss until that endpoint exists. The KV namespace uses placeholder IDs that must be replaced before production deploy.

The sitemap endpoints in the backend are structurally correct but return only placeholder URLs — the subjects and chapters sitemaps need to query the database to be useful. The prerender pipeline already has access to the full library bundle that could populate these.

The IndexNow integration adds an unauthenticated POST endpoint that forwards URL batches to the IndexNow API, plus a deployment script that walks the dist directory to discover prerendered pages. The workflow step runs only when the `INDEXNOW_API_KEY` secret is set — though the GitHub Actions secret comparison may not behave as expected.

## ISR fallback and the missing render endpoint

The ISR handler proxies cache misses to:

```
${env.AZURE_BACKEND_URL}/api/content/render${url.pathname}
```

No route matching `/api/content/render/...` appears in the backend routers registered in `main.py`, and none was added in this diff. The handler correctly returns `null` on non-200 responses (falling through to the SPA), so this won't cause user-facing errors — but it means ISR is inert until the render endpoint is built. Every bot request to a non-prerendered route will see the SPA shell.

There is no cache invalidation mechanism — after content updates, bots will see stale HTML for up to one hour (the KV TTL). For an education platform with infrequent content changes this is likely acceptable, but a manual KV flush or webhook-triggered invalidation would be needed for time-sensitive updates.

## IndexNow authentication gap

The `POST /api/v1/indexnow/submit` endpoint checks only that `INDEXNOW_API_KEY` is configured, then forwards whatever URLs the caller provides to the IndexNow API:

```python
payload = {
    "host": SITE_HOST,
    "key": settings.INDEXNOW_API_KEY,
    "urlList": body.urls[:10000],
}
```

There is no JWT check, no API key requirement, no IP allowlist. The edge worker does not gate this path behind JWT either — the JWT middleware injects `X-User-ID: anonymous` and passes through when no token is provided. An external attacker could submit thousands of arbitrary URLs to search engines using your key, potentially triggering IndexNow abuse detection and getting the key revoked.

## Sitemap endpoints: structure without data

The sitemap-subjects and sitemap-chapters endpoints have the deduplication logic and XML generation in place, but the actual URL enumeration is stubbed:

```python
# TODO: Replace with database query to get all chapter URLs
chapter_urls = [
    f"{BASE_URL}/library",
]
```

The prerender pipeline already has access to the full library bundle (boards/classes/subjects/chapters) — the same data source could populate sitemaps without waiting for a direct database query.

## Build budget vs. Cloudflare Pages free-plan wall

The comment in `build.mjs` says "Pages free-plan wall is 20 min; paid plan allows 30 min." If the project is on the free plan, the 25-minute `BUILD_BUDGET_MS` will be killed by Cloudflare at 20 minutes before the internal budget fires. The soft-stop in `prerender-routes.mjs` only helps if the internal timer fires first. On a free plan, expect Cloudflare to kill the build at ~60% completion for large route sets with a slow backend.

## RelatedTopicsNav sibling ordering anomaly

The sibling computation in `prerender-routes.mjs` uses `candidateChapters` (the traffic-ranked, limited slice) rather than the full chapters list. If chapter A is ranked first by traffic but is curriculum chapter #5, its "previous" link will be null even though curriculum chapters 1-4 exist. The internal linking graph reflects traffic ranking rather than pedagogical order — this may confuse users who expect "Previous" to mean the preceding curriculum topic.

## Course JSON-LD schema misuse

Course JSON-LD injects `numberOfCredits` as the chapter count. In schema.org, `numberOfCredits` represents academic credit hours (e.g., "3 credit hours"), not content quantity. Google's rich results documentation doesn't penalize this, but it could produce confusing structured data in knowledge panels. Consider using `hasPart` with individual chapter items or removing `numberOfCredits` in favor of a descriptive `courseWorkload`.

## IndexNow deployment script dead code

The script reads and parses `prerender-manifest.json` but never references the parsed data — URL discovery uses `walkDir(distDir)` exclusively. The manifest read should either be removed or used (it contains route counts and metadata that could gate whether submission proceeds).
