# Audit fixes re-implementation on chat-resilience base (v2)

Thirteen audit findings from PR #206 re-applied on top of PR #205's chat-resilience patterns. All five issues from the v1 review have been addressed: conversation history cache is now invalidated after both the `process_chat` inline save and the `_save_chat_async` fire-and-forget path; `test_security.py`'s `TestSSRFProtection` class is now `@pytest.mark.asyncio` with `async def` test methods; the Trivy scan post-push trade-off is documented with a comment explaining the alternative; `ExpiredSignatureError` has its own except clause ahead of `InvalidTokenError`; and the Trivy action is pinned to `@0.28.0`.

Watch for: `process_chat` creates a new Chat document per request instead of appending to the session's existing document, so `_load_conversation_history`'s `find_one` retrieves only the first (oldest) document for a session_id—multi-turn context accumulation is broken beyond the first exchange (confirmed). The `AuthContext.Provider` value computes `token` and `authHeader` from module-level variables via `getInMemoryToken()` at render time, but nothing triggers a re-render when those variables change, so consumers see stale auth state until an unrelated state update forces a re-render (confirmed).

**Verdict**: NEEDS_CHANGES

## High-level view

The cache invalidation fix resolves the most critical v1 issue—both the streaming and non-streaming save paths now delete the Redis key. But the persistence model itself still has a structural problem: each chat request creates a brand-new Chat document with the same `session_id`, producing multiple documents per session. The `_load_conversation_history` method calls `Chat.find_one({"session_id": session_id})` without a sort, which returns the first (oldest) document—one that only contains the initial exchange. Subsequent turns never see accumulated history.

The token management extraction into `useTokenManager.js` moves auth state into module-level variables outside React's state system. When `storeToken(newToken)` is called (e.g., after silent refresh), no React state updates, so the context value `{ token: getInMemoryToken(), authHeader: ... }` remains whatever it was at last render. The current code works only because every call to `storeToken` is followed by `setUser`, which forces a re-render—but the coupling is implicit and fragile.

## Chat document accumulation vs. find_one retrieval

The persistence pattern in `process_chat` (lines 334–363) constructs a new `Chat` document on every request:

```python
chat_doc = Chat(
    user_id=user_id if user else None,
    session_id=request.session_id,
)
chat_doc.add_message(role="user", content=sanitized_message)
chat_doc.add_message(role="assistant", content=response_text, ...)
await chat_doc.save()
```

This inserts a fresh document each time. A three-turn conversation produces three separate documents sharing the same `session_id`. Meanwhile, `_load_conversation_history` loads context via:

```python
chat = await Chat.find_one({"session_id": session_id})
recent = chat.messages[-(max_turns * 2):]
```

Without a sort parameter, `find_one` returns the first matching document by insertion order—the one containing only turn 1. Turns 2 and 3 are in separate documents that are never read. The cache invalidation fix from v1 is correctly in place, but it invalidates a cache key whose underlying data is structurally incomplete.

The same pattern exists in `_save_chat_async` (used by the stream endpoint), which also creates a new document rather than appending.

The fix: either change `process_chat` and `_save_chat_async` to find the existing session document and append (`Chat.find_one({"session_id": ...})` then `add_message` then `save`), or change `_load_conversation_history` to aggregate across all documents for the session (`Chat.find({"session_id": session_id}).sort("+created_at").to_list()`).

## Token state outside React's reactivity system

`useTokenManager.js` stores tokens in module-level variables:

```javascript
let _inMemoryToken = null;
let _inMemoryRefreshToken = null;
```

The `AuthContext.Provider` value is computed each render:

```jsx
<AuthContext.Provider value={{
  token: getInMemoryToken(),
  authHeader: getInMemoryToken() ? { Authorization: `Bearer ${getInMemoryToken()}` } : {},
  ...
}}>
```

Every current code path that updates the token (`login`, `signup`, `silentRefresh`) also triggers `setUser()`, which forces a re-render and incidentally picks up the new module-level value. But if a future change stores a refreshed token without also updating user state—e.g., an axios interceptor that refreshes silently—consumers of `useAuth().token` will see the old value until something else triggers a render. A `useState` wrapper for the token would make the reactivity explicit.
