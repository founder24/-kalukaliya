# Audit fixes re-implementation on top of chat-resilience

Thirteen audit findings from PR #206 are re-applied on the current main (which already includes PR #205's resilience patterns). The approach migrates python-jose to PyJWT, hardens prompt injection filtering with NFKC normalization, makes SSRF validation async, refactors the 700-line chat endpoint into a ChatService class, adds Redis caching for both search results and conversation history, introduces Trivy container scanning in CI, locks down CI lockfiles, documents secrets, and adds edge-worker tests. The chat.py refactoring is the riskiest piece because it must preserve the `asyncio.wait_for` timeout wrapping, granular error classification, and fire-and-forget persistence patterns already present.

Watch for: Conversation history cache is never invalidated after writes, producing stale multi-turn context for up to 30 minutes (confirmed). The existing `test_security.py` tests for `is_safe_url` now silently fail because the function became async but tests weren't updated (confirmed). Trivy scan runs after the image is already pushed to ACR, so a CRITICAL finding doesn't prevent the image from reaching the registry (confirmed).

## High-level view

The PyJWT migration replaces `jose.jwt` with `import jwt` and `JWTError` with `InvalidTokenError`. One catch block (`except (InvalidTokenError, ExpiredSignatureError)`) is harmlessly redundant because `ExpiredSignatureError` subclasses `InvalidTokenError`, but the `"expired" in str(e).lower()` heuristic is fragile compared to catching `ExpiredSignatureError` in its own except clause.

The ChatService refactoring preserves all PR #205 patterns: 30-second `asyncio.wait_for`, granular `RuntimeError` classification, httpx status errors, Sarvam-to-Vertex fallback, and fire-and-forget persistence. The risk is in the conversation history cache that never gets invalidated on write.

The prompt injection hardening adds NFKC normalization and zero-width character stripping before pattern matching, preventing Unicode homoglyph evasion. The pattern list now covers chat-ML markers (`<|system|>`, `[INST]`) and social-engineering phrases. Sequential pattern stripping has a theoretical composition risk where removal of one pattern could reveal another, though unlikely with the current pattern set.

The CI lockfile and Trivy changes are mechanical, except that Trivy scans post-push—a vulnerable image reaches the registry before the scan gates the deploy step. The Trivy action is pinned to `@master` rather than a SHA, which is a supply-chain risk.

The AuthContext refactoring extracts token storage, silent refresh, and anonymous data sync into three hooks. The `useTokenManager` module uses module-level variables for in-memory state, meaning token state is shared across any component tree importing the module—fine for a single-root SPA but would break with micro-frontends.

1. **Stale conversation history cache** — `_load_conversation_history` caches in Redis for 30 minutes but `_save_chat_async` never invalidates the cache key. Delete `conv_history:{session_id}` after persisting new messages, or set the cache on write rather than on read.

3. **Trivy scans after ACR push** — The image is built and pushed via `az acr build`, then pulled back and scanned. A CRITICAL vulnerability won't prevent the image from reaching the registry. Move the scan to a local `docker build` + Trivy step before pushing, or add a gate between scan and deploy.
4. **Redundant ExpiredSignatureError catch** — `except (InvalidTokenError, ExpiredSignatureError)` in `auth.py:175` is redundant since `ExpiredSignatureError` subclasses `InvalidTokenError`. The string-matching heuristic (`"expired" in str(e).lower()`) is fragile. Catch `ExpiredSignatureError` first in a separate except clause for explicit expired-token handling.
5. **Trivy action pinned to @master** — `aquasecurity/trivy-action@master` is unpinned. A compromised or broken upstream commit would run in CI with repository secrets available. Pin to a specific SHA or release tag.

## Conversation history cache without invalidation

`_load_conversation_history` (chat.py lines 60-90) checks Redis for `conv_history:{session_id}`, and on miss loads from MongoDB then writes to Redis with `ex=1800`. But `_save_chat_async` writes new messages to MongoDB without deleting or updating this cache key. In a multi-turn conversation, the second message within 30 minutes will see stale history that doesn't include the first message's response. The LLM loses conversational context precisely when it matters most—mid-session.

The fix: after `chat_doc.save()` in `_save_chat_async`, issue `await redis.delete(f"conv_history:{session_id}")`. Alternatively, update the cache eagerly with the new messages immediately after save.

## is_safe_url async migration without test updates

The function signature changed from `def is_safe_url(...)` to `async def is_safe_url(...)`, but `test_security.py` still calls it bare:

```python
assert is_safe_url("https://example.com") is True
```

This evaluates to `assert <coroutine object> is True` which raises `AssertionError`. Every test in the `is_safe_url` section will fail. If CI isn't running these tests (the task only mentions `ruff check` and edge tests as verification), this is a latent break that will surface when someone runs the backend pytest suite.

## Trivy scan ordering in deploy-all.yml

The workflow runs:
1. `az acr build` — builds and pushes to ACR
2. `docker pull` + Trivy scan
3. Deploy to Container Apps

If Trivy finds a CRITICAL vulnerability at step 2, step 3 doesn't execute—but the image is already in the registry from step 1 and available for manual pulls or rollback targets. A more robust pattern: build locally with `docker build`, scan with Trivy, then push only on clean scan.

## Token handling in auth.py PyJWT migration

The `except (InvalidTokenError, ExpiredSignatureError)` at line 175 uses `"expired" in str(e).lower()` to detect expired tokens. PyJWT raises `ExpiredSignatureError` with "Signature has expired" as the message—this works today but is an implementation detail that could change. A cleaner pattern:

```python
except ExpiredSignatureError:
    raise HTTPException(status_code=401, detail="token_expired")
except InvalidTokenError:
    raise HTTPException(status_code=401, detail="Invalid token")
```

## Sequential stripping composition risk in prompt injection filters

The patterns are applied sequentially with `re.sub`. An attacker could interleave recognized markers such that removal of one creates another (e.g., `"Ignore SYSTEMprevious: instructions"` becomes `"Ignore previous instructions"` after removing `"System:"`). The likelihood is low with the current pattern set but increases as patterns are added. A multi-pass or single-regex approach would eliminate this class of bypass.

## Search results cache key omits the `text` parameter

The cache key in `azure_search.py` is `sha256(f"{query}:{user_tier}:{limit}")`, but the `text` parameter (passed to `VectorizableTextQuery`) is not included. If `text` ever diverges from `query` for the same input—e.g., due to embedder preprocessing changes—the cache would serve stale vector results. Currently `text` and `query` are both derived from `sanitized_message` so the coupling holds, but the cache key should include `text` or the code should document the invariant.
