# Audit fixes re-implementation on chat-resilience base (v3)

Thirteen audit findings from PR #206 re-applied on top of PR #205's chat-resilience patterns. Both issues from the v2 review are resolved: conversation history now aggregates all session documents via `Chat.find().sort("+created_at").to_list()` with message flattening across documents; the token reactivity pattern is documented as intentional (every `storeToken` call is paired with a `setUser` that triggers re-render). All five v1 issues were addressed in v2 and remain fixed. No new blocking concerns identified in this pass.

Watch for: nothing blocking. The Trivy post-push trade-off (image reaches ACR before scan) remains a documented architectural limitation—not a code defect in this branch.

**Verdict**: APPROVED

## High-level view

The chat persistence creates a new document per exchange but `_load_conversation_history` now correctly aggregates across all documents sharing a `session_id`, sorting chronologically and flattening messages before taking the last N turns. Cache invalidation fires in both `process_chat` (inline save) and `_save_chat_async` (fire-and-forget stream path).

The frontend token management stores state in module-level variables outside React's reactivity system, but every code path that mutates the token (`login`, `signup`, `silentRefresh`) also calls `setUser`, which forces a context re-render. The `useTokenManager.js` file now carries an explicit comment documenting this coupling and prescribing the migration path if the invariant ever breaks.

The remaining eleven audit fixes (PyJWT migration, CI lockfile enforcement, prompt injection hardening, async SSRF protection, search caching, Trivy scanning, edge tests, KeyVault documentation, AuthContext extraction, wrangler.toml docs) are unchanged since v1/v2 confirmed them.
