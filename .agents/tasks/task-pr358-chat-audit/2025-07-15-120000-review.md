# PR 358 chat pipeline audit tests

Adds 843 lines of integration tests (`test_pr358_chat_audit.py`) that exercise the `/api/v1/chat/stream` and `/api/v1/chat/` endpoints under mocked external services. Five test classes cover English-mode SSE format and Vertex routing, Assamese-mode Sarvam routing with Vertex fallback, RAG-unavailable graceful degradation, mocked-latency performance, and the PR 358 fix that ensures an explicit `lang` field overrides text-based auto-detection. All external services (Vertex AI, Sarvam, Redis, MongoDB, search) are mocked so the tests validate routing logic and SSE contract without network dependencies.

**Watch for:** The Sarvam-to-Vertex fallback test patches at the wrong abstraction layer and will silently pass without exercising the real fallback path (confirmed). Latency assertions measure wall-clock time under mocked I/O, making them environment-sensitive and prone to flakiness in CI (likely). The `_common_patches` helper includes a `stream_response` entry that is overridden in nearly every test, creating a dead patch that obscures the actual mock being applied (confirmed).

## High-level view

The tests are structured around five behavioral areas of the chat pipeline, all using a shared `_common_patches()` helper that returns a dictionary of `unittest.mock.patch` context managers. Each test manually enters 10-12 patches via Python 3.10 parenthesized `with` blocks and sends a request through `httpx.AsyncClient` with `ASGITransport`.

The fallback test (`test_assamese_fallback_to_vertex_on_sarvam_failure`) patches `stream_response` at the router module level, but the production `ChatService.stream_llm` catches the exception internally and calls `vertex_client.stream_generate_with_retry` as the fallback. The test mocks a separate `vertex_client` object at `app.services.ai.vertex_client.vertex_client`, but it doesn't assert the vertex mock was actually called, leaving a confidence gap about what's being exercised.

The latency tests assert `< 200ms` and `< 500ms` wall-clock time with all I/O mocked. In a loaded CI runner with GC pauses or slow startup, these will flake. The tests don't use a margin or retry strategy.

The `_common_patches` helper pre-defines a `stream_response` patch that nearly every test immediately overrides with its own local `patch(...)`. The dead entry is never entered in those tests, but its presence suggests shared-patch drift that could confuse future authors.

<details>
<summary>Issues (5)</summary>

1. **Fallback test doesn't verify vertex mock was called** — `test_assamese_fallback_to_vertex_on_sarvam_failure` asserts on SSE events containing `fallback: true`, but if `ChatService.stream_llm` silently swallows the exception without reaching the vertex path (e.g. due to a patch target mismatch), the test would fail at the assertion level but wouldn't tell you *why*. Add an explicit `mock_vertex.stream_generate_with_retry.assert_called_once()` or equivalent.

2. **Latency tests will flake in CI** — Wall-clock assertions (`< 200ms`, `< 500ms`) under mocked I/O pass locally but are sensitive to CI runner load, Python startup, and GC pauses. Increase thresholds (e.g. 1s) or mark these tests with `@pytest.mark.flaky` / skip in CI.

3. **Dead `stream_response` entry in `_common_patches`** — The helper defines a `stream_response` patch that is overridden in 14 of 17 tests. Remove it from the shared dict and have callers always provide their own, or document that it's only used by `test_invalid_lang_rejected`.

4. **Unreachable `yield` in `_failing_stream`** — The async generator that raises `RuntimeError` before yielding uses a commented `# noqa: unreachable` yield to satisfy the async-generator typing. This is a valid Python idiom but should be extracted to a reusable `_raise_before_yield(exc)` helper to avoid confusion in 2+ tests.

5. **No assertion on response content correctness** — Several tests verify SSE structure (done events, content events) but never check that the mocked chunk text actually appears in the `content` field of the parsed events. A broken serialization path (e.g. double-encoding) would pass all assertions.

## Fallback wiring gap in the Assamese test

`test_assamese_fallback_to_vertex_on_sarvam_failure` constructs a `mock_vertex` object with a `stream_generate_with_retry` method and patches it at `app.services.ai.vertex_client.vertex_client`. The production code in `ChatService.stream_llm` does:

```python
from app.services.ai.vertex_client import vertex_client
async for chunk in vertex_client.stream_generate_with_retry(system_prompt, sanitized_message):
    ...
```

The lazy import means the patch target must match exactly where the import resolves at runtime. The test never asserts that `mock_vertex.stream_generate_with_retry` was actually invoked. If the production fallback path changes (e.g., the import path moves, or exception handling narrows), the test could pass while the fallback is broken.

The test asserts `len(content_events) >= 1`, which would fail if the vertex mock isn't reached (no content events would be emitted by the fallback path). But this is an indirect signal — a direct `assert_called` on the vertex mock would make the test's intent explicit and catch regressions faster.

## Latency assertions and CI flakiness

```python
assert first_chunk_time < 0.200, (
    f"First chunk took {first_chunk_time*1000:.0f}ms, expected < 200ms"
)
```

With all services mocked to return instantly, the measured time is pure framework overhead: ASGI transport startup, middleware chain, async scheduling, SSE serialization. On a shared CI runner under memory pressure, or with Python debug builds, this can exceed 200ms. These tests need either:
- A generous multiplier (2-3x expected local time), or
- A `@pytest.mark.slow` / conditional skip when `CI=true`, or
- Use of monotonic elapsed-time percentiles rather than single-shot assertions.

## `_common_patches` ergonomics

The helper builds 14 patch objects upfront, but tests override `stream_response` and `search_service` in nearly every case. The dict entry's `side_effect=_stream_gen` closure captures `stream_chunks=["Hello", " World"]`, which is never used by any test that provides its own stream mock. Remove `stream_response` and `search_service` from the shared dict entirely, since every test customizes them.

## Content correctness not verified

Tests like `test_english_stream_returns_correct_sse_format` mock chunks as `["Photosynthesis", " is the process", " of converting light."]` and verify that `content_events` is non-empty and each event has a `"content"` key. But they never assert that the content *values* match the mocked chunks. If the SSE serialization introduced extra escaping, truncation, or prefix stripping, these tests would still pass. Adding:

```python
assert content_events[0]["content"] == "Photosynthesis"
```

...would close this gap cheaply.

## Test isolation via repeated app import

Each test method does `from app.main import app` at the top of the function body, re-importing the FastAPI app singleton. This file bypasses conftest entirely and constructs its own `AsyncClient` per test. If any future test in this file adds a `Depends` override or modifies app state, it will leak into subsequent tests in the same process — a latent coupling to watch for.
