# SEO/GEO/AEO structured data, feeds, and sitemap expansion

This change layers Knowledge Graph entity linking (Wikidata/DBpedia `sameAs` on the Organization and subject-level CollectionPage), pre-rendered FAQ/DefinedTerm microdata for bot HTML, RSS/JSON Feed endpoints, a topic-level sitemap, ImageObject schema for multi-modal grounding, and citation array support onto the existing JSON-LD and bot-rendering infrastructure. It also removes a non-standard `Content-Signal` comment block from the edge worker's robots.txt. The approach is additive — existing schema builders gain new nodes and properties without restructuring the `@graph` emission pattern.

**Watch for:** The edge worker `robots.ts` still contradicts the frontend `robots.txt` on crawler policies (GPTBot allowed vs. disallowed) — this drift pre-dates this PR but isn't addressed here and can confuse AI crawlers that hit the API subdomain first (confirmed). The FAQ microdata in bot HTML uses `itemprop="mainEntity"` on question items scoped under a FAQPage `itemscope`, but each child `<div itemscope>` re-establishes scope without an `itemprop` linking back to the parent — microdata validators may not associate the questions with the FAQPage (likely). The `_xml_escape` function in the feed endpoint doesn't escape single quotes (`'` → `&apos;`), which is technically valid XML but could matter if feed content lands in attribute contexts (possible).

## High-level view

The JSON-LD changes in `jsonld.js` add `sameAs` arrays mixing social profiles with Wikidata/DBpedia geographic URIs on the Organization, and link subject-level schemas to Wikidata when the name exactly matches a constant key. The risk is silent failure: any drift in entity key naming (e.g. "English Literature" vs. "English") drops the linkage with no error.

The bot-rendered HTML in `vite.config.js` now emits FAQ microdata and DefinedTerm `<dl>` blocks — but these only execute via the Vite dev-mode plugin. Production bot rendering goes through the edge proxy and backend pipeline, which doesn't emit these blocks. The "triple-stacking" benefit is dev-only unless the production renderer is updated.

The backend gains `/feed.xml` (RSS 2.0), `/feed.json` (JSON Feed 1.1), and `/sitemap-topics.xml`. The feeds use template strings instead of real content for descriptions, giving AI crawlers no unique signal per item. The topics sitemap emits fragment-based URLs (`#topic-slug`) which Google ignores in sitemaps per their documentation.

The `ChapterTopicGraph` component diversifies sibling anchor text by appending "- definition" or "notes" on a modulo-3 index pattern. If topic list ordering is non-deterministic, the same link appears with different anchor text across crawls — a cloaking signal.

## Entity-first Knowledge Graph grounding via `sameAs`

The `WIKIDATA_ENTITIES` and `DBPEDIA_ENTITIES` constants map 13 educational concepts to canonical URIs. The lookup is a strict key match:

```js
if (subjectName && WIKIDATA_ENTITIES[subjectName]) {
  aboutThings.push({
    '@type': 'Thing', name: subjectName,
    sameAs: [WIKIDATA_ENTITIES[subjectName], DBPEDIA_ENTITIES[subjectName]],
  });
}
```

"physics", "PHYSICS", or "English Literature" won't match. Whether this is a real gap depends on how consistently the upstream database uses these exact capitalized strings. Any subject stored with different casing or a name not in the map (e.g., "Political Science") silently gets no Knowledge Graph linkage.

The Organization's `sameAs` array now mixes social profiles (`linkedin.com/company/…`), the site's own origin, and geographic Wikidata entities (Assam, India, Guwahati). Schema.org `sameAs` on an Organization means "same entity, different URL" — the Wikidata URIs for "Assam" and "India" are not the same entity as Syrabit.ai. Google recommends `sameAs` for social profiles and Knowledge Panel linking, not geographic qualifiers. The existing `areaServed` property already handles the geography correctly; these Wikidata URIs in `sameAs` may be ignored or misinterpreted by validators.

## Fragment-based sitemap for topics

The `/sitemap-topics.xml` endpoint generates URLs like:

```
https://syrabit.ai/render/{board}/{class}/{subject}/{chapter}/notes#topic-{slug}
```

Google's sitemaps documentation explicitly states: "URLs that contain fragment identifiers are not supported." Submitting fragment URLs means Google will either strip the fragment (creating duplicates of the parent page) or ignore entries entirely. If the goal is per-topic indexation, these need distinct URL paths without fragments.

The URL path also uses `/render/` which appears to be an internal bot-rendering route, not the user-facing canonical URL pattern (`/{board}/{class}/{subject}/{chapter}`). This conflicts with canonicalization elsewhere in the codebase.

## RSS/JSON feed content quality

Both the RSS `<description>` and JSON Feed `content_text` are generated from a template:

```python
description = f"Study notes for {chapter} in {subject} for {board} {class_level} students."
```

The actual `meta_description` or content body from the document isn't used. AI crawlers consuming feeds for content understanding get no useful signal beyond the title and URL. The JSON Feed spec recommends `content_html` or `content_text` contain the actual body — the current implementation puts the template in `content_text` without a `summary` field.

The feeds also lack pagination. With a hard limit of 50, content older than the 50th-most-recent update is permanently invisible to feed consumers.

## Bot-rendered microdata: dev-only execution path

The FAQ and DefinedTerm HTML sections in `vite.config.js` run inside `botRenderPlugin`'s `configureServer`, which only executes in Vite dev mode:

```js
// NOTE: configureServer only runs in Vite dev mode.
// In production, bot rendering is handled by:
//   1. Edge proxy (workers/edge-proxy)
//   2. Backend BotRenderMiddleware
//   3. Backend root_redirect
```

The JSON-LD schema (DefinedTerm nodes, FAQPage nodes from `chapterSchema`) does reach production via React rendering. But the microdata "triple-stacking" strategy — having both JSON-LD and microdata attributes on visible HTML — only works if the production bot renderer also emits these blocks. Currently it doesn't, making this a dev-only enhancement.

## Anchor text diversification and ordering stability

The sibling pill component rotates anchor text on a modulo-3 pattern:

```js
const pattern = index % 3;
if (pattern === 1) return `${title} - definition`;
if (pattern === 2) return `${title} notes`;
return title;
```

This produces position-dependent text that changes if topics are reordered. If the list order comes from a non-deterministic database query (no explicit `ORDER BY`), the anchor text for a given topic flickers between "X", "X - definition", and "X notes" across crawls. Search engines can interpret unstable anchor text on the same `href` as cloaking.

## Static sitemap uniform lastmod

The static sitemap gained `<lastmod>2025-01-01</lastmod>` on every URL. Identical dates across all static pages signal nothing to crawlers — they use lastmod deltas to prioritize crawl budget, and uniform dates are equivalent to no dates. If these pages change at different rates, per-page real dates from build metadata or CMS would be more useful.
