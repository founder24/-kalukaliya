# P0 bug fixes and deploy pipeline hardening

Eleven application-level fixes (security, performance, error handling, observability) applied to a FastAPI + Cloudflare Workers monorepo, accompanied by workflow changes that wire a canary deploy step, migrate runtime secrets to Azure KeyVault, and remove stale Supabase references. The fixes span auth token revocation, bot protection, input sanitization ordering, embedding token caching, email async migration, and PostHog analytics integration. The workflow changes add a deployment gate and eliminate secrets stored as plain GitHub environment variables.

**Watch for:** KeyVault secrets written to `GITHUB_OUTPUT` are visible to all subsequent steps and accessible via API with `actions:read`, creating a secret exposure surface despite `::add-mask::` (confirmed). The Resend email client singleton is never closed on shutdown, which may silently drop in-flight emails (confirmed). Turnstile enforcement on chat POST inadvertently covers `/api/v1/chat/feedback`, which is an authenticated-only endpoint that shouldn't require bot verification (confirmed).

## High-level view

The auth hardening makes the refresh endpoint fail-closed when Redis is unreachable for revocation checks, and forces logout callers to always supply a refresh token. The gap is that old refresh tokens whose revocation *storage* fails remain live until natural expiry (7 days).

Bot protection now requires Turnstile tokens for chat POST requests at the edge. The `startsWith('/api/v1/chat')` check also catches `/api/v1/chat/feedback` POST, which is unintentional collateral — feedback is authenticated-only and doesn't need bot gating.

The deploy pipeline fetches 13 secrets from Azure KeyVault and passes them through step outputs to `az containerapp update`. The step lacks `set -euo pipefail`, so a failed KeyVault fetch writes empty strings to outputs and the deploy proceeds with blank env vars, crashing silently until the 150-second health check timeout.

The canary job gates all three service deployments (backend, edge, frontend). Since the canary validates backend health, a transient Azure issue blocks unrelated edge and frontend deploys.

The Resend email client migrates to a native `httpx.AsyncClient`, eliminating thread-pool exhaustion. The new singleton is not registered with the lifespan shutdown sequence, unlike the four other HTTP clients that are explicitly closed.

## KeyVault secret injection via step outputs

The `Fetch secrets from KeyVault` step fetches 13 secrets and writes each to `$GITHUB_OUTPUT`. Step outputs are part of the workflow's run object and accessible via the API to anyone with `actions:read` on the repository. If the repository ever becomes public or an Actions token leaks, all 13 secrets are exposed.

A more robust pattern: use Container Apps `secretref` syntax in `--set-env-vars` pointing to KeyVault-backed Container Apps secrets, eliminating the need to read secret values in the workflow at all.

The step lacks error handling. If any `az keyvault secret show` fails (network blip, secret deleted), the shell variable is empty, and `$GITHUB_OUTPUT` gets an empty value. The deployment proceeds with empty env vars, causing a runtime crash that won't surface until the health check timeout 150 seconds later.

```yaml
# Missing at the top of the run block:
set -euo pipefail
```

## Auth token revocation asymmetry

The refresh endpoint returns 503 when Redis is unavailable for the revocation *check* (fail-closed). The asymmetry is in the *write* path: after issuing new tokens, if Redis fails to store the old jti as revoked, the code logs and continues. The old refresh token remains usable until its natural expiry (7 days). This breaks the guarantee that refresh-token rotation invalidates the previous token.

`LogoutRequest.refresh_token` is now a required `str` field. Clients that previously omitted it will get a 422 validation error — this is a breaking API change.

## Turnstile over-matching on chat routes

The edge worker condition:

```typescript
const requiresTurnstile = isAuthEndpoint ||
  (url.pathname.startsWith('/api/v1/chat') && request.method === 'POST');
```

Matches `/api/v1/chat/`, `/api/v1/chat/stream`, and `/api/v1/chat/feedback`. The feedback endpoint is registered at `/api/v1/chat/feedback` (mounted under the chat router at `/api/v1/chat` with sub-path `/feedback`). Feedback submission is from authenticated users providing thumbs-up/down on responses — requiring Turnstile here breaks the UX unless the frontend already sends tokens on every POST. The fix is to either check `url.pathname === '/api/v1/chat/' || url.pathname === '/api/v1/chat/stream'` or exclude the feedback path explicitly.

## Resend client lifecycle gap

The shutdown path in `main.py` explicitly closes `vertex_client`, `sarvam_client`, `embedder.close_http_client()`, and `razorpay_client`. The Resend client is missing. An unclosed `httpx.AsyncClient` during graceful shutdown may drop in-flight email requests without surfacing an error.

## Embedding token cache race

`_get_cached_token()` stores the token in module-level globals without a lock. Two concurrent coroutines hitting an expired cache will both call `token_provider()`, producing a burst of token acquisition calls to the Azure IMDS endpoint. Functionally safe (both get valid tokens), but under high concurrency at cache-refresh boundaries this wastes a round-trip. An `asyncio.Lock` would prevent this if IMDS latency becomes a concern.

## Webhook idempotency and duplicate emails

The webhook validates `event_id` presence (400 if missing) and checks Redis for duplicates. If Redis is unavailable, the check is skipped and processing continues. Since `subscription.charged` triggers `send_receipt_email`, a Redis outage during a Razorpay retry produces a duplicate email. Consider making the email send conditional on successful idempotency storage, or deduplicating at the email layer.
