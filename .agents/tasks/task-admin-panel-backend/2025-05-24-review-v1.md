# Admin panel backend: 15 router modules for 158 endpoints

Fifteen new FastAPI router modules provide the backend for a pre-built React admin panel. The frontend was calling ~158 admin API endpoints that all returned 404; this change wires them up. Endpoints fall into two categories: real data (dashboard stats, user management, conversations, alerts, settings) that query MongoDB via Beanie/Motor, and placeholders (SEO pipeline, Cloudflare analytics, GA4, IndexNow, etc.) that return static JSON with `"source": "placeholder"`. All endpoints gate on the same `_validate_admin_session` cookie check from the existing `admin.py`, and mutating operations also run `_csrf_check`. A test file covers auth guard rejection and response-shape validation for the primary endpoints.

**Watch for:** Unbounded `find_all().to_list()` in dashboard and analytics loads every chat document with full message arrays into memory (confirmed). Multiple update endpoints pass the raw request body directly into `$set` without field allow-listing, meaning an authenticated admin can overwrite arbitrary document fields including `_id` or inject operator keys (confirmed). The admin role-change endpoint allows an admin to grant `admin` role to any user, with no secondary confirmation or audit trail (confirmed).

---

## High-level view

Every endpoint calls `_validate_admin_session` (httponly JWT, checks `type=admin && role=admin`), and all mutating handlers run `_csrf_check`. The auth boundary is not weakened by this change.

The two dashboard/analytics endpoints that compute "total messages" pull the entire `chats` collection into Python and iterate in-process. As chat volume grows this becomes a memory bomb. A MongoDB aggregation pipeline would keep memory constant.

Settings, alert-settings, notification-prefs, plan-config, subject updates, and syra-prefs all accept the raw `request.json()` body and pass it directly to `$set`. There is no schema validation or field allow-list. The risk is bounded by admin-only access, but a compromised session or confused-deputy frontend bug would have unchecked write authority over those collections.

The conversations endpoint performs an N+1 user lookup: for each chat in a page of 50, it issues a separate `User.find_one()`. At scale this is 50 round-trips per page load.

Roughly 60% of the endpoint surface is placeholder stubs returning static JSON. These exist solely to stop the frontend from seeing 404s. They introduce no runtime risk but significantly inflate the route table and make it harder to audit what's real.

## Memory-unbounded dashboard aggregation

Both `admin_dashboard.py` and `admin_analytics.py` compute total message counts by loading the full chat collection into Python:

```python
all_chats = await Chat.find_all().to_list()
total_messages = sum(len(c.messages) for c in all_chats)
```

Each Chat document embeds a `messages` array. With 10k chats averaging 20 messages each, this materializes hundreds of megabytes in a single request handler. The graceful fallback (returning zeros on exception) won't save an OOM kill. A MongoDB aggregation pipeline like `[{"$project": {"msg_count": {"$size": "$messages"}}}, {"$group": {"_id": null, "total": {"$sum": "$msg_count"}}}]` keeps memory constant regardless of collection size.

The same pattern repeats for "messages today" in the dashboard, where only today's chats are loaded but still fully materialized with their message arrays.

## Unvalidated document writes via raw `$set`

The settings update pattern appears in at least six endpoints:

```python
body = await request.json()
await db.site_settings.update_one({"_id": "main"}, {"$set": body}, upsert=True)
```

Potential consequences:

- A field named `_id` in the body causes a write error on existing docs, but on the upsert path it can create a document with a non-standard `_id`.
- Fields like `$unset` or `$rename` would be rejected by Motor's server-side validation, but the error surfaces as a 500 with the raw exception message leaked to the client via `detail=str(e)`.
- Any field the application doesn't expect (e.g., `is_superadmin: true`) gets persisted silently and could be read back by a future code path.

The fix is a small allow-list per endpoint: `allowed = {"registrations_open", "maintenance_mode", "app_name", "tagline", ...}; body = {k: v for k, v in body.items() if k in allowed}`.

## Admin role escalation without audit

`admin_users.py` validates that the new role is one of `("student", "educator", "admin")` but performs no additional check when the target role is `admin`. A compromised admin session can silently grant admin access to any user account. At minimum, admin-role grants should write to the `audit_log` collection with the acting admin's `sub` claim and the target user ID.

## N+1 user resolution in conversations

```python
for chat in chats:
    if chat.user_id:
        user = await User.find_one({"_id": ObjectId(chat.user_id)})
```

For a page of 50 conversations, this issues up to 50 sequential database round-trips. The fix: collect unique `user_id` values from the page, issue a single `User.find({"_id": {"$in": user_ids}}).to_list()`, build a lookup dict, and resolve in-memory.

## Duplicate route: `/alerts/unacknowledged-count`

`admin_dashboard.py` registers `GET /alerts/unacknowledged-count` (line 97) and `admin_alerts.py` registers an identical route (line 50). Both routers are mounted at `/api/v1/admin`. FastAPI resolves to the first registered match, so the `admin_alerts.py` version is unreachable dead code. Remove the duplicate from `admin_dashboard.py` since the alerts module is the canonical location.

## Error message leakage

Several endpoints expose raw Python exception messages to the client:

```python
raise HTTPException(status_code=500, detail=str(e))
```

This can leak internal paths, collection names, or driver error details. Admin-only exposure reduces the blast radius, but a generic "Internal error" with a correlation ID logged server-side is safer practice.

## Test coverage gaps

The test file validates auth guards (7 endpoints) and response shapes (7 endpoints). Not tested:

- Any mutating endpoint (PATCH/POST/DELETE) — no write-path coverage at all.
- The CSRF check rejection path (e.g., POST without valid Origin header).
- The `admin_security` block/unblock IP flow.
- The `admin_alerts` acknowledge/acknowledge-all flow.
- Any endpoint that performs a write and verifies the DB state.

The auth-guard and shape tests are a good foundation but leave the write paths entirely unexercised.
