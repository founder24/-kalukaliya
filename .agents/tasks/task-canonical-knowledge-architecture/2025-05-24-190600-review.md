# Canonical Knowledge Architecture for Syrabit (v2)

A structured content system for the Syrabit educational platform: a `KnowledgeObject` Beanie model, a Jinja2 rendering pipeline publishing to Cloudflare KV and Azure Search, plus public content, admin CRUD, and SEO sitemap router groups. The six issues from v1 — autoescaping, public endpoint data leakage, sitemap memory, input validation, bulk publish, and draft exposure — have all been addressed. The remaining concerns are minor: the `generated` field is still exposed on the public JSON endpoint (MCQ answers visible to students), the `list_chapters` endpoint has no projection, and the sitemap projection doesn't fully isolate from unbounded growth.

**Watch for:** Public content JSON endpoint still exposes `generated.mcqs` with correct answers and explanations to unauthenticated users (confirmed). `list_chapters` loads full documents into memory without projection (confirmed). Bulk publish still has no batch-size cap or progress reporting, but the per-object try/except makes this a low-severity operational concern (confirmed).

**Verdict**: APPROVED

## High-level view

The public content JSON endpoint now filters by `is_published == True` and excludes `derivatives` and `page_views` via `model_dump(exclude=...)`. However, the entire `generated` sub-model (MCQs with answers, tutoring context) is still included in the response, which means students can read correct answers directly from the API.

Sitemap endpoints use a `SitemapProjection` Pydantic model with `.project()` so only the four URL-path fields are fetched from MongoDB. The `to_list()` call still materializes the full result set, but at ~100 bytes per projected document this is acceptable up to hundreds of thousands of objects — though the sitemap protocol's 50,000-URL-per-file limit will be hit first.

The `list_chapters` endpoint fetches full documents (including `body_markdown` and all generated content) but only uses five fields in its response. This is the same pattern the v1 sitemap issue exhibited, just on a smaller scale.

<summary>Issues (3)</summary>

1. **Public JSON leaks MCQ answers** — `GET /api/v1/content/{slug}` excludes `derivatives` and `page_views` but still returns `generated.mcqs` with `correct` and `explanation` fields visible to unauthenticated users. Exclude `generated` from the public response or strip answer fields before returning.
2. **`list_chapters` loads full documents** — The `/subject/{board}/{class_level}/{subject}` endpoint calls `.to_list()` without projection, fetching full `body_markdown` and `generated` content into memory for every chapter in a subject. Use a projection to fetch only the fields destructured in the response dict.
3. **Sitemap `to_list()` unbounded** — The projection reduces per-document size, but there's no limit on result count. For sitemaps exceeding 50,000 URLs (the sitemap protocol limit), the endpoint will produce invalid XML. Add a `limit(50000)` or paginate into multiple sitemap files.

## Public JSON exposes MCQ answers

The `get_content_json` endpoint in `content.py`:

```python
return ko.model_dump(by_alias=True, exclude={"derivatives", "page_views"})
```

The `generated` field contains `mcqs` with `correct` answer keys and `explanation` text, plus `tutoring_context` (internal prompt material). For an educational platform where MCQs are a learning tool, exposing answers in the API response defeats the purpose — a student can inspect the network response and see every correct answer without attempting the questions.

Either exclude `generated` entirely from the public endpoint (the admin endpoint already returns the full document), or build a response model that strips `correct` and `explanation` from each MCQ dict.

## `list_chapters` memory pressure

```python
chapters = await KnowledgeObject.find(
    KnowledgeObject.board == board,
    KnowledgeObject.class_level == class_level,
    KnowledgeObject.subject == subject,
    KnowledgeObject.is_published == True,
).to_list()
```

The response only uses `slug`, `chapter`, `topic`, `metadata.difficulty`, and `metadata.estimated_read_time_min`. A subject with 30 chapters means loading 30 full documents when only ~5 fields per document are needed. The same `SitemapProjection` pattern used in `seo.py` would work here with a subject-specific field set.

## Sitemap protocol limit

The sitemap protocol specifies a maximum of 50,000 URLs per sitemap file. The current implementation has no limit on the `to_list()` call. If the collection grows past 50,000 published objects, the generated XML will exceed the protocol limit and search engines will reject it. The sitemap-index pattern is already in place, so the fix is to add multiple numbered sub-sitemaps with a 50,000-URL cap per file.

At current scale this is not blocking, but it's a growth constraint worth noting.
