# Canonical Knowledge Architecture for Syrabit

A new structured content system for the Syrabit educational platform: a `KnowledgeObject` Beanie model storing board/class/subject/chapter educational content, a pipeline service that renders HTML via Jinja2, indexes to Azure Search, and publishes to Cloudflare KV and IndexNow, plus three router groups (public content, admin CRUD, SEO sitemaps). The architecture is sound — a single document drives five derived page types, search indexing, and edge caching — but the rendering engine has a correctness bug that makes the HTML output unusable, and the public content endpoint exposes internal generated content without access control.

**Watch for:** Jinja2 autoescaping double-escapes all rendered HTML body content and JSON-LD schemas (confirmed), public `/{slug}` endpoint exposes full `KnowledgeObject` including generated content and internal hashes without auth (confirmed), sitemap endpoints load all published objects into memory unbounded (confirmed).

## High-level view

The `KnowledgeObject` model is well-designed for this use case: a single document with content, metadata, derivative hashes, and generated content sub-models, indexed for both URL-path resolution and text search. The slug uniqueness constraint and compound index on `(board, class_level, subject, chapter)` will handle the access patterns cleanly.

The rendering pipeline has a fatal flaw: `Environment(autoescape=True)` combined with raw HTML strings passed as template variables means `body_html` and `json_ld_schemas` will be entity-escaped in the output. Every `<section>`, `<h2>`, and JSON-LD `<script>` tag becomes visible text instead of functional HTML. The tests don't catch this because they assert substring presence (e.g., `"DefinedTermSet" in html`) which matches the escaped `&quot;DefinedTermSet&quot;` representation.

The content pipeline's fail-soft design (each step wrapped in try/except, returns a status dict) is appropriate for a multi-step publishing workflow where partial completion is better than total failure. The placeholder AI generation produces minimal but structurally valid content.

The public content router exposes `/{slug}` as a catch-all that returns the full `model_dump()` of a `KnowledgeObject`, including `derivatives` (internal hash state), `generated` (AI-produced MCQs, summaries), and `page_views`. This endpoint has no auth and no field filtering.

Sitemap generation loads the entire `knowledge_objects` collection per request. With 10K+ objects this will OOM or time out.

<details>
<summary>Issues (6)</summary>

1. **Jinja2 autoescaping breaks HTML output** — `body_html` and `json_ld_schemas` are raw HTML/JSON strings rendered into a template with `autoescape=True`. Either mark them with `Markup()` or use `|safe` in the template. Without this fix, rendered pages are broken.
2. **Public JSON endpoint exposes internal state** — `GET /api/v1/content/{slug}` returns `model_dump()` with no field exclusion, leaking `derivatives`, `generated`, `page_views`, and metadata internals. Add a response model or exclude internal fields.
3. **Sitemap unbounded collection load** — Each sitemap endpoint calls `.find(is_published=True).to_list()` loading all objects into memory. Add pagination or use `.project()` to fetch only the fields needed for URL construction.
4. **Admin create endpoint accepts arbitrary dict fields without validation** — `create_or_update_knowledge` parses `request.json()` and passes `body["content"]` directly to `ContentBlock(**...)`. Malformed payloads will produce 500 errors instead of 400. Use a Pydantic request model.
5. **Bulk publish has no concurrency limit** — `run_bulk_publish` iterates all matching objects sequentially but with no batch size or error threshold. A large collection will run indefinitely as a background task with no visibility into progress.
6. **Content JSON endpoint has no `is_published` filter** — `GET /api/v1/content/{slug}` returns objects regardless of publish state, exposing draft content to the public.

## Jinja2 autoescape double-escaping

The `ContentRenderer` creates a Jinja2 `Environment(autoescape=True)` and renders a template containing `{{ body_html }}` and `{{ schema }}`. The `_render_body` method constructs raw HTML strings (`<section class="...">`, `<h2>`, `<ul>`, `<li>` tags) and `_build_json_ld` returns dicts that get `json.dumps`'d before template rendering. With autoescaping enabled, Jinja2 escapes all `<`, `>`, `&`, `"` characters in these variables.

The result: instead of a rendered HTML page, the browser sees escaped entities. The JSON-LD scripts become `&lt;script type=&quot;application/ld+json&quot;&gt;{...}&lt;/script&gt;` which crawlers cannot parse.

The fix is either:
- Wrap `body_html` and schema strings with `markupsafe.Markup()` before passing to `template.render()`
- Use `{{ body_html | safe }}` and `{{ schema | safe }}` in the template
- Switch to `autoescape=False` (less safe but this template has no user-facing input that isn't already generated server-side)

The tests don't catch this because assertions like `assert "BreadcrumbList" in html` match the escaped string `&quot;BreadcrumbList&quot;` — the substring is still present, just surrounded by escaped JSON. A test asserting `assert "<section" in html` would fail.

## Public content endpoint leaks internal state

```python
@router.get("/{slug}")
async def get_content_json(slug: str):
    ko = await KnowledgeObject.find_one(KnowledgeObject.slug == slug)
    if not ko:
        raise HTTPException(status_code=404, detail="Content not found")
    return ko.model_dump(by_alias=True)
```

This returns the entire document: `derivatives` (hash values the pipeline uses to detect staleness), `generated.mcqs` (AI-generated answers), `generated.tutoring_context`, `page_views`. There's also no `is_published == True` filter, so unpublished draft content is accessible to anyone who guesses or enumerates slugs.

For a public API endpoint, this should either use a response model that excludes internal fields, or return only the fields needed for frontend hydration (content, metadata, topic, board info).

## Sitemap memory scaling

All four sitemap endpoints follow this pattern:

```python
objects = await KnowledgeObject.find(
    KnowledgeObject.is_published == True
).to_list()
```

`to_list()` materializes the entire result set in memory. For the subjects sitemap, only `(board, class_level, subject)` tuples are needed — a MongoDB distinct or aggregation pipeline would be far more efficient. For the chapter/MCQ sitemaps, only the path-component fields are needed, not the full document with `content.body_markdown` and `generated.mcqs`.

At minimum, use `.project()` to fetch only the fields needed for URL construction. Better: use MongoDB aggregation for distinct subjects, and streaming/cursor-based generation for large sitemaps.

## Admin endpoint input validation gap

The `create_or_update_knowledge` endpoint deserializes `request.json()` into a plain dict, then constructs Pydantic models from it:

```python
ko_data = {
    "content": ContentBlock(**(body.get("content", {"body_markdown": ""}))),
    "metadata": ContentMetadata(**(body.get("metadata", {}))),
    ...
}
```

If `body["content"]` contains unexpected types (e.g., `body_markdown` as an integer), Pydantic will raise a `ValidationError` that FastAPI won't catch cleanly since the endpoint doesn't declare a request model. The error will propagate as a 500 Internal Server Error rather than a 422 with structured validation errors. Using a Pydantic `Body` model as the endpoint parameter would give automatic validation and better error messages.

## Bulk publish operational concerns

The bulk publish background task iterates every matching `KnowledgeObject` and calls `pipeline.publish()` on each one sequentially. Each `publish()` call involves: a MongoDB fetch, content generation, HTML rendering for 5 page types, Azure Search indexing, an IndexNow HTTP POST, and 5 Cloudflare KV PUT requests. For 1000 objects, this is 1000 sequential publishes with no progress reporting, no timeout, and no way to cancel.

The `try/except` per object prevents one failure from stopping the batch, which is correct. But there's no mechanism to report progress back to the admin, no limit on batch size, and no circuit breaker if external services (Cloudflare, Azure) are down.
