# Security fix, deploy guard bypass, and environment sync

This change fixes a critical prompt injection bypass in the streaming chat endpoint, replaces `REPLACE_ME` sentinel values in wrangler.toml with hex placeholders that pass the deploy-all CI guard, syncs `.env.shared` with all environment variables referenced in the codebase, corrects an impossible vite version constraint, and adds documentation comments for existing Turnstile enforcement and health-check redirects.

Watch for:
- **Dead-letter forensics loss** — the fix means `store_dead_letter` now receives the sanitized (normalized, zero-width-stripped) message instead of the raw user input; forensic analysis of injection attempts loses the original payload. (likely)
- **KV placeholder IDs** (`0000...000a`) will pass the `REPLACE_ME` grep guard but will cause a hard runtime failure if anyone deploys without replacing them — the warning comment is the only safety net. (confirmed)
- **pnpm-lock.yaml TypeScript version drift** — the lockfile adds `typescript@5.8.3` while retaining `typescript@6.0.3`, suggesting a specifier change not visible in this diff's `package.json` delta. (confirmed)

## High-level view

The security fix is a one-line change: `request_message=request.message` becomes `request_message=sanitized_message` in the streaming chat endpoint. This closed a path where the raw, unsanitized user message was passed through to `store_dead_letter` on double-LLM-failure, and more critically, where a crafted message that *passed* sanitization could still differ from the `sanitized_message` in subtle ways (Unicode normalization, zero-width stripping). The fix ensures the same normalized string flows through the entire pipeline. The trade-off is that dead-letter entries no longer preserve the original user input verbatim.

The wrangler.toml sentinel fix is a CI-focused workaround: `REPLACE_ME` strings are swapped for zero-padded hex IDs that satisfy the `grep -qi 'REPLACE_ME'` guard in deploy-all.yml. The ISR_CACHE_KV namespace will still fail at Cloudflare runtime since these aren't real namespace IDs — the guard prevents accidental deploys, but the new placeholders technically bypass that intent.

The `.env.shared` sync adds 15 variables across 4 new sections (KV config, edge worker bindings, SEO/IndexNow, cron secrets) to satisfy `check-env-sync.sh`. The script only fails on "undocumented" variables (used in code but missing from `.env.shared`); the 65 "unused" variables it reports are accessed via pydantic-settings, so the script's grep-based heuristic misses them.

The vite version fix (`^7.4.0` -> `^7.3.0`) corrects a constraint that could never resolve because vite 7.4.0 was never published. The lockfile pins 7.3.3, but also shows a TypeScript specifier changing from `~6.0.3` to `~5.8.3` that isn't reflected in the `package.json` portion of the diff.

## Streaming chat sanitization bypass

The `chat_stream` endpoint in `chat.py` calls `sanitize_user_input(request.message)` early and uses `sanitized_message` for language detection, RAG retrieval, and the `sanitized_message=` keyword argument to `stream_llm`. But it also passed `request_message=request.message` — the raw, un-normalized input — as a separate parameter.

Inside `ChatService.stream_llm`, `request_message` is used in exactly one place: `store_dead_letter(user_id, request_message, detected_lang, str(fallback_err))` when both the primary Sarvam provider and the Cloudflare fallback fail. A crafted message containing zero-width characters or Unicode confusables that survived the injection pattern check could reach the dead-letter store in its raw form. If any downstream system processes dead letters without re-sanitization, it's a latent injection vector.

The trade-off: dead-letter entries no longer preserve the original user input verbatim, which may matter for abuse forensics. If the team investigates failed messages, they'll see the normalized version only. Consider logging a SHA-256 of the raw input alongside the sanitized version for correlation without storing the dangerous payload.

## Deploy guard and KV namespace placeholders

The deploy-all.yml guard at line 216 runs:

```bash
grep -v '^\s*#' apps/edge/wrangler.toml | grep -qi 'REPLACE_ME'
```

The old sentinel values (`REPLACE_ME_WITH_REAL_KV_NAMESPACE_ID`) tripped this check and blocked deployment. The new values (`0000000000000000000000000000000a`) pass the grep because they don't contain the literal string `REPLACE_ME`.

This weakens the guard's protective value. A developer who forgets to create the KV namespace will now get past CI and hit a Cloudflare API error during actual deploy (`namespace not found`). The existing warning comment block above the binding is the only remaining safety net. The guard could additionally validate that the IDs aren't all-zeros, or the deploy step could run `wrangler deploy --dry-run` to catch invalid namespace IDs before the real deploy.

## Vite version constraint and lockfile

The lockfile diff shows `typescript` changing from `specifier: ~6.0.3 / version: 6.0.3` to `specifier: ~5.8.3 / version: 5.8.3`, while the `package.json` change in this diff only shows the vite line. Either the `package.json` TypeScript specifier was changed in a prior commit within this range, or it was an uncommitted change that got swept into `pnpm install`. Both `5.8.3` and `6.0.3` resolution entries remain in the lockfile, suggesting another workspace package still references TypeScript 6. Worth confirming this is intentional and not a lockfile corruption from concurrent edits.
