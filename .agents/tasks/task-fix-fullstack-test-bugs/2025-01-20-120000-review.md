# Six fullstack test-bug fixes across auth, payments, content, and resilience

This change fixes six distinct bugs discovered by the fullstack layer test script. The fixes span the circuit breaker (`get_status` using raw state instead of the timeout-checking property), a MongoDB ObjectId serialization failure in the content endpoint, missing error handling around Razorpay API calls, admin auth that only accepted cookies (now also accepts Bearer tokens), a webhook that rejected payloads using `event_id` instead of `id`, and a too-strict anon-ID validation regex. The most impactful change is making `_validate_admin_session` async and updating all ~47 call sites across 15 admin route files.

**Watch for:** The Bearer token fallback in admin auth introduces a privilege-escalation path if the DB lookup is bypassed or if token type claims are forged (confirmed). The broadened anon-ID pattern removes the structural guarantee that production IDs follow a known format (confirmed). The `reset()` method on the circuit breaker has no access control consideration noted (possible — depends on where it's exposed).

## High-level view

The admin auth change is the riskiest piece: it adds a second authentication path (Bearer token with DB lookup) that trusts any valid JWT with `type: "access"` to gain admin access if the user record has `role == "admin"`. A stolen access token now reaches admin endpoints, whereas before it could not. The async conversion's blast radius means a single missed `await` site would produce a coroutine-never-awaited bug that silently returns a truthy (non-dict) value, bypassing auth.

The payment fixes wrap Razorpay calls in try/except returning 503, but the bare `except Exception` conflates transient gateway failures with permanent credential errors. The `event_id` fallback in the webhook is a compatibility shim for test payloads that don't follow Razorpay's standard `id` field naming.

The anon-ID regex was relaxed from `^anon_[a-f0-9]{32}$` to `^[a-z][a-z0-9_-]{7,63}$`, which accepts the test format but also accepts arbitrary strings that the frontend may never generate. This removes a defense-in-depth constraint without replacing it with anything else.

<summary>Issues (5)</summary>

1. **Bearer token widens admin attack surface** (confirmed) — A stolen access token now grants admin access if the user has `role == "admin"` in the DB. Consider scoping admin Bearer auth to specific use cases or requiring a separate admin-scoped token.
2. **No fallback 403 on failed DB lookup** (confirmed) — If `User.get(user_id)` returns `None` (user deleted but token still valid), the code falls through to the generic `raise HTTPException(403, "Insufficient permissions")`, which is correct, but the error message doesn't distinguish "user not found" from "user exists but isn't admin." Low severity, but makes debugging harder.
3. **Anon-ID regex too permissive for production** (confirmed) — The new pattern `^[a-z][a-z0-9_-]{7,63}$` accepts strings the frontend never generates. If anon IDs are used as DB keys or cache keys, the relaxed format allows injection of crafted identifiers. Consider validating the production format separately and only relaxing for a test/dev mode.
4. **Circuit breaker `reset()` has no caller access control** (possible) — If `reset()` is exposed via an admin/health endpoint, any caller with access to that endpoint can force-close a circuit that should be open. Verify where `reset()` is called and whether it's protected.
5. **Bare `except Exception` in Razorpay calls** (likely) — Catching all exceptions means transient network errors and permanent credential errors are both reported as 503. The caller cannot distinguish "try again later" from "config is wrong." Consider catching `razorpay.errors.ServerError` separately from auth/validation errors.

## Admin auth: Bearer token fallback and async conversion

The Bearer path is tried only when the session cookie is absent, preserving the existing cookie-based flow for browsers. The token validation has two paths:

```python
# Path 1: token with type="admin" and role="admin" — trusted directly
if payload.get("type") == "admin" and payload.get("role") == "admin":
    return payload

# Path 2: access token — requires DB lookup to confirm role
if payload.get("type") == "access":
    user = await User.get(user_id)
    if user and user.role == "admin":
        return {...}
```

Path 1 trusts claims in the JWT itself. If the signing key is shared between admin and non-admin token issuance, an attacker who can influence token claims could forge an admin token. The security posture depends entirely on whether `type: "admin"` tokens are only ever minted by the admin login endpoint. If the regular auth endpoint also mints tokens with configurable `type` claims, this is exploitable.

Path 2 doesn't trust the token's role claim — it checks the DB. But it means every admin API call with a Bearer token hits the database, which is a latency consideration at scale.

The async conversion across 15 files is mechanical but high-blast-radius. If any call site was missed, the function returns a coroutine object (truthy), which would pass an `if payload:` check and effectively bypass auth. The task notes verify via AST that all sites were updated.

## Razorpay error handling in payment endpoints

The bare `except Exception` catch is broad. Razorpay's SDK raises `razorpay.errors.BadRequestError` for invalid parameters (a code bug, not a transient failure) and `razorpay.errors.ServerError` for gateway issues. Both return 503 to the client, which makes transient errors indistinguishable from configuration errors. A client retrying on 503 when the real problem is an invalid API key will retry forever.

## Anon-ID validation relaxation

The regex moved from `^anon_[a-f0-9]{32}$` (exactly 36 characters, structured format) to `^[a-z][a-z0-9_-]{7,63}$` (8-64 characters, lowercase alphanumeric with hyphens/underscores). By relaxing the backend validation, the constraint now lives nowhere — the frontend generates one format, the backend accepts many. If anon IDs become part of cache keys, database queries, or rate-limiting buckets, the wider format surface increases the risk of collisions or unexpected key patterns. The old format's entropy (128 bits from 32 hex chars) was a feature, not a limitation.

## Circuit breaker: `reset()` lacks state lock

The `reset()` method zeroes all counters and forces CLOSED but doesn't acquire `_state_lock`, which means a concurrent `call()` could be mid-execution when the reset happens. This is an asymmetry with the rest of the state management code which always acquires the lock. Low practical risk for a manual admin action, but worth noting.
