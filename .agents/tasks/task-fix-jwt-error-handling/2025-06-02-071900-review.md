# Catch-all exception handlers converted to 401 responses in JWT auth

The `get_current_user` dependency had a bare `raise` in its catch-all exception handler, propagating unexpected errors as 500s to callers. The `refresh_token_endpoint` lacked a catch-all entirely, meaning a `RuntimeError` from `_get_verification_key()` or a DB error would also surface as 500. Both are now converted to HTTP 401 responses. Three new tests confirm invalid tokens yield 401 across `/users/me`, `/auth/refresh`, and `/subscription/create-order`.

**Watch for:** The catch-all in `refresh_token_endpoint` masks operational failures (DB down, misconfigured keys) behind a 401 "Invalid or expired refresh token" message, making production debugging harder (confirmed). The log message in `get_current_user` still says "Unexpected database error" even though the handler now catches non-DB exceptions like `RuntimeError` from key misconfiguration (confirmed).

## High-level view

The fix is minimal and focused: one line changed from `raise` to `raise HTTPException(...)`, and one new `except Exception` block added. The pattern mirrors what already existed for `get_current_user`'s JWT-specific handlers and for other endpoints like signup/login. The `CollectionWasNotInitialized` check is preserved, routing genuine DB initialization failures to 503 before the generic 401.

The new tests are integration-level: they send malformed tokens through the full ASGI stack and assert the status code. The conftest mocks `User.get` and `User.find_one` to return None and disables rate limiting, so the tests exercise the JWT decoding path without needing a live database. Test coverage for the specific RuntimeError path (production RS256 misconfiguration) is absent.

## Masking operational errors as authentication failures

Both handlers now catch `Exception` and emit 401. The `_get_verification_key()` function raises `RuntimeError("RS256 JWT_PUBLIC_KEY required in production")` when the app is in production mode without a public key configured. This is an infrastructure misconfiguration, not an invalid token. Returning 401 to the client is misleading — the token might be perfectly valid, the server just can't verify it.

The existing pattern in the same file provides a precedent: when Redis is unavailable during token revocation in `refresh_token_endpoint`, the code raises 503. A `RuntimeError` from missing keys is semantically the same kind of failure — "the server cannot perform validation" — and should arguably get 503 rather than 401.

The log lines do fire (`logger.error`), so operators aren't completely blind, but the 401 response will cause clients to retry authentication rather than back off, potentially amplifying the problem.

## Log message mismatch in get_current_user

Line 313 logs `f"Unexpected database error: {e}"` but the handler now catches any `Exception`, including `RuntimeError` from `_get_verification_key()`. The log message predates this change (it existed when the handler only caught DB-related exceptions that leaked past the Beanie/Mongo layer). Now that it also handles key-verification failures, the "database error" label is inaccurate and could mislead on-call engineers searching logs.

## Test coverage gaps

The three new tests exercise the `InvalidTokenError` branch — the most common real-world failure (user sends garbage or expired token).

Not tested:

- `RuntimeError` from `_get_verification_key()` (requires patching `settings.APP_ENV = "production"` and removing `JWT_PUBLIC_KEY`)
- `CollectionWasNotInitialized` branch (requires patching `User.get` to raise that exception)
- The `get_current_user` handler receiving a non-JWT exception after successful decode but before user lookup (e.g., a network timeout from MongoDB)

These gaps represent the paths most likely to regress if the handler logic is modified again.
