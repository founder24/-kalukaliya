# CI pipeline fixes: lint, test setup, and workflow hardening

This change resolves CI failures on PR #220 through three categories of fix: removing unused Python variables flagged by ruff (F841), rewriting the Vitest test setup to work with Vitest 4.x's matcher registration model, and excluding three test files that import modules from a non-existent edge/worker package. A parallel effort hardens all 24 GitHub Actions workflow files — adding permissions blocks, downgrading `azure/login` from v3 (node24) to v2 (node20), and fixing string-to-number coercion bugs in `if:` conditions.

**Watch for:** The three excluded frontend test files are technical debt that will silently rot (confirmed). The `fromJSON()` fix in the canary deploy workflow depends on `printf "%.2f"` formatting — if `bc` fails on a runner, `printf` defaults to `"0.00"`, which would cause the canary to be promoted rather than rolled back (likely).

## High-level view

The Vitest setup change addresses a real incompatibility in Vitest 4.x where importing `@testing-library/jest-dom/vitest` brings in a separate `expect` instance, causing matchers to silently not register. The fix imports vitest's own `expect` and manually extends it. Three test files that depend on edge/worker modules (not part of the frontend workspace) are excluded rather than deleted — these are dead code that no CI pipeline will ever exercise.

The workflow hardening applies a consistent permissions model across all 24 workflow files, downgrades Azure login to a node20-compatible action version, and fixes four `if:` conditions that compared string step outputs against numeric literals. The `printf "%.2f"` normalization ensures `fromJSON()` always receives a parseable number, but the failure mode of `bc` itself is not guarded.

## Excluded edge/worker test files

Three test files are excluded via the vitest config's `test.exclude` array:

```
src/test/edge-do-routing.test.js
src/test/edge-proxy-kv-aggregation.test.ts
src/test/middleware-ssr-route.test.js
```

These import from paths like `../../workers/edge-proxy` and `../../functions/_middleware` — modules that live in the edge workspace (`apps/edge/`), not the frontend workspace. They were likely placed in the frontend test directory during a refactor that moved edge code to its own package. They represent dead test code that will never execute in any CI pipeline unless someone moves them to `apps/edge/` and wires them into that workspace's test config.

## fromJSON coercion and the bc formatting gap

GitHub Actions step outputs are always strings. The original conditions like `if: steps.monitor.outputs.error_rate > 2` performed string comparison, which produces wrong results at boundary values (lexicographic `"10.00" > "2"` is false). The fix wraps each output in `fromJSON()` to parse as a number.

To make `fromJSON()` safe, the `bc` output is piped through `printf "%.2f"`, which always produces a valid JSON number like `0.05` or `100.00` (raw `bc` with `scale=2` produces `.05` without a leading zero, which `fromJSON` cannot parse). The else branch hardcodes `"100.00"`.

The gap: if `bc` itself fails (not installed, division error), `printf "%.2f"` receives empty input and produces `"0.00"`. This wouldn't trigger rollback because `0.00 <= 2` evaluates to true, meaning a broken health check leads to canary promotion. The `validate` step catches the empty-string case but not the printf-defaulting-to-zero case, because `"0.00"` is not empty. Adding `set -o pipefail` to the run block or checking `$?` after `bc` would close this gap.
