# Hardening edge-to-backend trust and filling API gaps

This change addresses five audit findings (SEC-001, SEC-002, SEC-006, CFG-001, API-001) across the Cloudflare Edge worker and FastAPI backend. The approach: add RS256 JWT verification at the edge with algorithm auto-detection, replace the static shared-secret trust model between edge and backend with per-request HMAC-SHA256 signatures, loosen CSP to accommodate third-party scripts, add a production-time guard against misconfigured backend URLs, and introduce conversation CRUD endpoints.

**Watch for:** The edge JWT verifier silently falls back to HS256 when a token declares `RS256` but no public key is configured — an algorithm confusion vulnerability that undermines the asymmetric verification (confirmed). The anonymous conversation endpoints accept any client-supplied `x-anon-id` with no format validation, enabling enumeration of other users' anonymous chats (confirmed). The HMAC signature scheme signs `url.pathname` at the edge but verifies against `request.url.path` in the backend — if these ever differ due to middleware path normalization, signatures will break silently (likely).

## High-level view

The JWT verifier in the edge worker now parses the token header to determine `alg`, branching into RS256 (Web Crypto RSASSA-PKCS1-v1_5) or HS256 paths. It correctly rejects `alg: none`. However, when a token declares `RS256` but no public key is configured, it falls back to verifying with the HMAC secret — a classic algorithm confusion pattern that undermines the entire point of asymmetric verification.

The per-request HMAC scheme signs `timestamp:userId:path` at the edge and verifies it in the backend with a 30-second window. The backend preserves backward compatibility by allowing unsigned requests during rollover but logs a warning. The asymmetry between what the edge calls `url.pathname` (TypeScript `URL.pathname`) and what Python sees as `request.url.path` (Starlette) is unlikely to diverge today but is brittle under middleware that rewrites paths. The backward-compat legacy path has no sunset mechanism.

The conversation CRUD is a straightforward Beanie-backed set of endpoints. Authenticated endpoints use ownership checks via `user_id` matching. Anonymous endpoints rely entirely on a client-supplied `x-anon-id` header with no format validation or rate limiting, meaning anyone who guesses or enumerates the ID can read/delete another anonymous user's conversations. The shared `user_id` column creates a namespace collision risk between anonymous IDs and real user ObjectIds.

The production config guard rejects API requests if `AZURE_BACKEND_URL` contains `localhost`/`127.0.0.1` while `ALLOWED_ORIGIN` doesn't contain `localhost`. The wrangler.toml now ships a placeholder URL in production vars that triggers this guard if not overridden by a Wrangler secret, providing a fail-closed deployment default.

The CSP update permits Turnstile, PostHog, Sentry, and Cloudflare Web Analytics. The Sentry wildcards (`*.sentry.io`) are broader than necessary and could be narrowed to the project's DSN subdomain.

## RS256 verification and algorithm confusion

The problem is in `jwt.ts`:

```typescript
} else if (alg === 'HS256' || (alg === 'RS256' && !publicKey)) {
  // HS256 verification (or RS256 fallback when no public key is available)
```

If an attacker crafts a token with `alg: RS256` and the worker has no `JWT_PUBLIC_KEY` configured, verification falls through to HMAC with the shared `JWT_SECRET`. This means an attacker who obtains the symmetric secret (e.g., leaked env var) can forge tokens that claim to be RS256-signed but are verified with a weaker symmetric key. The fix: when `alg === 'RS256'` and no public key exists, throw an error rather than silently downgrading.

## Per-request HMAC signature (SEC-002)

Edge signs `${timestamp}:${userId}:${url.pathname}` with HMAC-SHA256, attaches `X-Edge-Signature` (hex) and `X-Edge-Timestamp`. Backend reconstructs the message and verifies with `hmac.compare_digest`. The 30-second staleness window is reasonable for clock drift.

The edge uses TypeScript's `url.pathname` and the backend uses Starlette's `request.url.path`. If any middleware (trailing-slash redirect, path normalization) alters the path between signature generation and verification, the HMAC will silently fail. A safer approach: have the edge send the signed path as an additional header so the backend verifies against the exact string that was signed.

The backward-compatibility fallback allows requests without `X-Edge-Signature` to pass through if the shared secret matches — with a deprecation warning logged. There's no enforcement timeline or feature flag to disable it. Without one, the weaker path persists indefinitely and SEC-002 provides no real security improvement until the legacy path is removed.

## Anonymous conversation endpoints and enumeration

The anonymous endpoints (`/anon`, `/anon/{id}`) identify users solely by a client-supplied `x-anon-id` header. There's no validation that this value is a UUID or follows any format, and no rate limiting on listing. An attacker can:

1. Supply a known user's anonymous ID (or iterate plausible values) to list their conversations.
2. Delete conversations belonging to other anonymous users.

Since anonymous chats store `user_id = anon_id` in the same `chats` collection as authenticated users, there's a namespace collision: if an anon-id happens to match a real user's ObjectId string, the anonymous endpoints would return that user's conversations. The ownership check (`chat.user_id != anon_id`) doesn't distinguish between authenticated and anonymous ownership.

Mitigations: validate `x-anon-id` as a UUID v4, prefix anonymous IDs with `anon:` in the database to prevent namespace collisions, and add rate limiting to the anon endpoints.

## Production config guard (CFG-001)

The detection heuristic (`!env.ALLOWED_ORIGIN?.includes('localhost')`) treats any non-localhost origin as "production." A staging environment with `ALLOWED_ORIGIN = "https://staging.syrabit.ai"` would also reject localhost backends. This is likely fine (staging shouldn't use localhost either), but the error message ("Backend URL misconfiguration detected") doesn't help an operator understand they need to set a Wrangler secret.
