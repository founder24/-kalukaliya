# Topic embedding gate for the chat RAG pipeline

The chat pipeline now generates a Vertex AI embedding for each user query and compares it against pre-computed topic embeddings stored in MongoDB. If no topic matches above 0.70 cosine similarity, RAG retrieval is skipped entirely and the LLM responds without context. Embeddings are generated during content publish (step 8) and stored as `TopicEmbedding` Beanie documents. A backfill script handles the existing corpus.

Watch for: the embedding API call adds serial latency to every non-generic query (confirmed); token refresh happens on every call without caching, unlike the existing vertex_client pattern (confirmed); the streaming endpoint blocks on `check_topic_match` before starting history load in parallel (confirmed).

## High-level view

The token-per-call pattern in `_get_embedding_access_token` is the most actionable performance issue. The existing `vertex_client.py` caches tokens with a lock and 60-second buffer before expiry. The new embedder creates credentials from scratch on every invocation, adding ~200-400ms of token-refresh latency to every chat request that isn't caught by the generic-query regex.

In the non-streaming `/chat` endpoint, `check_topic_match` runs inside `_maybe_retrieve()` which executes in parallel with history load and rate-limit check — the latency impact is absorbed into the existing gather. In the streaming endpoint, `check_topic_match` runs sequentially *before* the `asyncio.gather` that loads history, meaning history load cannot overlap with the embedding call. This asymmetry adds unnecessary TTFB to streams.

The in-memory cache of all topic embeddings is a pragmatic choice at current scale. The 5-minute TTL and `invalidate_cache()` on publish provide reasonable freshness. The vectorized numpy approach (single matrix multiply) is efficient. The concern is what happens when the cache reload races with concurrent requests — there's no lock, so multiple requests arriving during a TTL expiry can trigger parallel MongoDB loads.

The content publisher generates one embedding per topic sequentially, which is fine for publish-time work. The backfill script follows the same pattern with a 100ms sleep between topics to avoid rate-limiting.

## Token refresh on every embedding call

`_get_embedding_access_token` (embedder.py:96-130) constructs `service_account.Credentials` from the settings JSON and refreshes them on every invocation. The existing `vertex_client.py` (line 124-175) solves this with a `_cached_token`, `_token_expiry`, and an `asyncio.Lock` for safe concurrent refresh. Without this, every chat request that passes the generic-query filter pays a full OAuth2 token-refresh round-trip (~200-400ms to Google's token endpoint).

```python
# vertex_client.py pattern (what embedder should replicate):
if self._cached_token and _time.time() < self._token_expiry - 60:
    return self._cached_token
async with self._token_lock:
    ...
```

The fix is straightforward: module-level `_cached_token`, `_token_expiry`, and `_token_lock` variables in embedder.py, or better yet, reuse the singleton `vertex_client` instance's token since it uses the same scopes.

## Streaming endpoint latency asymmetry

In the non-streaming `/chat` endpoint, the embedding check runs inside `_maybe_retrieve()` which is gathered in parallel with `load_conversation_history` and `check_rate_limit`. This is well-structured — the embedding latency overlaps with other I/O.

In the streaming `/chat/stream` endpoint (chat.py lines 508-528), `check_topic_match` is awaited *before* the `asyncio.gather` that loads history:

```python
topic_match = await ChatService.check_topic_match(sanitized_message)  # serial
if topic_match is None:
    context_chunks, history = await asyncio.gather(   # only then parallel
        _noop_context(),
        ChatService.load_conversation_history(request.session_id),
    )
```

History load (~5-50ms for Redis cache hit, longer for MongoDB fallback) could execute in parallel with the embedding API call. Restructuring to gather both would shave that off TTFB.

## httpx client lifecycle

`generate_embedding_vector` creates a new `httpx.AsyncClient` per call (embedder.py:75). Each new client means a fresh TCP connection and TLS handshake to `{location}-aiplatform.googleapis.com`. At chat-time, this adds ~50-100ms. A module-level client (or one owned by a singleton like `vertex_client`) would reuse the connection pool.

## Cache reload race condition

`TopicMatcher.match_topic` checks `_is_cache_valid()` without a lock. Under load, if multiple requests arrive right after TTL expiry, each will independently call `_load_embeddings`, which loads all documents from MongoDB. This is wasteful but not incorrect — it won't corrupt state because Python's GIL protects the final assignment. However, it can spike MongoDB read load proportional to request concurrency during the TTL boundary. An `asyncio.Lock` around the reload, with a double-check inside, would deduplicate.

## No timeout wrapping the embedding call in chat path

`ChatService.check_topic_match` (chat_service.py:119-127) calls `generate_embedding_vector` and `topic_matcher.match_topic` with no timeout. The downstream `retrieve_context` wraps its work in `asyncio.wait_for(..., timeout=0.8)`, but the embedding call happens *before* that. If Vertex AI takes 3 seconds to return, the total RAG phase exceeds the intended 0.8s budget, degrading user-perceived latency. A dedicated timeout (e.g., 0.5s) on the embedding call would fail fast and fall through to LLM-only mode.

## Failed MongoDB load poisons cache for full TTL

In `_load_embeddings` (topic_matcher.py:57-62), when `TopicEmbedding.find_all().to_list()` throws, the method catches the exception, sets `self._embeddings = []` and stamps `self._last_load = time.time()`. This means `_is_cache_valid()` returns True for the next 5 minutes, during which all queries will see an empty embedding set and skip RAG. A transient MongoDB hiccup becomes a 5-minute outage of the topic-matching gate. Either don't stamp `_last_load` on error (so the next request retries immediately) or use a much shorter error-state TTL (e.g., 10 seconds).

## Content publisher: sequential embedding generation

`_generate_topic_embeddings` (content_publisher.py) calls `generate_embedding_vector` sequentially for each topic. A chapter with 15 topics will take 15 * (token_refresh + API_call) = potentially 15-30 seconds. This is publish-time work so it doesn't affect chat latency, but it means publish operations are significantly slower. If token caching is added, this drops to 15 * ~100ms = 1.5s which is acceptable. Without token caching, this is the other side of the same issue.

## Test coverage observations

The 13 tests cover cosine similarity correctness, cache behavior, integration with `ChatService.check_topic_match`, and error handling (embedding generation failure returns None). The tests mock MongoDB access and embedding generation appropriately.

Not tested: behavior when `_load_embeddings` fails (MongoDB down), race conditions on cache reload, behavior of the chat endpoints' topic-match logging paths in integration, and the content publisher's `_generate_topic_embeddings` method.
