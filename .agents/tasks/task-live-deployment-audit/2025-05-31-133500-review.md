# Live deployment audit script for syrabit.ai

A 5266-line bash script that performs ~500 automated checks against the live syrabit.ai production deployment, covering DNS, TLS, security headers, performance benchmarking, API completeness, data integrity, deployment configuration, compliance/SEO, and monitoring. It produces a scored Production Readiness percentage and supports JSON/HTML export. The script is well-structured with per-section functions, color output, and multiple execution modes (quick, section-specific, full).

Watch for: The script hardcodes the GCP project ID and infrastructure details into a committed, publicly-visible file (**confirmed**). Several check patterns have false-positive/false-negative risks due to loose string matching (**likely**). The `set -euo pipefail` combined with certain subshell patterns could cause silent early exits in edge cases (**possible**).

## High-level view

The script follows a clean section-per-function architecture with shared helper utilities (`perform_request`, `check_pass/fail/warn/critical`, `add_json_result`). Each of the 8 sections is independently callable via `--section N`. The `perform_request` helper wraps curl with timing metrics and populates global variables, which the check functions then evaluate with simple conditionals. Scoring is straightforward: PASS=1.0, WARN=0.5, FAIL/CRITICAL=0.0, reported as a percentage.

The security checks cover OWASP headers, CORS, JWT algorithm confusion, path traversal, host header injection, and sensitive file exposure. The coverage is broad but shallow — it confirms the presence or absence of protections rather than deeply probing them. The CORS test only checks three origin variants; the JWT test only checks `alg:none`.

The performance section measures TTFB, compression, concurrency, and sustained load. The cold-start detection approach (measuring variance across 5 requests) is a reasonable heuristic but won't reliably distinguish cold starts from network jitter when running from a single geographic location.

The script hardcodes production infrastructure identifiers (GCP project `blissful-acumen-495019-t6`, region `asia-south1`, domains `syrabit.ai` and `api.syrabit.ai`) with env-var overrides. These are exposed in a public repository — not a credentials leak, but operational details that some teams prefer to keep private.

## Double-counting in the critical path

The `check_critical` function increments both the FAIL and CRITICAL counters:

```bash
check_critical() {
    local msg="$1"
    TOTAL_CHECKS=$((TOTAL_CHECKS + 1))
    TOTAL_CRITICAL=$((TOTAL_CRITICAL + 1))
    TOTAL_FAIL=$((TOTAL_FAIL + 1))       # <-- also counted as fail
    ...
    SECTION_CRITICAL[$idx]=$(( ${SECTION_CRITICAL[$idx]} + 1 ))
    SECTION_FAIL[$idx]=$(( ${SECTION_FAIL[$idx]} + 1 ))  # <-- also here
    ...
}
```

The scoring formula only uses `TOTAL_PASS` and `TOTAL_WARN` (both FAIL and CRITICAL contribute 0 points), so the score calculation is correct. But the summary output prints "Failed: N" and "Critical: M" separately, where N already includes M. A reader seeing "Failed: 5, Critical: 2" would think 7 issues exist when only 5 do.

## JSON export fragility

The `add_json_result` function escapes double quotes with sed but doesn't handle other JSON-special characters: literal backslashes, control characters (newlines are stripped, but tabs aren't), or multi-byte sequences that could confuse jq's `--arg`. The `|| echo "$JSON_RESULTS"` fallback means a single malformed message silently drops that check from the JSON export without any warning.

## `body_contains` reliance on GNU grep

```bash
body_contains() {
    local needle="$1"
    local body="${2:-$RESP_BODY}"
    if echo "$body" | grep -qi "$needle" 2>/dev/null; then
        return 0
    fi
    return 1
}
```

Call sites pass needles like `"turnstile\|cf-turnstile\|challenges.cloudflare.com"` and `"rel=\"preload\""`. The `\|` alternation is a GNU grep extension to BRE. On macOS BSD grep or minimal Alpine containers, this won't match alternations. Since the script header comment says "Requirements: bash, curl, jq, openssl, dig" without specifying GNU grep, this could fail on some environments.

## Temp file and directory leaks

`perform_request` is called hundreds of times, each creating two temp files. The cleanup is immediate (`rm -f "$tmpbody" "$tmpheaders"`), but a `SIGINT` during any of the hundreds of curl operations leaves orphans. A `trap cleanup EXIT` at the top level that removes a dedicated temp directory would be more robust.

## CORS validation gap

The CORS test for evil origins sends an OPTIONS request:

```bash
perform_request "$BASE_URL/health" \
    -H "Origin: https://evil-site.com" \
    -X OPTIONS \
    -H "Access-Control-Request-Method: GET"
```

If the backend doesn't implement OPTIONS on `/health` (many don't — FastAPI doesn't auto-add CORS preflight handling without middleware), the response might be 405 with no CORS headers at all. The check then sees no `access-control-allow-origin` header and reports "CORS rejects evil-site.com origin" — a true positive for "doesn't reflect the origin" but a false positive for "has origin validation." The distinction matters: the backend may allow the evil origin on an actual GET request with credentials even though it doesn't answer the preflight.

## Script portability and the pipefail interaction

The `set -euo pipefail` at the top means any pipeline where a component fails will exit the script. Most uses are safe (grep is in conditionals or has `|| true`), but a few patterns in the HTML export section use pipes with grep that could theoretically fail:

```bash
echo "$JSON_RESULTS" | jq -r '...' >> "$output_file" 2>/dev/null || true
```

This is correctly guarded. The risk is low but the `|| true` pattern is applied inconsistently — some sections rely on `2>/dev/null` alone without `|| true`, which under pipefail could cause issues if jq or a preceding command in the pipeline fails.
