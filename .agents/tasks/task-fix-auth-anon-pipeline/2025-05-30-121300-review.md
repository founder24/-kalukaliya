# Anonymous access pipeline for chat history

This change opens the `/chat/history` and `/chat/conversations` endpoints to anonymous users by switching from mandatory auth (`get_current_user`) to optional auth (`get_current_user_optional`). Anonymous users are identified by the `x-anon-id` request header and receive a hard-capped 5-entry history. The edge worker's `OPTIONAL_AUTH_PATHS` is widened to allow unauthenticated requests through to the `/api/v1/conversations` prefix. A new test file exercises the anonymous path, the cap enforcement, and the authenticated-user bypass.

**Watch for:** The `/chat/history` endpoint accepts any string as `anon_id` without format validation (**confirmed**), unlike the sibling `/conversations/anon` endpoint which enforces a strict `anon_[a-f0-9]{32}` pattern. The edge worker prefix match on `/api/v1/conversations` now makes JWT optional for *all* conversation sub-paths including authenticated-only endpoints like `DELETE /conversations/{id}` (**confirmed** — defense still exists at the backend layer, but the edge no longer rejects tokenless requests early).

## High-level view

The backend change gives two endpoints an anonymous branch guarded by the presence of `x-anon-id`. Authenticated users flow through unchanged logic; anonymous users get an early-return empty list when no identifier is present, or a capped query when one is. The constant `ANON_HISTORY_LIMIT = 5` is defined in both `chat.py` and `conversations.py` — worth noting if the cap ever needs coordinated change.

The edge worker change widens the prefix `/api/v1/conversations` in `OPTIONAL_AUTH_PATHS`. Because matching uses `startsWith`, this covers every sub-route under that prefix — including endpoints that still enforce auth at the backend. No access control bypass occurs, but the edge loses its ability to reject tokenless requests early for authenticated conversation endpoints.

The anonymous path in `/chat/history` does not validate the `x-anon-id` header format. An arbitrary string will be used as a MongoDB query filter. The `/conversations/anon` endpoint validates against `anon_[a-f0-9]{32}` before querying. This asymmetry means the history endpoint can be probed with any user_id value — a data leak vector limited to 5 entries per request.

## Anon_id used as unvalidated query filter

In `chat.py`, the anonymous branch reads the header and queries directly:

```python
anon_id = http_request.headers.get("x-anon-id") or http_request.headers.get("X-Anon-ID")
# ... no format check ...
chats = await Chat.find({"user_id": anon_id}).sort("-updated_at").skip(skip).limit(limit).to_list()
```

The `conversations.py` file applies `_validate_anon_id` which enforces `^anon_[a-f0-9]{32}$`. Without this check in the history endpoint, a caller can pass an authenticated user's ID as the `x-anon-id` header and retrieve their chat history (limited to 5 entries, but still a data leak). The fix is a one-line import and call to the same validator before querying.

## Edge prefix-match widens optional auth surface

The OPTIONAL_AUTH_PATHS matching uses `startsWith`:

```typescript
const isOptionalAuth = OPTIONAL_AUTH_PATHS.some((p) => url.pathname.startsWith(p));
```

Previously, only `/api/v1/conversations/anon` was listed, which narrowly covered the anonymous endpoint. The new entry `/api/v1/conversations` now matches every path under that prefix:

- `GET /api/v1/conversations` (authenticated — `list_conversations`)
- `DELETE /api/v1/conversations/{id}` (authenticated)
- `PATCH /api/v1/conversations/{id}` (authenticated)
- `GET /api/v1/conversations/{id}` (authenticated)

The backend still enforces auth via `Depends(get_current_user)` so no actual access bypass occurs. But the edge was previously the first line of defense rejecting tokenless requests before they hit the backend. If the intent was only to cover the `/chat/history` alias (mounted at `/api/v1/chat/conversations`), this prefix is unnecessary since `/api/v1/chat` was already listed.

## Test coverage

Not tested: what happens when `x-anon-id` contains an authenticated user's ID (the validation gap), and the behavior of the `/chat/conversations` legacy alias (only the `/chat/history` path is tested directly).
