# Azure-to-GCP migration: Vertex AI Search for RAG, Cloud Run for hosting

A full-stack platform migration that rips out Azure Cognitive Search and Container Apps, replacing them with Google Cloud's Vertex AI Search (Discovery Engine) for RAG retrieval and Cloud Run for backend hosting. The change touches 56 files across the backend (Python), edge worker (TypeScript), CI/CD pipeline, infrastructure-as-code, and documentation. The search interface contract (return format from `search_context()`) is preserved so the chat service continues to work unchanged.

The approach is clean: a new `vertex_search.py` module mirrors the interface of the deleted `azure_search.py`, the edge worker's `AZURE_BACKEND_URL` becomes `BACKEND_URL`, and the deploy pipeline swaps ACR/Container Apps steps for Artifact Registry/Cloud Run steps. Circuit breaker, Redis caching, and graceful degradation patterns carry over.

**Watch for:** The search indexer's create-then-update-per-document strategy will be extremely slow for large batch operations (confirmed). The Vertex Search filter syntax uses `ANY()` which requires the field to be configured as a repeated/filterable field in the datastore, but the schema declares `tier_access` only as indexable, not explicitly filterable — this needs verification (likely). The `content_publisher.py` creates a new `DocumentServiceClient` on every publish call rather than reusing one (confirmed).

## High-level view

The Vertex AI Search integration follows the same singleton pattern as the old Azure client: credentials are loaded from `GOOGLE_APPLICATION_CREDENTIALS_JSON` at import time, the sync Discovery Engine client is wrapped in `asyncio.to_thread` for async compatibility, and the circuit breaker gates all external calls. The key architectural risk is that Discovery Engine's sync client is invoked per-document in indexing loops, making batch ingestion O(n) network round-trips with no parallelism.

The CI/CD migration uses Workload Identity Federation (replacing Azure OIDC login), Artifact Registry (replacing ACR), and `gcloud run deploy` with `--set-secrets` mapping secrets from Secret Manager. The rollback job identifies the previous Cloud Run revision and reroutes traffic. One edge case: on a first-ever deploy with only one revision, the rollback will exit 1 rather than silently no-op, which is the right failure mode.

The edge worker rename from `AZURE_BACKEND_URL` to `BACKEND_URL` is thorough — every TypeScript source file, test file, and wrangler binding was caught. The production wrangler.toml defaults to a sentinel value (`https://MUST-BE-CONFIGURED.run.app`) that the edge worker's localhost-detection won't catch, meaning a missing secret produces connection errors rather than a clean 503.

The `.env.shared` template defines `BACKEND_URL` twice (edge bindings section and Cloud Run section) — different contexts, same value — which could confuse a new contributor.

<summary>Issues (6)</summary>

1. **Per-document indexing with no parallelism** — `search_indexer.py` issues one `create_document` (then potentially one `update_document`) per chunk sequentially via `asyncio.to_thread`. For a knowledge object with 50+ chunks, this will be very slow. Use `import_documents` batch API or at minimum `asyncio.gather` with bounded concurrency.
2. **Client instantiation on every publish** — `content_publisher.py` creates a new `DocumentServiceClient` (including credential parsing) on every `publish_to_vertex_search()` call. Cache the client as an instance attribute or module-level singleton.
3. **Filter syntax vs schema alignment** — The filter `tier_access: ANY("free")` uses a repeated-field operator on a scalar string field. Discovery Engine may reject this or silently return no results. Use `tier_access = "free"` for equality filtering, or verify `ANY()` works on scalars in a real datastore.
4. **Score extraction always returns 0** — `vertex_search.py` tries `getattr(result, "model_scores", {}).get("score", 0)` but Discovery Engine search results don't expose a `model_scores` attribute. Every result gets `score: 0`. If downstream logic ever sorts by score, ordering will be arbitrary.
5. **Seed script error handling masks partial failures** — `seed-search.py` catches create/update failures per-chunk with a warning and continues. A batch with 90% failures still returns success if at least one document imported.
6. **Duplicate BACKEND_URL in .env.shared** — The template defines `BACKEND_URL` in both the "Edge Worker Bindings" section and the "Google Cloud Run" section, creating ambiguity about the source of truth.

## Discovery Engine score extraction gap

The score extraction logic in `vertex_search.py` will silently produce zeros:

```python
"score": getattr(result, "model_scores", {}).get("score", 0)
    if hasattr(result, "model_scores")
    else 0,
```

Discovery Engine `SearchResponse.SearchResult` doesn't have a `model_scores` field. The relevance signal comes from result ordering (implicit rank) or from `modelScores` only when a custom ranking model is attached. Without a custom model, every result gets `score: 0` and `reranker_score: 0`, making the response format technically contract-compatible but informationally empty. If downstream logic ever sorts or filters by score, it'll get arbitrary ordering.

## Batch indexing performance gap

The `SearchIndexer.index_knowledge_object()` method calls `create_document` for each chunk individually, falling back to `update_document` on failure. For a typical knowledge object chunked into 20-50 segments, this means 20-50 sequential gRPC calls (or 40-100 if creates fail and updates are needed).

Discovery Engine offers `import_documents` for bulk operations, accepting inline documents or a GCS source. Even without switching to the batch API, the sequential `asyncio.to_thread` calls could be parallelized with `asyncio.gather` and a semaphore. The current pattern makes reindexing an entire content library prohibitively slow.

The same pattern appears in `content_publisher.py`:

```python
for doc in documents:
    doc.name = f"{parent}/documents/{doc.id}"
    request = discoveryengine_v1.UpdateDocumentRequest(...)
    await asyncio.to_thread(client.update_document, request=request)
```

Additionally, `publish_to_vertex_search` instantiates a fresh `DocumentServiceClient` and parses `GOOGLE_APPLICATION_CREDENTIALS_JSON` on every invocation. The search service (`vertex_search.py`) correctly initializes the client once in `__init__`; the publisher should follow the same pattern.

## Schema and filter compatibility

The `ANY()` filter operator in Discovery Engine is designed for repeated fields (arrays). For a single-value string field like `tier_access`, the correct filter syntax is `tier_access = "free"`. The `ANY()` operator may still work (treating a scalar as a single-element collection) but this is undocumented behavior that should be tested against a real datastore before relying on it in production.

The schema retains a `content_vector` field typed as `STRING` with all capabilities disabled — vestigial from the Azure schema where embeddings were stored explicitly. Since Discovery Engine handles embedding internally, this field serves no purpose and creates a confusing signal in the schema definition.

## Edge worker sentinel and missing CI guard

The production wrangler.toml sets `BACKEND_URL = "https://MUST-BE-CONFIGURED.run.app"` as a default that must be overridden by a Wrangler secret. The edge worker's safety check only looks for `localhost` or `127.0.0.1`:

```typescript
const isLocalBackend = env.BACKEND_URL?.includes('localhost') || env.BACKEND_URL?.includes('127.0.0.1');
```

The sentinel won't trigger this guard, so a missing secret produces connection errors rather than a clean 503. The CI pipeline's "Guard: check for KV sentinel IDs" step checks `wrangler.toml` for `REPLACE_ME` but not for `MUST-BE-CONFIGURED`. A similar guard for the backend URL sentinel could catch deploy-before-configure mistakes.
