# Fullstack layer-by-layer cloud shell test script

A 2097-line bash script that validates the Syrabit AI platform end-to-end through 18 layers of curl-based HTTP tests. The script is a deployment verification tool designed to run from a cloud shell or CI against a live or staging environment, covering frontend health, edge worker behavior, auth flows, chat (streaming and non-streaming), content APIs, payments/webhooks, and cross-cutting concerns like CORS and rate limiting. It follows established patterns from the existing `live-deployment-test.sh` with colored output, pass/fail/warn/skip helpers, timed requests, and a summary section.

**Watch for:** Token leakage in verbose mode logs the full curl command including `Authorization: Bearer <token>` (confirmed). Temp files from `perform_request` will leak if the script is killed mid-request because `set -e` can cause early exit between `mktemp` and `rm -f` (confirmed). The `--layer` flag doesn't run layer 4 (auth) before layers 5–18, so authenticated tests silently degrade to skip when a single layer is selected (confirmed).

## High-level view

The script is structured as a reusable `perform_request` function wrapping curl with timing instrumentation, and 19 `test_layer_N_*` functions each exercising a slice of the platform. Most unexpected responses are treated as warnings rather than failures, which tolerates partial rollouts and third-party service degradation but means the script will report "all critical checks passed" even when significant functionality is broken — it only fails on complete unreachability (layers 0–3).

Authentication state flows forward through global variables: layer 4 obtains a token from credentials or environment, and layers 5–18 use it if present. When `--layer N` runs a single layer in isolation, layer 4 is skipped, so the token is never populated unless the caller provides `TEST_JWT_TOKEN`. A `--layer 12` run with `ADMIN_EMAIL` set will skip all admin tests because no login occurred.

The script itself leaks secrets through its verbose logging — `VERBOSE=1` prints full curl commands including bearer tokens. The configuration display correctly redacts `ADMIN_PASSWORD`, making the curl-logging leak inconsistent and easy to miss.

<summary>Issues (5)</summary>

1. **Token leakage in verbose mode** — `verbose_log "curl ${curl_cmd[*]}"` prints the full curl command array including `-H "Authorization: Bearer <real-token>"`. Redact bearer tokens from debug output or replace with a placeholder.
2. **Temp file leak on early exit** — `perform_request` creates two temp files via `mktemp`, then removes them at the end. If `set -e` triggers an exit between creation and cleanup (e.g., a jq parse failure), the files persist. Use a trap or move the rm into a cleanup function.
3. **Single-layer mode skips auth** — Running `--layer 8` with `ADMIN_EMAIL`/`ADMIN_PASSWORD` set will not obtain a token because layer 4 is skipped. Document this limitation in `--help` or auto-run layer 4 when `AUTH_TOKEN` is empty and credentials are available.
4. **JSON export vulnerable to injection** — The `EXPORT_JSON` heredoc interpolates `$BASE_URL` and `$FRONTEND_URL` directly into JSON without escaping. A URL containing a double quote breaks the output file. Use jq to produce the JSON instead of cat-heredoc.
5. **`set -u` interaction with empty `$@`** — `local extra_args=("$@")` when called with no extra arguments expands to an empty array, which in older bash (< 4.4) with `set -u` triggers an "unbound variable" error. The `${#extra_args[@]}` guard works only if bash >= 4.4. Minimum bash version is undocumented.

## Token and credential exposure in verbose mode

Line 257 logs the full curl command array: `verbose_log "curl ${curl_cmd[*]}"`. By this point `curl_cmd` contains arguments like `-H "Authorization: Bearer eyJ..."`. Anyone running with `VERBOSE=1` in a CI pipeline will have tokens printed to the build log. Line 691 also logs partial response body from an admin login attempt, which could contain token material depending on the API response format.

The configuration display redacts `ADMIN_PASSWORD` (line 359), showing awareness of the issue — but the curl command logging undoes this protection for any request that carries auth headers.

Fix: filter `curl_cmd` before logging, replacing any value following `-H "Authorization:` with a redacted placeholder.

## Temp file lifecycle under `set -e`

`perform_request` (lines 237–269) and `perform_stream_request` (lines 272–292) both follow this pattern:

```bash
tmpfile=$(mktemp)
header_file=$(mktemp)
# ... curl ...
CURL_STATUS=$(echo "$timing_json" | jq -r '.status // 0')
CURL_BODY=$(cat "$tmpfile" 2>/dev/null || echo "")
rm -f "$tmpfile" "$header_file"
```

If any unguarded command between mktemp and rm fails under `set -e`, the temp files persist. The risk is low for the current code (jq failures are handled) but grows as the script evolves. A trap-based cleanup at the function level would be more defensive.

## `--layer` isolation and auth dependency

The `main()` function's `--layer` handler runs layer 0 followed by the selected layer only. It does not run layer 4 unless explicitly requested:

- `--layer 5` through `--layer 18` will find `AUTH_TOKEN=""` unless `TEST_JWT_TOKEN` is set in the environment
- `ADMIN_EMAIL` + `ADMIN_PASSWORD` do nothing in single-layer mode (requires two invocations or explicit `TEST_JWT_TOKEN`)

A user running `./fullstack-layer-test.sh --layer 12` with admin credentials set will see everything skipped with no explanation of why.

## JSON export injection surface

Lines 2071–2085:

```bash
cat > "$json_file" << JSONEOF
{
  "base_url": "$BASE_URL",
  ...
}
JSONEOF
```

`$BASE_URL` is user-controlled input. If it contains `"` or `\`, the resulting file is invalid JSON. Using `jq -n --arg base "$BASE_URL" ...` would produce guaranteed-valid output.

## CSRF test cannot distinguish "not enforced" from "wrong credentials"

Layer 18 tests CSRF by sending a POST with `Origin: https://evil-site.example.com` and expects HTTP 403. If the server processes the request normally (returning 401 for bad credentials rather than 403 for wrong origin), that's indistinguishable from "CSRF is not enforced server-side." The script reports this as a warning, which is the safe default, but a reviewer should understand this test can never confirm CSRF enforcement is absent — only that it's present.
