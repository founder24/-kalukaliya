# Cookie consent banner, SPA rewrite rules, and sitemap lastmod dates

Three unrelated SEO/compliance changes bundled in one diff: a cookie consent UI component, Cloudflare Pages rewrite rules to prevent 308 redirects on key routes, and `<lastmod>` elements added to the static sitemap XML. The component follows the existing PWAInstallPrompt pattern (lazy-loaded, localStorage-gated, fixed-position banner). The redirects fix is a standard CF Pages technique. The sitemap dates are hardcoded.

Watch for: The cookie consent banner is cosmetic only — analytics (PostHog via Cloudflare Zaraz) fires unconditionally regardless of the user's choice (confirmed). The banner creates a legal compliance gap rather than solving one.

## High-level view

The CookieConsent component records the user's preference in localStorage but never communicates that decision to any analytics system. PostHog is loaded via `dns-prefetch` in index.html and captured through Cloudflare Zaraz's global interception — neither checks `syrabit_cookie_consent` before tracking. The banner gives users the impression of control without delivering it, which in GDPR/ePrivacy jurisdictions is arguably worse than no banner at all.

The `_redirects` additions are correctly placed before the trailing-slash 301 rules, so CF Pages will serve `index.html` with a 200 for `/login`, `/signup`, `/about`, `/privacy`, and `/terms` without triggering its default 308 trailing-slash behaviour. Because `_routes.json` includes `/*` and doesn't exclude these paths, the rules are compatible with the Worker routing.

The sitemap `<lastmod>` dates use a static `2025-01-15` value across all entries in both the index and the static urlset. The date will drift from reality over time since nothing updates it on deploy. The dynamic sitemaps (subjects, chapters, topics) already derive lastmod from `updated_at` in the database, so only the static sitemap has this staleness risk — and the index-level lastmod will mislead crawlers about sub-sitemap freshness.

## Consent banner without enforcement

The component stores one of two values: `'accepted'` or `'declined'`. The analytics module in `utils/analytics.jsx` calls `window.posthog.capture()` without checking this key. PostHog itself is initialized by Cloudflare Zaraz at the CDN edge layer — it's not even loaded by application JavaScript that could be conditionally imported. The `dns-prefetch` hints in `index.html` for `us.i.posthog.com` and `us-assets.i.posthog.com` confirm the tracking infrastructure loads before any React component mounts.

For GDPR compliance, the consent value needs to be read before any tracking call fires. The practical options are: (1) wrap the `track()` helper in `analytics.jsx` with a `localStorage.getItem(CONSENT_KEY) === 'accepted'` guard, which handles the PostHog `capture()` calls but not the Zaraz-level page view tracking; or (2) configure Zaraz's consent mode to check a cookie/localStorage key before injecting PostHog, which handles everything but requires Cloudflare dashboard configuration outside this codebase.

If neither enforcement path is viable right now, the banner should be reframed as a notice ("We use cookies for analytics") without Accept/Decline buttons — just a dismiss action. This avoids the legal exposure of offering a "Decline" that doesn't decline anything.

## Sitemap index lastmod vs dynamic sub-sitemaps

`SITEMAP_INDEX_XML` uses `{base_url}` as a format placeholder but the `<lastmod>` values are baked into the template string as `2025-01-15`. The dynamic sub-sitemaps (subjects, chapters, topics) are regenerated from the database on each request, so their actual freshness diverges from what the index claims. A crawler checking the index to decide whether to re-fetch sub-sitemaps will see a stale date and may skip re-crawling after content updates. The index-level lastmod should ideally be derived at runtime from the max `updated_at` across knowledge objects, or at minimum from a deploy-time timestamp.
