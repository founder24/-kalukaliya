# GCP/Vertex AI infrastructure setup automation

A new shell script (`infra/gcp/setup-vertex.sh`, 481 lines) automates the full GCP infrastructure provisioning for the Syrabit backend: project creation, API enablement, service account with IAM roles, Vertex AI Search datastore and engine creation via REST API, Artifact Registry setup, and key generation. The script is idempotent (checks for existing resources before creating) and supports a `--dry-run` flag. It ends by printing the environment variables the backend needs.

**Watch for:** The script dumps an entire service account key JSON into stdout (confirmed), the schema applied inline diverges from the canonical `vertex-search-schema.json` format already in the repo (confirmed), and the `--dry-run` path silently skips the schema-application step rather than printing the equivalent curl command (confirmed).

## High-level view

The script is structured as seven sequential sections, each gated by idempotency checks. gcloud CLI handles project, IAM, Artifact Registry; curl + REST handles Discovery Engine resources since gcloud lacks CLI support there.

Security posture centers on generating a long-lived service account key and printing its full JSON content to the terminal. This is a common bootstrap pattern for local dev but conflicts with the adjacent `clouddeploy.yaml` that implies production Cloud Run usage, where Workload Identity would be the expected credential mechanism. No mention of key rotation or Workload Identity migration appears.

The schema embedded inline in the curl body uses a different format (`structSchema` with JSON Schema types) than the existing `vertex-search-schema.json` file (which uses `structDefinition` with `fields` array and `STRING` types). Maintaining two schema definitions invites drift.

The dry-run mode is incomplete: the REST API sections have their own conditional blocks that print *some* planned operations, but the schema-application step inside the datastore section only executes in live mode with no dry-run echo.

## Service account key handling and credential exposure

The final output section runs `cat "$KEY_FILE_PATH" | tr -d '\n'` and echoes the result as the suggested value for `GOOGLE_APPLICATION_CREDENTIALS_JSON`. This prints the full private key material to the terminal, which ends up in shell history, scrollback buffers, and potentially CI logs if someone runs this in automation. The `chmod 600` on the key file is good, but the echo undoes that protection by sending the same content to stdout.

The script would be safer printing only the file path and instructing the user to read it themselves:

```bash
echo "GOOGLE_APPLICATION_CREDENTIALS_JSON=<paste content of ${KEY_FILE_PATH}>"
```

The generated key is a long-lived credential with no rotation mechanism. The `clouddeploy.yaml` in the same directory defines a Cloud Run service, which natively supports Workload Identity (no key needed). The script's next-steps section should mention this migration path.

## Schema duplication and format mismatch

The script applies a schema using a `structSchema` payload with JSON Schema `"type": "string"` annotations and custom properties like `"indexable"`, `"retrievable"`, `"searchable"`, `"completable"`. Meanwhile, `infra/gcp/vertex-search-schema.json` already exists and defines the same fields using a `structDefinition.fields` array with `"type": "STRING"` values.

Both formats may be accepted by different Discovery Engine API endpoints/versions, but maintaining two representations of the same schema invites drift. The script could instead read from the existing JSON file, or the script's format could replace the file entirely. As-is, if someone updates the field list in one place, the other goes stale.

## Dry-run coverage gap

The `--dry-run` path handles three situations differently:

1. gcloud commands route through `run_cmd`, which prints the command string — complete.
2. REST API calls (datastore creation, engine creation) have explicit `if DRY_RUN` blocks that print the planned URL and body — complete.
3. The schema PATCH call at the end of Section 4 sits *inside* the `else` branch (live-only) with no dry-run equivalent.

Running `--dry-run` produces no indication that schema application would occur, so the dry-run output under-represents what the live run actually does.

## Hardcoded wait before schema application

After datastore creation, the script `sleep 10` before applying the schema. Discovery Engine datastore creation is asynchronous (returns a long-running operation). If the datastore takes longer than 10 seconds to become ready — which happens on first project setup when quotas are being provisioned — the schema PATCH will fail with no retry. A polling loop on the operation status or a retry with backoff would be more robust. For a setup script run interactively and re-runnable, this is tolerable but will confuse users on first failure.
